## 1. 임베딩 모델 정밀도 — fp32 / fp16 / int8 (TRIP-518)

### 문제

임베딩 모델(`nlpai-lab/KURE-v1`, bge-m3 계열 568M 파라미터, 1024차원)의 fp32 가중치가
**2,271 MB**다. AI 이미지에 넣으면 FastAPI 경계 한 줄 고칠 때마다 2GB를 다시 굽는다.
안 넣었더니 **KB 검색 3종이 컨테이너에서 404로 죽어 있었다**(2026-09-01 발견). 넣기도
안 넣기도 애매한 크기라 컨테이너를 분리했고(TRIP-517), 분리한 이미지를 얼마나 줄일 수
있는지가 이 측정의 질문이다.

### 무엇을 바꿨나

빌드 단계에서 **fp16으로 저장**하고(`ai/embedding/bake_model.py` — `state_dict`를 half로
바꿔 `load_state_dict(..., assign=True)` 후 `model.save()`), 런타임에 **fp32로 되올려**
쓴다(`ai/embedding/app.py._load()` → `model[0].auto_model.float()`).
이미지에는 fp16 파일만 들어가고 연산은 종전 fp32 경로 그대로다.

### 실측 결과

> 측정일 2026-09-01 · macOS arm64 · **전 변형 CPU 4스레드 고정** · KB-3 24건 × 질의 6종
> 재현: `uv run python scripts/measure_embedding_precision.py`

| 변형 | 이미지 크기 | 크기비 | 인코딩 지연 | 지연비 | 코사인 최소/평균 | top4 순위 유지 |
|---|---:|---:|---:|---:|---:|---|
| fp32 (종전) | 2,271 MB | 1.00× | 576 ms | 1.00× | — | 기준 |
| **fp16 저장 → fp32 로드 (채택)** | **1,136 MB** | **0.50×** | **595 ms** | **1.05×** | **1.00000 / 1.00000** | **6/6 질의 · 24/24 위치** |
| int8 동적 양자화 | 1,362 MB | 0.60× | 1,764 ms | 3.06× | 0.97651 / 0.98103 | 1/6 질의 · 19/24 위치 |
| fp16 저장 → fp16 연산 | 1,136 MB | 0.50× | 37,741 ms | 19.13× | 0.99998 / 1.00000 | 5/6 질의 |

fp16 왕복이 실제로 일어났는지 검증한 값:

```
검사 텐서: embeddings.word_embeddings.weight (250002, 1024)
  변경된 원소: 110,256,473 / 256,002,048 (43.1%)
  최대 절대오차: 2.441e-04
```

### 왜 이 값으로 정했나

- **이미지에서 무거운 건 가중치 파일이지 런타임 dtype이 아니다.** fp16 저장이면 파일이
  정확히 절반이고, 로드할 때 fp32로 올리면 연산은 같은 경로를 탄다. 남는 손실은
  `fp32 → fp16 → fp32` 반올림 **한 번**뿐이다.
- 가중치의 **43%가 바뀌었는데도** 문서 임베딩 코사인이 소수점 5자리까지 1.00000이고
  6개 질의 top4가 **24/24 위치 전부 동일**했다. 정규화된 1024차원 임베딩에서 개별
  가중치의 2e-4 오차가 상쇄된 결과다. 검색이 소비처이므로 절대 점수가 아니라
  **순위가 바뀌는지**가 유일한 판정 기준이다.
- **int8은 세 축 전부에서 진다** — 더 크고(1,362 > 1,136 MB), 3배 느리고, 6개 질의 중
  5개에서 top4가 달라졌다. 검토 종료.
- **fp16을 연산까지 끌고 가면 19배 느리다** — CPU에 fp16 고속 경로가 없어 매 연산이
  에뮬레이션을 탄다. 배포 대상이 CPU 컨테이너인 한 못 쓴다.

### 측정에 걸린 함정 셋 (전부 "조용히 틀린 답"을 준다)

1. **`st[0].auto_model = 변환결과`가 예외 없이 무시된다.** `sentence_transformers` 6.x의
   `Transformer.auto_model`은 setter 없는 property(`self.model` 별칭)다. 대입하면
   `nn.Module.__setattr__`이 `_modules`에 넣지만 조회는 클래스 property가 가로채 원본을
   돌려준다. 모르고 재면 원본 fp32가 그대로 돌면서 "손실 없는 양자화"로 읽힌다 —
   이 측정의 1차 결론이 실제로 *"int8은 no-op"* 이었고, `nn.Linear` 개수를 세어 보고서야
   (145 → 0, 양자화 모듈 290) 변환은 정상이고 대입이 문제임이 드러났다. 그래서 스크립트가
   교체 후 모듈 수를 `assert` 한다. **성능 개선이 공짜로 보이면 개선이 아니라 적용이 안 된
   것을 먼저 의심한다.**
2. **크기를 `parameters()` 합으로 재면 안 된다.** 양자화 모듈의 packed params는
   `nn.Parameter`가 아니라 안 잡힌다 — int8이 fp32보다 **커 보인다**(실측 2,271 → 3,329 MB).
   이미지에 실리는 건 직렬화 파일이므로 `state_dict`를 `torch.save`한 바이트로 잰다.
3. **변형끼리 device가 다르면 지연 비교가 통째로 무효다.** `SentenceTransformer(...)`는
   device를 자동 선택한다(측정 머신에서는 MPS). 1차 측정이 기준만 자동, 비교군만 CPU여서
   지연비가 무의미했다. 배포 대상(CPU)으로 전부 고정한다.

### 같은 서빙 경로의 부수 조치 (참고)

| 조치 | 값 | 근거 |
|---|---|---|
| 기동 백그라운드 워밍 (#448) | 스레드 1개, `/health`의 `loaded`로 진행 노출 | 워밍 없이 띄우면 첫 요청이 콜드스타트 3.5초를 물어 임베딩 상한(3초)을 넘겨 KB 검색 하나가 `EmbeddingUnreachable: timed out`으로 강등 (2026-09-02 실측) |
| 임베딩 호출 마감 3.0 → 5.0초 (#456, 2026-09-02) | `_DEFAULT_TIMEOUT_SEC = 5.0` | 3초가 콜드스타트(3.5초)를 못 덮었다. 5초가 실질 상한 — 요청 경로가 임베딩을 **직렬 3회** 부르므로 5초면 검색 최악 15초, 여기에 LLM 몫이 더 붙는다 |
| 컨테이너 메모리 한도 5g (#464, 2026-09-08) | `mem_limit: 5g` | 실측 2026-09-02: 워밍 직후 4.29GiB · 배치 상한 256건 인코딩 후 4.37GiB. 관측 정점 대비 15% 여유 |

### 남은 한계

- **품질(코사인·순위)은 하드웨어 무관이지만 지연은 아니다.** 배포 대상 리눅스 컨테이너에서
  재측정해야 한다 — 특히 x86_64는 양자화 백엔드가 fbgemm이라 int8 지연이 다를 수 있다
  (품질 손실은 그대로라 결론은 안 바뀔 것으로 본다).
- 이미지가 절반이 된 뒤의 **실제 이미지 크기·콜드스타트는 미측정**(TRIP-517 몫).
- 더 공격적인 압축(torchao, ONNX Runtime)은 다음 후보지만, fp16이 **새 의존성 0으로**
  절반을 주므로 지금 그 비용을 치를 이유가 없다.

## 2. Cascade routing 임계값 튜닝 (TRIP-653 → 657 → 678)

### 문제

의도 파악을 LLM 단발 호출에 맡기면 (a) 표현 다양성에 약하고 (b) EDIT/REPLAN/GENERATE
경계에서 오라우팅이 비싼 실패가 되며 (c) 축적·보정 구조가 없다
(`intent-matching-design.md` §1). 그래서 3단 캐스케이드로 바꿨다 —
**1차 뱅크 임베딩 매칭(LLM 0회) → 2차 유사질문 생성 + 가중 투표 → 3차 LLM 직접 분류.**
임계값이 곧 "LLM 호출량 ↔ 정확도" 다이얼이다.

```
[1] 뱅크 top-k(k=5)
      top1 ≥ t_high ∧ top1·top2 의도 일치 → CONFIDENT (LLM 0회)
      top1 ≥ t_mid                        → 2차
      그 외                                → 3차
[2] 유사질문 n개 생성 → 원문 포함 재매칭 → 유사도 가중 투표
      최다 득표율 ≥ vote_ratio → VOTED / 미달 → 3차
[3] LLM 직접 분류(closed-set 라벨 강제) → 실패 시 결정론 폴백
```

### 무엇을 바꿨나 (조정 이력)

| 파라미터 | before | after | 날짜 | 티켓 / PR |
|---|---:|---:|---|---|
| `t_high` | 0.88 | **0.82** | 2026-09-02 | TRIP-657 (#459) — 계측 기반은 TRIP-653 (#449) |
| `vote_ratio` | 0.60 | **0.80** | 2026-09-08 | TRIP-678 (#477) |
| `t_mid` | 0.75 | 0.75 (무변) | — | 초기값 유지 — **조정 근거 미측정** |
| `k` | 5 | 5 (무변) | — | 초기값 유지 — **조정 근거 미측정** |
| `n_paraphrase` | 3 | 3 (무변) | — | 초기값 유지 — **조정 근거 미측정** |

### 실측 결과

**t_high 0.88 → 0.82** (라벨 발화 30건 · KURE-v1 임베딩 · LangSmith `trippilot-intent`)

| 항목 | 값 |
|---|---|
| in-scope 발화 중 top1 ≥ 0.80 | 전건 정답 의도 |
| LLM 호출량 | **−30%** (1차 CONFIDENT 전환분) |
| 정확도 | **손실 0** |
| 관측된 최고점 오분류 | 범위 밖 발화가 뱅크 경계 문장("저녁에 맛집 하나 넣어줘")에 **0.783** |
| 채택값과의 여유 | 0.037 |

**vote_ratio 0.60 → 0.80** (§6 평가셋 88건 × 운영 배정(PARAPHRASE=Claude) · `scripts/trace_intents.py --eval data/intent_eval_set.yaml`)

| 항목 | vote_ratio 0.60 | vote_ratio 0.80 |
|---|---:|---:|
| 정확도 | 86/88 | **88/88** |
| LLM 호출량 | 기준 | **+16%** |
| p95 지연 | 3.4 s | **5.5 s** |

득표율 분포는 **1.0 / 0.73~0.76 양봉**이다 — 유사질문이 결정론(Claude temperature 0)이면
투표는 "만장일치" 아니면 "두 의도 동률"로 갈린다. 동률대(0.73~0.76)의 투표 정답률은
**3/5**인 반면 그 구간을 3차로 넘기면 LLM이 **승격분 전건 정답**이었다.

### 왜 이 값으로 정했나

- **0.82**: 관측된 최상단 오분류(0.783)보다 위이면서, 전건 정답이던 0.80 대역을 살리는
  가장 낮은 값. 여유 0.037은 넓지 않다 — 그래서 **뱅크 검수(§3.3) 전까지의 하한**으로
  못 박았다. 여유를 더 주면(0.85+) 정답 발화가 다시 2·3차로 새어 호출이 늘고, 낮추면
  범위 밖 발화가 CONFIDENT로 통과한다.
- **0.80**: 양봉 사이의 골에 임계를 놓아 "동률대는 전부 3차로" 라는 규칙이 되게 한 값.
  투표가 동률일 때는 투표보다 LLM이 낫다는 것이 관측이고, 그 대가(+16% 호출, p95 +2.1s)를
  정확도 2건(86→88)과 맞바꿨다. 라우터가 사용자 대기 경로에 아직 안 붙어 있어(아래 한계)
  p95 상승의 실제 UX 비용은 **아직 지불되지 않았다** — 배선 시 재평가할 값이다.
- 임계값은 **하드코딩하지 않는다**(`IntentRouterConfig` 주입, `__post_init__`이
  `0 ≤ t_mid ≤ t_high ≤ 1`·`vote_ratio ∈ (0,1]`을 강제). 설계 §5의 요구 그대로다.

### 남은 한계

- **라우터가 어느 요청 경로에서도 실행되지 않는다**(TRIP-529 미배선). `api/wiring.py`가
  `IntentRouter`를 import하지 않고, 열려 있는 경계는 의도를 인자로 받지 않는다.
  위 수치는 전부 오프라인 러너(`scripts/trace_intents.py`)가 넣은 발화 기준이다.
- 평가셋 라벨이 **사람 검수를 거치지 않았다** — 거치면 `vote_ratio`를 재확인한다(TRIP-678 기재).
- 뱅크 검수(§3.3) 미완 → `t_high` 0.82는 잠정 하한.
- LangSmith는 **dev 그룹**이라 운영 이미지(`uv sync --no-dev`)에 없다(TRIP-656) —
  발화 유출 가드를 의존성 부재로 보장한 대가로 **운영 환경 관측이 구조적으로 불가능**하다.
  배선 후 운영 관측이 필요하면 의존성 승격 + 마스킹·샘플링을 함께 결정해야 한다.
- `t_mid`·`k`·`n_paraphrase`는 초기값 그대로이고 **스윕 측정이 없다**.

## 3. 적응형 청킹과 병렬 스케줄링 (TRIP-373 → 376 → 378 → 380)

### 문제

`PREFERENCE_SCORING` 실호출 지연이 **바닥 ~3s + 건당 ~0.2s 선형**이다(TRIP-373 실측:
7건 3.2s, 193건 단일 호출 **44.5s**). 실전 후보 풀이 193건이라 단일 호출은 단계 예산
14s 밖이다. 그 전에는 더 나빴다 — 게이트웨이 기본 2.5s 배분에서는 **LLM 점수가 구조적으로
한 번도 쓰이지 않았다**(TRIP-376).

### 무엇을 바꿨나

| 단계 | 조치 | 날짜 / PR |
|---|---|---|
| TRIP-376 | 고정 분할 폐기 → **단계별 상한 + 어셈블리는 잔여 전부**. 점수 단계 상한 2.5s → **14s** | 2026-08-15 (#207) |
| TRIP-378 | **병렬 청킹** — poi_id 정렬 균등 분할, 청크별 `gateway.call`을 스레드로 동시 실행 후 병합 | 2026-08-15 (#209) |
| TRIP-380 | 고정 상수 `score_chunk_size=20` → **예산 유도 공식** + `as_completed(timeout=)` **벽시계 마감** | 2026-08-16 (#211) |

**유도식** (`workers/preference.adaptive_chunk_size`):

```
T_target = stage_budget / safety                 safety = 2.0
c*       = clamp(⌊(T_target − base) ÷ per_item⌋, chunk_min, chunk_max)
           base = 3,000 ms · per_item = 200 ms · [chunk_min, chunk_max] = [5, 40]
병렬수 N = ⌈풀 ÷ c*⌉, 상한 score_max_parallel = 10
```

### 실측 결과

**예산 → 청크 크기** (기본 파라미터)

| 단계 예산 | c* | 비고 |
|---:|---:|---|
| 14 s | **20** | TRIP-378 고정 상수를 정확히 재현 (현행 동등) |
| 10 s | 10 | |
| 8 s | 5 | |
| 4 s | 5 | `chunk_min` 클램프 |

**예산 배분** (`agents/schedule/budget.allocate`, 어셈블리 바닥을 **먼저** 뗀다)

| 전체 예산 | 어셈블리 바닥 | 후보 풀 상한 | 점수 단계 상한 |
|---:|---:|---:|---:|
| 5,000 ms (day1) | 2,500 | 750 | 1,750 — 실호출 바닥 ~3s > 상한이라 **규칙 점수 유지가 의도** |
| 20,000 ms (전체) | 5,000 | 1,000 | 14,000 |

**관측된 변동** — 실측 변동 3~4배(TRIP-373), 청크 편차 **4.8 ~ 19.5 s**(TRIP-380 계측).

### 왜 이 값으로 정했나

- **`as_completed(timeout=단계 예산)`으로 벽시계를 강제한 이유**: SDK read-timeout
  (`LlmRequest.timeout_sec`)은 **바이트 간격 기준**이라 총 시간을 못 막는다 — 실측에서
  **19.5s 청크가 14s 타임아웃에도 "성공"으로 완료**됐다. 슬로 테일이 그대로 deadline을
  잠식했고, 이전 504 사건의 동인이 이것이다. 마감까지 완료된 청크만 수용하므로
  **점수 단계 소요 ≤ 단계 예산이 구조적으로 보장**된다.
  - `with ThreadPoolExecutor(...)`(= `shutdown(wait=True)`)를 쓰지 않는다 — 마감 넘긴
    스레드를 기다리면 그 보장이 깨진다. 마감 후 `shutdown(wait=False, cancel_futures=True)`로
    즉시 반환하고, 유기 스레드의 늦은 완료는 폐기한다(future 강제 취소는 불가).
- **안전율 2.0**: 실측 변동이 3~4배이고 청크 편차가 4.8~19.5s라, 기대 소요가 예산의
  절반에 오도록 목표 시간을 잡았다. 내림(`⌊⌋`)도 같은 방향의 보수적 선택이다.
- **클램프 [5, 40]**: 너무 작으면 호출 바닥(3s)만 반복 지불하고, 너무 크면 슬로 테일
  한 방이 단계 전체를 삼킨다.
- **균등 분할**: 가장 느린 청크가 벽시계를 정하므로, 고정 크기 자투리(193 → 20×9+13)가
  아니라 균형 분할(20×3+19×7)로 **최대 청크를 키우지 않는다.**
- **결정론 병합**: 수용된 청크를 도착 순서가 아니라 **청크 인덱스 순**으로 병합하고,
  중복 poi_id는 첫 등장 우선, 병합 후 전체 풀 기준으로 다시 교차한다(INV-1 2겹 —
  청크 게이트 + 병합 후). 같은 입력·같은 성공 집합이면 항상 같은 산출이다.
- **침묵 금지**: 청크 수·성공/실패/마감초과를 `ScoreChunkEvent`로 남긴다
  (`success + failure + timed_out = chunk_count`). 부분 실패는 성공분만 `value`에 싣고
  `error="partial_chunks_failed:n/m"`으로 표시하며, 미완 POI의 규칙 점수 보충은 호출측 몫이다.

### 남은 한계

- 공식 파라미터(`base` 3,000 ms · `per_item` 200 ms)는 **TRIP-373 시점 모델·프롬프트의
  실측**이다. 예산이 바뀌면 c*가 자동 추종하지만 **모델이 바뀌면 재측정해야 한다** —
  현재 재측정 기록 없음.
- 병렬 상한 10의 **벤더 rate limit 영향은 미측정**.
- 마감 초과 청크의 POI가 규칙 점수로 채워질 때의 **품질 저하는 계량되지 않았다**
  (건수는 `ScoreChunkEvent`에 남지만 점수 품질 지표는 없다).
- 청킹 도입 전후의 **엔드투엔드 지연 비교표가 없다** — 단일 호출 44.5s와 단계 예산 14s는
  각각 측정됐지만, 같은 조건에서 나란히 잰 표는 저장소에 없다.

### 실측 결과

**(a) SDK 내부 재시도** — 계측 실측 2026-08-16: SDK 기본 재시도 2회가 타임아웃 계약을

폴백 계단 소유이고 SDK가 몰래 하면 계단이 무의미해진다. 전 조립 지점(`main.py` 2곳,
`scripts/smoke_llm.py`)이 `max_retries=0`이며 `tests/test_llm_client_retries.py`가 단언한다.

**(b) 기본 마감 2.5 → 10.0 s** — 2.5는 BR-U4-04·NFR-1.2가 "요청 예산 5초의 절반"으로
정당화한 값인데, 그 5초는 generate day1 예산이고 **정작 이 기본값을 쓰는 feature는 그
예산과 무관**하다. 상위 티어가 붙으면서(`gpt-5.6-sol` 실측 **5.1 s**) 2.5는 "폴백을 강제하는
값"이 됐고 **PlanB가 컨테이너에서 100% 타임아웃**했다. 현재 이 기본값이 실제로 쓰이는
프로덕션 경로는 `REFLECTION_NUDGE`와 deadline을 안 실은 `ALTERNATIVE_SELECTION` 둘뿐이며,
둘 다 사용자 대기 화면이 아니다.

**(d) 재시도 모델 후보 비교** — 2026-09-08, **실 PlanB 프롬프트 5회**

| 모델 | 중앙값 | 편차 / 꼬리 |
|---|---:|---|
| `gpt-5.6-sol` (1차) | 5.0 s | 최대 7.8 s · 관측 꼬리 최대 **21 s** |
| `gpt-5.6-terra` | 5.2 s | — |
| `opus` | 7.6 s | 편차 1.2 s |

**더 빠른 모델은 없었다.** 그래서 재시도 모델은 속도가 아니라 **벤더 독립**으로 골랐다 —
sol의 꼬리는 벤더 쪽 사건이라 같은 벤더의 terra로 가면 같은 꼬리를 밟기 쉽다.

**(c) 몫이 0.5 → 0.7 → 0.5로 돌아온 경위** — 0.7로 올린 근거는 그때의 `gpt-5.6-sol` 실측
**중앙값 6.8초**였다(0.5면 20초 예산에서도 10초라 중앙값 근처에서 오락가락한다). 그 뒤
백엔드 슬롯 후보 예산이 15 → 25초로 오르면서 0.5의 절대값이 10.5 → **12.5초로 늘어**
비율을 되돌릴 수 있었고, 줄어든 비율 몫을 `llm_retry_share`가 가져갔다. 같은 날 다시 잰
sol 중앙값은 5.0초다 — **두 수치는 다른 측정이므로 나란히 비교하면 안 된다.**

**예산 배분 현행값**

| 값 | 현행 | 25 s 예산에서의 절대값 |
|---|---:|---:|
| `llm_budget_share` (1차 LLM) | 0.5 | 12.5 s (sol 중앙값 5.0·최대 7.8s 대비 여유) |
| `llm_retry_share` (재시도) | 0.35 | 8.75 s (opus 최대 7.8s 대비 **1 s 여유 — 얇다**) |
| 합계 상한 | ≤ 0.85 | 나머지 15%는 검색·풀 조립·게이트·직렬화 몫 |
| 백스톱 마진 | 5,000 ms | `deadline_ms + margin`에서 504 |

거부한다(`temperature is deprecated for this model`; `haiku-4-5`는 받는다). 게이트웨이
기본이 0.0이라 **sonnet-5·opus-5로 가는 feature 전부**(EXPLANATION · REFLECTION_TEMPLATE ·
PHOTO_HIGHLIGHT · _VISION)가 매번 400 → 규칙 폴백이었고, **응답은 200이라 안 보였다.**

### 왜 이 값으로 정했나

- **몫의 합 ≤ 0.85**: 검색이 임베딩을 **직렬 3회** 부르고(워밍 후 각 수백 ms, 콜드 스타트
  최대 5초) 그 뒤 풀 조립·게이트·직렬화가 온다. 15%를 남겨야 정상 경로에서 백스톱에
  안 걸린다. 콜드 스타트와 2회 타임아웃이 겹치면 넘는데, 그건 백스톱이 받고 백엔드가
  로컬 풀로 강등한다(구조로 인정한 케이스).
- **0.7 → 0.5로 되돌린 것이 축소가 아닌 이유**: 백엔드 예산이 15 → 25초로 오르면서
  절대값은 10.5 → **12.5초로 늘었다**. 줄어든 비율 몫은 `llm_retry_share`가 가져갔다.
- **타임아웃에만 벤더를 바꾼다**: `unsupported`는 재시도해도 같고(TRIP-595), 벤더 오류는
  사유가 갈려서 재시도로 덮으면 원인이 안 보인다. 그래서 `_invoke`가 실패 사유를
  `timeout:` / `unsupported:` / `llm_error:` 셋으로 가르고, 2단 폴백은 `timeout`만 탄다.
- **백스톱은 정상 폴백 뒤에 선다**: 정상적인 deadline 소진은 오류가 아니라 C2 체인 최후
  보루(`required_ms=0`)가 **200 + MINIMAL + is_fallback=true**로 수렴시킨다(TRIP-291).
  백스톱은 그 보장마저 못 나간 비정상(프로세스 행)에서만 발동해야 하므로 발동 시점을
  항상 `deadline + margin`에 둔다. 마진 0은 `__post_init__`이 거부한다.
- **재시도 기록은 지어내지 않는다**: 1차 실패는 `LlmCallRecord(success=False)`로, 모델
  전환은 `FallbackEvent(from_mode="llm:<1차>", to_mode="llm:<재시도>")`로 **실제 모델명을
  실어** 남긴다.

### 남은 한계

- **재시도 여유 1초는 얇다.** opus 최대 7.8s 대비 8.75s. 재시도까지 실패하면 규칙 랭킹이
  받으므로 손해는 대기 시간뿐이지만, 여유가 이 정도면 벤더 지연이 조금만 나빠져도 무용해진다.
- 백스톱은 **sync 라우트 스레드를 죽이지 못한다**(cancel은 best-effort). 504는 즉시 나가고
  유기 태스크의 늦은 발신은 폐기된다. 이미 응답이 시작된 뒤 발동하면 504를 덧보낼 수 없어
  연결 절단으로 끝난다(로그는 남는다).
- rate-limit·백스톱·비용 누계 전부 **단일 프로세스 in-memory** 전제다.
- `timeout_sec` 10.0은 "안전망"이라 실제 최적값 탐색을 한 적이 없다 — **미측정**.
- 타임아웃으로 끝난 호출은 응답이 없어 토큰이 0으로 기록된다. 벤더가 그 호출을 과금할
  수 있으나 **AI 쪽에서는 알 방법이 없다**(§7의 비용 하한 문제).

| **비율 0.85 (최고점 대비)** | **0.944** | **1건** | **채택** |
| 절대 0.50 | 1.000 | 0건 | 미채택 — 모델 종속 |

### 왜 이 값으로 정했나

- **top_k = 4**: reason 버킷이 비대칭이라(weather 10건 ↔ delay·none 2건) 한 값이 모두를
  만족시킬 수 없다. 4는 **가장 큰 "전건이 필요한" 버킷(fatigue 4건)을 정확히 덮으면서**
  컨텍스트를 프롬프트 골격의 46%로 유지한다. 6이면 컨텍스트의 절반이 무관 문서다.
  정밀도만 보면 2가 1.000으로 최고지만, 그건 필요한 문서를 못 넣는 값이다 — 그래서
  재현율이 아니라 **버킷 크기**를 기준으로 골랐다.
- **비율 컷을 기본으로 쓰는 이유**: 절대값은 **임베딩 모델에 종속**이다(코사인 분포가
  모델마다 다르다). 팀은 provider 전환을 전제하고 있어(2026-08-22 결정 "provider를
  바꾸면 전량 재적재") 절대 컷은 모델을 바꾸는 순간 조용히 잘못 자른다. 비율은 그
  전환에도 유효하다. **절대 0.50이 수치상 더 좋았지만(1.000 / 무관 0건) 그래서 안 썼다.**
- **절대 바닥(현재 0.0)은 비율의 구멍을 막는다**: 최고점 자체가 낮은(= 아무것도 안 닮은)
  질의에서 비율만 쓰면 잡음을 그대로 통과시킨다. 0.0은 "음수 코사인 컷"을 뜻한다.
  구현 주의 — `ratio = 0`을 "컷 없음"으로 쓰려면 `top × 0 = 0`을 그대로 하한으로 쓰면
  안 된다(음수 코사인이 잘린다). 코드는 그 경우 `-inf`를 쓴다.
- **collection 이름에 모델명을 넣은 이유**(`collection_for(kb, model_id)`): 벡터 공간은
  모델마다 다르므로 다른 모델로 색인한 벡터를 섞어 검색하면 **순위가 조용히 무의미해진다.**
  차원이 같으면(우리는 전부 1024) DDL(`vector(1024)`)도 어댑터의 BR-AF-09 검증도 이걸
  못 잡는다. 어댑터의 런타임 대조(`HttpEmbeddingAdapter`가 서비스 응답의 `model` 확인)는
  **질의 쪽만** 보므로, 적재를 B로 질의를 A로 했는데 양쪽이 각자 정합이면 통과한다.
  collection을 갈라 두면 그 경우 옛 collection 질의가 **0건**으로 떨어져 시끄럽게 드러나고,
  모델 교체 시 **재적재가 구조로 강제**된다. 이름은 해시로 줄이지 않는다 — DB를 열었을 때
  어느 모델로 색인했는지 사람이 읽을 수 있어야 한다(`nlpai-lab/KURE-v1` → `nlpai_lab_kure_v1`).

### 남은 한계

- **측정 범위는 KB-3(SITUATION)뿐이다.** `_safe_retrieve`가 세 KB에 같은 `top_k`를 넘기지만
  KB-1·KB-2는 적재 0건이라 측정 대상이 없었다. 데이터가 붙으면 KB별 분리를 판단한다
  (지금 나누면 근거 없는 상수가 둘 더 생긴다).
- top_k 표(KB 24건)와 한국어 치환 측정(KB 49건)은 **다른 스냅샷**이다 — 두 표의 수치를
  가로로 비교하면 안 된다.
- `min_score_ratio` 0.85 자체의 **스윕은 없다**(3점 비교뿐). 모델 고정이 확정되면 절대 컷
  재검토 여지는 남아 있다.
- `max_alternatives = 3`은 설계 §9 미결 #5의 **잠정값**(UX 확정 대기).
- 검색 컷·top_k 변경이 **최종 대안 품질에 미친 영향은 미측정** — 측정된 것은 검색 정밀도까지다.

## 6. 선호 점수 캐시 (TRIP-477, #301)

### 문제

2단계 생성(1차 day1 → 2차 잔여, TRIP-267·293)이 **같은 후보 풀을 두 번 점수 매긴다.**
2026-08-21 실측: 1차 21.5 s + 2차 22.1 s (합 43.6 s) vs 단일 생성 30.9 s.

### 무엇을 바꿨나

`CachingScoringWorker` — `PreferenceScoringWorker`와 **같은 `score()` 시그니처**를 갖는
데코레이터(오케스트레이터 무변경 주입).

| 설계 항목 | 값 | 이유 |
|---|---|---|
| 캐시 키 | `((taste_tags, companion, budget), poi_id)` | 점수는 (POI, 페르소나)의 함수 — 같은 취향이면 **여행·호출 경계와 무관하게** 같은 점수 |
| TTL | 900 s | 생성 세션(1차→2차 사이 수 초~수 분)만 감당하면 된다 |
| 최대 엔트리 | 4,096 | POI 단위 — 풀 상한(수십) × 동시 세션(수십) |
| 축출 | `OrderedDict` LRU (히트 시 뒤로) | 표준 라이브러리로 충분 |
| 저장 대상 | `ScoredPoi(poi_id, score)`만, `is_llm_score=True`인 것만 | |

### 실측 결과

| 항목 | 값 |
|---|---|
| 도입 동기가 된 중복 (2026-08-21 실측) | 1차 21.5 s + 2차 22.1 s vs 단일 30.9 s |
| 정상 경로의 2차 점수 LLM 호출 | **0회** — 2차 풀은 1차 풀에서 배치분을 뺀 부분집합이라 전건 히트 |
| 도입 후 지연 절감 | **미측정** |
| 히트율 | **미계측** — 캐시 전용 관측 이벤트가 없다 |

### 왜 이렇게 정했나

- **폴백·규칙 점수는 캐시하지 않는다.** 캐시가 강등을 고착화하면 다음 호출의 실 LLM
  재시도 기회가 사라진다 — INV-4의 반대 방향 오염이다. 그래서 `is_llm_score`인 점수만
  적재한다.
- **부분 미스는 미스만 부분 풀로** 내부 워커에 넘기고 병합한다(TRIP-378 청크 패턴과 동형).
  미스 호출이 폴백이면 **히트만 부분 성공으로 내보내고**(`error="cache_partial_fallback: …"`),
  나머지는 오케스트레이터의 기존 missing 규칙 채움이 맡는다. 히트도 없고 호출도 폴백이면
  그 폴백을 그대로 돌려준다.
- 폴백 이벤트를 여기서 다시 내지 않는다 — 게이트웨이가 이미 발행했다(이중 계수 방지).
- 가격 캐싱 금지(business-rules §6)와는 무관하다 — `ScoredPoi`(poi_id·score)만 저장한다.

### 남은 한계

- **프로세스 로컬 dict**다(`# ponytail:` 주석으로 표시된 의도적 단순화). AI 다중 인스턴스가
  생기면 백엔드 라우팅 고정(sticky)이나 외부 캐시로 올려야 한다.
- **절감 실측이 없다.** 위 21.5/22.1/30.9는 *도입 동기*(중복이 존재한다는 사실)이지
  도입 후 측정이 아니다. 캐시가 실제로 몇 %의 호출을 없앴는지는 계측 이벤트가 없어
  로그로도 못 뽑는다 — §7의 `llm_cost` 줄이 붙으면 요청당 호출 수·비용으로 간접 확인은 가능하다.

## 7. 요청당 비용 집계 (본 작업)

### 문제

`domain/observability.LlmCallRecord`에는 `input_tokens` · `output_tokens` · `latency_ms`가
이미 있지만 **비용이 없다.** docstring이 그 이유를 적어 뒀다 —
`LLM 비용 = Σ(tokens × 단가) ← 단가는 소비 측, 도메인엔 안 둠`.
단가는 벤더·계약·시점의 함수라 도메인 불변식이 아니고, 코드에 박으면 가격이 바뀔 때마다
배포가 필요하다. 그래서 **"요청당 비용"을 낼 통로 자체가 지금까지 없었다** — 본 문서의
표들에 그 열이 없는 이유도 이것이다(추정치로 채우지 않았다).

### 무엇을 바꿨나

**도메인은 건드리지 않았다.** 소비 측(`api/`)에만 붙였다.

| 파일 | 역할 |
|---|---|
| `src/trippilot/api/cost.py` (신규) | 단가표 로드(`load_prices`) · 호출당 비용(`ModelPrices.cost`) · trace_id별 누계(`CostLedger`) |
| `src/trippilot/api/wiring.py` `LoggingTrace` | `LlmCallRecord`를 받으면 `llm_cost` 구조화 로그 한 줄을 덧붙인다 |
| `tests/test_llm_cost.py` (신규) | 19건 — 설정 출처·계산·누계·설정 오류·emit 무예외 |

**단가 출처 (코드에 하드코딩 없음)**

```
TRIPPILOT_LLM_PRICE_FILE=/etc/trippilot/llm-prices.json   (우선)
TRIPPILOT_LLM_PRICES='{"currency":"USD","models":{...}}'   (인라인 JSON)
```

```json
{
  "currency": "USD",
  "models": {
    "claude-haiku-4-5": {"input": 1.0,  "output": 5.0},
    "gpt-5.6-sol":      {"input": 1.25, "output": 10.0}
  }
}
```

단가는 **100만 토큰당**이고, 키는 `LlmCallRecord.model_id`와 정확히 같은 문자열이다
(그 값은 `C1Config`의 `model_ids`·`feature_models`·`retry_models`가 준 이름이다).

**로그 한 줄 (`llm_cost`)**

| 필드 | 뜻 |
|---|---|
| `trace_id` · `feature` · `model_id` · `success` | 어떤 호출인지 |
| `input_tokens` · `output_tokens` · `latency_ms` | 도메인 레코드 값 그대로 |
| `call_cost` | 이 호출의 비용. **`null` = 단가표에 없는 모델**(0이 아니다) |
| `request_cost` | 같은 `trace_id`의 누계 — 한 요청의 마지막 줄이 그 요청의 총액 |
| `unpriced_calls` | 단가 미상 호출 수. **0보다 크면 `request_cost`는 하한이다** |
| `currency` | 단가표가 선언한 통화(계산에 안 쓰이고 그대로 실린다) |

### 왜 이렇게 정했나

- **지어내지 않는다.** 단가 미설정이면 집계 자체가 꺼진다(`CostLedger.from_env()` → `None`) —
  "비용 0"이 아니라 "모름"이다. 단가표에 없는 모델도 0으로 세지 않는다: 0은 "공짜로 돌았다"는
  거짓이고 그 거짓이 합계에 그대로 섞인다(INV-4 취지).
- **설정이 깨졌으면 기동 실패.** 파싱 불가·음수 단가·`bool` 단가(오타로 `true`가 1로 읽히는 것)를
  전부 `PriceConfigError`로 드러낸다 — `MiddlewareSettings.from_env`와 같은 판단이다.
- **접두어 매칭을 하지 않는다.** 날짜 접미가 붙은 모델을 뭉뚱그리면 어느 단가로 셌는지
  사후에 알 수 없다. 정확 일치만 하고, 나머지는 `unpriced_calls`로 드러낸다.
- **요청 경계 대신 누적값을 매 줄에 싣는다.** 이 계층은 요청 종료를 모른다(트레이스 싱크는
  ASGI 미들웨어와 별개다). 종료 이벤트를 새로 만드는 대신 호출마다 누계를 함께 싣는 쪽이
  더 작고, 로그 수집에서 `trace_id`로 뽑으면 그대로 요청당 비용이 된다.
- **2단 폴백도 자연히 합산된다** — 게이트웨이가 1차 실패를 그 모델명으로, 재시도를 재시도
  모델명으로 각각 `LlmCallRecord`로 남기므로 두 줄이 같은 `trace_id`에 누적된다.

### 열을 채우는 법

1. 단가표를 설정한다 (`TRIPPILOT_LLM_PRICE_FILE` 또는 `TRIPPILOT_LLM_PRICES`).
2. 재려는 경로를 실 LLM으로 돌린다 (`scripts/smoke_itinerary.py`·`smoke_planb.py`, 또는 실 요청).
3. 로그에서 `trace_id`별 마지막 `llm_cost` 줄의 `request_cost`를 뽑는다:

```bash
grep '^.*llm_cost ' app.log | sed 's/.*llm_cost //' \
  | jq -s 'group_by(.trace_id)[] | {trace: .[0].trace_id,
           cost: (max_by(.request_cost).request_cost),
           calls: length, unpriced: (max_by(.unpriced_calls).unpriced_calls)}'
```

`unpriced > 0`이면 그 요청의 `cost`는 **하한**이다 — 단가표에 모델을 추가하고 다시 잰다.

### 남은 한계

- **비용 실측치가 없다.** 단가표는 운영자가 넣는 값이고, 저장소에는 실측 비용 데이터가
  없다. 참고 추정치는 `aidlc-docs/inception/design-artifacts/ai-cost-estimation.md` §3에
  있으나 **2026-07-12 기준 추정이지 실측이 아니다** — 그 값으로 이 열을 채우면 안 된다.
- **프롬프트 캐시가 반영되지 않는다.** 어댑터가 `usage.cache_read_input_tokens`를 읽지
  않아(`LlmResponse`에 필드 자체가 없다) 캐시 히트분도 정가 입력 토큰으로 계산된다 —
  캐시를 켜면 `request_cost`는 **상한**이 된다. Batch API 할인(50%)도 마찬가지로 미반영.
- **타임아웃 호출은 토큰 0으로 기록된다**(응답이 없으므로). 벤더가 과금할 수 있으나
  AI 쪽에서 알 방법이 없다 — `request_cost`가 하한이 되는 두 번째 경로다.
- 누계는 **프로세스 로컬**(LRU 1,024 trace). 다중 인스턴스에서는 로그 수집 쪽에서
  `trace_id`로 합치는 것이 맞다.
