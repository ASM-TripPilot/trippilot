# 우리가 쓰는 모델 2종 — 클라이언트 관점 설명

**FE 요청으로 작성(2026-09-24).** "임베딩이랑 로컬 모델이 뭐냐"에 답하는 문서다.

## 먼저 결론: FE 가 직접 부를 일은 없다

둘 다 **AI 서비스 내부 부품**이다. FE 는 백엔드 공개 REST 만 쓰고(`frontend/README.md`),
백엔드가 AI 서비스를 부르고, AI 서비스가 이 둘을 쓴다.

```
FE ──REST──> 백엔드 ──HTTP──> AI 서비스 ──┬──> 임베딩 모델 (검색용)
                                          └──> 로컬 LLM   (알림 문구용)
```

그래서 FE 코드에 이 둘의 주소·키·모델명이 들어갈 일이 없다. **FE 가 알아야 할 것은
"이것들이 느려지거나 죽으면 화면이 어떻게 되는가" 하나다** — 아래 §3.

---

## 1. 임베딩 모델 — "비슷한 문서 찾기"

| | |
|---|---|
| 무엇 | `nlpai-lab/KURE-v1` (한국어 임베딩) |
| 하는 일 | 문장을 숫자 벡터로 바꿔서 **의미가 비슷한 것끼리 가깝게** 만든다 |
| 어디 쓰나 | Plan-B 지식베이스 검색 (비 오면 뭘 하지? 같은 상황에서 관련 문서 찾기) |
| 어디 도나 | AWS EKS 의 **CPU** 파드 (`deploy/eks/chart/templates/embedding.yaml`) |

"강남 맛집"과 "서울 남부 음식점"은 글자가 하나도 안 겹치지만 의미가 가깝다. 키워드
검색으로는 못 찾는 이런 걸 찾으려고 쓴다.

**주의**: 임베딩 모델을 바꾸면 벡터 공간이 달라져서 **기존에 저장한 벡터를 전부 다시
만들어야 한다.** 그래서 "느리니까 다른 걸로 갈아끼우자"가 간단한 작업이 아니다.

## 2. 로컬 LLM — "알림 문구 쓰기"

| | |
|---|---|
| 무엇 | `Qwen3-4B-Instruct` 를 우리 데이터로 파인튜닝한 모델 |
| 하는 일 | 그날 일정을 보고 푸시 알림 **한 문장**을 쓴다 |
| 어디 쓰나 | 리마인드 알림 (`POST /ai/v1/notification/copies`) |
| 어디 도나 | AWS Bedrock (서버리스, 무요청 시 과금 0) |

실제 출력은 이렇다:

```
원통사에서 시작해 도봉산양고기와 원당샘공원을 둘러보세요.
연화사와 연기향교를 둘러보고 세종호수공원에서 자연을 만끽해 보세요 🌿
```

**왜 큰 모델(GPT·Claude)을 안 쓰나**: 이 과제는 좁다 — "장소 이름 몇 개로 한 문장".
좁은 과제에선 작은 모델을 그 과제로만 학습시키는 게 더 낫다. 실측으로 우리 4B 가
교사 역할을 한 235B 모델을 블라인드 비교에서 **12:8 로 이겼다**. 비용은 비교가 안 되게 싸다.

**왜 "로컬"이라 부르나**: 외부 API(OpenAI·Anthropic)가 아니라 **우리가 가중치를 가지고
우리가 띄우는** 모델이라는 뜻이다. 사용자 기기에서 돈다는 뜻이 아니다.

---

## 3. FE 가 실제로 알아야 할 것 — 죽으면 어떻게 되나

둘 다 **죽어도 화면은 안 깨진다.** AI 실패는 전부 결정론적 폴백으로 내려간다(INV-4).

| 무엇이 죽나 | 사용자가 보는 것 |
|---|---|
| 임베딩 | Plan-B 추천이 덜 똑똑해진다. 화면 구조는 그대로 |
| 로컬 LLM | 알림 문구가 **기존 고정 문구**로 나간다 (`오늘 어디를 가는지 확인해 보세요.`) |

즉 **FE 에서 이 둘을 위한 로딩 상태나 에러 화면을 따로 만들 필요가 없다.** 값은 항상
오고, 다만 덜 좋을 뿐이다.

한 가지만 알아 두면 된다 — **알림 문구는 발송 몇 시간~며칠 전에 미리 채워진다.**
푸시가 울리는 순간에 만드는 게 아니라서, 일정을 바꾼 직후에는 옛 문구가 남아 있을 수
있다(재적재로 닫는 창이 있다).
