# 임베딩 모델 정밀도 — 컨테이너 이미지에 어떤 형태로 올릴 것인가 (TRIP-518)

> 측정일 2026-09-01 · 대상 `nlpai-lab/KURE-v1` (bge-m3 계열, 568M 파라미터, 1024차원)
> 조건: macOS arm64 · **전 변형 CPU 4스레드 고정** · KB-3 24건 × 질의 6종
> 재현: `scripts/measure_embedding_precision.py`

## 결론

**fp16 으로 저장하고 fp32 로 로드한다.** 이미지 절반, 속도 그대로, 검색 결과 완전 동일.

| 변형 | 이미지 크기 | 크기비 | 인코딩 지연 | 지연비 | 코사인 최소/평균 | top4 순위 유지 |
|---|---:|---:|---:|---:|---:|---|
| fp32 (현행) | 2,271 MB | 1.00× | 576 ms | 1.00× | — | 기준 |
| **fp16 저장 → fp32 로드** | **1,136 MB** | **0.50×** | **595 ms** | **1.05×** | **1.00000 / 1.00000** | **6/6 질의 · 24/24 위치** |
| int8 동적 양자화 | 1,362 MB | 0.60× | 1,764 ms | 3.06× | 0.97651 / 0.98103 | **1/6 질의 · 19/24 위치** |
| fp16 저장 → fp16 연산 | 1,136 MB | 0.50× | 37,741 ms | 19.13× | 0.99998 / 1.00000 | 5/6 질의 |

**int8 은 세 축 전부에서 fp16 저장에 진다** — 더 크고(1,362 vs 1,136 MB), 3배 느리고,
품질 손실이 실제 순위를 바꾼다(6개 질의 중 5개에서 top4 가 달라졌다). 검토 종료.

## 왜 fp16 저장 → fp32 로드인가

컨테이너 이미지에서 무거운 건 **가중치 파일**이지 런타임 dtype 이 아니다. fp16 으로
저장하면 파일이 정확히 절반이 되고, 로드할 때 fp32 로 올리면 연산은 지금과 같은 경로를
탄다. 남는 손실은 `fp32 → fp16 → fp32` 반올림 **한 번**뿐이다.

그 손실이 실제로 얼마인지 확인했다 — 왕복이 진짜 일어났는지부터 검증했다:

```
검사 텐서: embeddings.word_embeddings.weight (250002, 1024)
  변경된 원소: 110,256,473 / 256,002,048 (43.1%)
  최대 절대오차: 2.441e-04
```

**가중치의 43% 가 바뀌었는데도** 문서 임베딩 코사인은 소수점 5자리까지 1.00000 이고,
6개 질의 top4 순위가 **24/24 위치 전부 동일**했다. 정규화된 1024차원 임베딩에서
개별 가중치의 2e-4 오차가 상쇄된 결과다.

반대로 **fp16 을 연산까지 끌고 가면 19배 느려진다.** CPU 에 fp16 고속 경로가 없어
매 연산이 에뮬레이션을 탄다. 배포 대상이 CPU 컨테이너인 한 이 조합은 못 쓴다
(GPU 인스턴스로 가면 다시 볼 값이다).

## 측정에 걸린 함정 셋 — 전부 "조용히 틀린 답"을 준다

이 셋 때문에 **틀린 결론을 두 번 냈다가 되돌렸다.** 다음 사람은 여기서 시간을 아끼길.

### 1. `st[0].auto_model = 변환결과` 가 예외 없이 무시된다

`sentence_transformers` 6.x 의 `Transformer.auto_model` 은 **setter 없는 property**
(`self.model` 별칭)다. 대입하면 `nn.Module.__setattr__` 이 `_modules` 에 넣지만 조회는
클래스 property 가 가로채 **원본을 돌려준다.** `_modules["auto_model"] = ...` 직접 대입도
같은 이유로 안 먹는다.

```python
conv = torch.ao.quantization.quantize_dynamic(m[0].auto_model, {nn.Linear}, torch.qint8)
m[0].auto_model = conv          # ❌ 조용히 무시
m[0].model = conv               # ✅ 올바른 경로
```

이걸 모르고 재면 **원본 fp32 가 그대로 돌면서 크기·지연·코사인이 전부 fp32 와 같게**
나온다. 그게 "손실 없는 양자화"로 읽힌다. 실제로 이 측정의 1차 결론이
*"int8 은 이 스택에서 no-op 이다"* 였는데, `nn.Linear` 개수를 세어 보고서야
(145 → 0, 양자화 모듈 290) **변환은 정상이고 대입이 문제**임이 드러났다.

→ 그래서 스크립트가 교체 후 모듈 수를 세어 `assert` 한다. **성능 개선이 공짜로 보이면
개선이 아니라 적용이 안 된 것을 먼저 의심한다.**

우리 코드는 `auto_model` 에 대입하는 곳이 없다(`ai/` 전수 확인) — 측정 스크립트 한정 문제다.

### 2. 크기를 `parameters()` 합으로 재면 안 된다

양자화 모듈의 packed params 는 `nn.Parameter` 가 아니라 `parameters()` 에 안 잡힌다.
그렇게 재면 int8 모델이 fp32 보다 **커 보인다**(실측 2,271 → 3,329 MB). 이미지에 실리는
건 직렬화된 파일이므로 `state_dict` 를 `torch.save` 한 바이트로 잰다.

### 3. 변형끼리 device 가 다르면 지연 비교가 통째로 무효다

`SentenceTransformer(...)` 는 device 를 자동 선택한다(이 머신에서는 MPS). 기준만
자동으로 두고 비교군만 `device="cpu"` 로 고정하면 지연비가 의미를 잃는다 — 1차 측정이
정확히 그랬다. 배포 대상(CPU)으로 **전부** 고정한다.

## 남은 것

- **품질(코사인·순위)은 하드웨어 무관이지만 지연은 아니다.** 배포 대상 리눅스 컨테이너에서
  다시 재야 한다 — 특히 x86_64 는 양자화 백엔드가 fbgemm 이라 int8 지연이 다를 수 있다
  (품질 손실은 그대로라 결론은 안 바뀔 것으로 본다).
- 이미지가 절반이 된 뒤의 실제 이미지 크기·콜드스타트는 **TRIP-517(컨테이너 분리)** 에서 측정한다.
- 더 공격적인 압축이 필요해지면 `torchao` 나 ONNX Runtime 이 다음 후보다. 다만 **fp16 이
  새 의존성 0으로 절반을 주므로**, 지금 그 비용을 치를 이유는 없다.
