# 임베딩·벡터 DB 사이징 근거

> 배포 구성의 정본은 `deploy/eks/`(백엔드 소유, TRIP-885)다. 이 문서는 그 값들이
> **왜 그 값인지** 중 AI 쪽에서만 알 수 있는 것을 남긴다. 기준 `4cd43f74`.

## 1. 런타임 임베딩은 자유 텍스트 요청에서만 일어난다

`embedding.replicas: 1`(dev·prd 공통)의 근거다. 질의 생성 지점을 전부 추적한 결과:

| 경로 | 질의 | 런타임 임베딩 |
|---|---|---|
| 상황 KB (KB-3, 24건) | `_situation_query` = `{kind} {reason} 상황` | **0회** |
| 페르소나 KB (KB-2, 0건) | `_persona_query` = `{reason} {kind} 대안 선호` | **0회** |
| 지시 사전 칩 (KB-4, 97건) | `directives.resolve_chips` | **0회** |
| 지시 사전 자유입력 | `directives.match_free_text(text)` | **1회 / 요청** |
| 일정 KB (KB-1, 0건) | `_schedule_query` — `schedule_id`·날짜 포함, 열림 | 1회 / 요청 |

앞의 셋이 0인 이유가 다르다:

- 상황·페르소나 질의는 **`TriggerKind` 4종 × `_REASON_KO` 7종 = 28가지로 완전히 닫혀 있다.**
  적재 시점에 전부 계산해 둘 수 있는 유한집합이다(지금은 안 한다 — 필요해지면 그때).
- 칩 경로는 `resolve_chips` 독스트링 그대로 **"벡터를 안 탄다"** — 닫힌 키 테이블 조회다.

→ **동시성 요구는 "자유 텍스트를 실제로 친 요청의 비율"에 묶인다.** 그 값이 실측되기 전에는
replica 를 늘릴 근거가 없다. 늘릴 때도 **워커가 아니라 replica** 다 — `--workers 1` 이고
모델이 프로세스당 4.2 GiB 라 같은 파드에서 워커를 늘리면 OOM 이다.

관련: KB-4 가 자유 입력을 닫힌 키로 옮기는 방향이라 이 비율은 시간이 갈수록 줄어든다.

## 2. 메모리 실측치

| 항목 | 값 | 출처 |
|---|---:|---|
| 워밍 직후 | 4.29 GiB | compose 주석 실측 2026-09-02 |
| 256건 배치 인코딩 정점 | 4.37 GiB | 〃 |
| 재확인 | 4.21 GiB | `docker stats` 2026-09-12 |
| 이미지 가중치 (fp16 저장) | 1,136 MB | TRIP-518 |
| 런타임 상주 (fp32 로드) | 2,271 MB + torch 런타임 | 〃 |

**정점이 상주와 거의 같다** — 배치를 상한(256)까지 밀어도 80 MiB 만 더 쓴다. 즉 여유는
동시성이 아니라 런타임 오버헤드를 위한 것이고, EKS 의 requests 5Gi / limits 6Gi 는
이 실측 위에서 정해졌다.

`kb_vectors` 는 121행 / 904 kB(directive 97 · situation 24)로 **KB 전체가 1 MB 미만**이다.
로컬 compose 의 `ai-vectordb` 에 `mem_limit: 1g` 을 둔 근거는 그 파일 주석에 있다.
벡터 인덱스는 이 규모에서 정확검색이 더 정확하고 빨라 **만들지 않는다**.

## 3. 임베딩 공급자를 바꾸는 일의 성질

`TRIPPILOT_EMBEDDING_PROVIDER` 는 `openai|titan|local|http` 4종이고, EKS 는 `http`
(별도 KURE 컨테이너)로 배선돼 있다. Bedrock Titan(`titan`)은 **코드에 이미 있다** —
`amazon.titan-embed-text-v2:0`, `dim=1024`, `normalize=True`.

바꾸면 상주 4.2 GiB 가 통째로 사라지지만, 알아야 할 것이 둘이다.

- **전환은 쿼리 단위가 아니라 적재 단위다.** 모델이 다르면 벡터 공간이 비호환이라
  쿼리만 갈아타면 검색이 오염된다(팀 결정 2026-08-22).
- **다만 파괴적이지 않다.** `model_id` 가 collection 이름에 들어가므로(TRIP-519)
  `planb_situation__amazon_titan_embed_text_v2_0` 이 새로 생기고 기존
  `__nlpai_lab_kure_v1` 과 **공존한다.** 되돌리기는 env 한 줄이고, 121건이라 적재도 짧다.

**막는 것은 한국어 검색 품질이다.** KURE-v1 은 한국어 특화 bge-m3 파인튜닝이고 KB 문서·질의가
전부 한국어다. 현재 측정치(top_k 정밀도 0.708 → 비율 컷 0.944)는 **KURE 기준이라 그대로
가져올 수 없다.** 전환을 검토한다면 순서가 정해져 있다:

```
Titan 으로 적재 → scripts/measure_kb_topk.py 재측정 → KURE 수치와 비교 → 결정
```

재보지 않고 갈아타면 **검색 품질이 조용히 떨어진다** — `rag.py` 의 `_safe_retrieve` 가
스토어·게이트웨이 실패를 결정론 폴백으로 흡수하므로(INV-4) 예외도 로그도 나지 않는다.

## 4. 운영 함정 — `/health` 는 모델 로드를 기다리지 않는다

`ai/embedding/app.py` 의 `/health` 는 `{"loaded": ...}` 를 **싣기만 하고 200 을 돌려준다.**
프로세스 생존만 보는 것이 의도된 설계다 — AI 서비스는 임베딩 없이도 떠야 하고
(UnwiredEmbedding 계약), 여기에 결합을 걸면 임베딩 재시작 루프가 일정 생성·회고까지
기동 실패로 끌고 간다.

대신 기동 시 **백그라운드 스레드가 모델을 워밍**한다(`_warm`). 워밍 없이 띄우면 첫 요청이
콜드스타트 3.5초를 물어 임베딩 상한 3초를 넘기고 KB 검색 하나가 강등된다(2026-09-02 실측).

→ 남는 것은 **파드가 Ready 인데 아직 `loaded:false` 인 수 초의 창**이다. 적재·실측처럼
결과를 신뢰해야 하는 작업은 그 앞에서 한 번 확인한다:

```bash
kubectl -n trippilot exec deploy/ai -- \
  curl -s http://embedding:8100/health   # {"loaded":true} 를 보고 진행
```
