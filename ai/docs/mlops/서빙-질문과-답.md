PR [#657](https://github.com/ASM-TripPilot/trippilot/pull/657) 을 보고 나온 질문들과 그
답을 그대로 남긴다. 설계 근거는 `ai/docs/superpowers/specs/2026-09-21-k8s-serving-autoscaling-cache-design.md`
이고, 이 문서는 **"왜 이렇게 돼 있나"에 대한 답변 기록**이다.

## Q1. 오토스케일링을 왜 기본값으로 꺼 두나? 켜는 게 낫지 않나?

> **2026-10-04 해소 — dev 는 켰다.** 아래가 설명하는 "선행 조건 부재"를 없앴다:
> `infra/terraform/stack/eks.tf` 의 `aws_eks_addon.metrics_server`(EKS 커뮤니티 애드온).
> 지금 상태는 **차트 기본값 꺼짐 · dev ai 켜짐(min 1·max 3) · prd 고정 2** 다. 차트
> 기본값을 꺼짐으로 남긴 이유는 아래 ①~③ 그대로다 — metrics-server 없는 클러스터에
> 올려도 안전해야 한다. prd 는 사람이 켠다(근거는 아래 §권고, 절차는
> `서빙-의사결정-기록.md` §11). 이 절의 나머지는 **그 조건이 왜 필요했나**로 읽는다.

**조건이 없으면 켜도 동작하지 않는다.** HPA 는 파드의 CPU 사용률을 metrics API 로 읽어서
판단하는데, 그 값을 공급하는 `metrics-server` 를 **EKS Auto Mode 가 주지 않는다**(AWS 의
Auto Mode 시작 안내도 HPA 절에서 따로 배포하라고 적는다).

    $ grep -ril "metrics-server" deploy infra
    (2026-09-26 당시 0건 — 지금은 infra/terraform/stack/eks.tf 가 걸린다)

metrics-server 없이 HPA 를 켜면 이렇게 된다.

1. HPA 오브젝트는 생성된다. 에러도 안 난다.
2. `kubectl get hpa` 의 TARGETS 가 `<unknown>/70%` 로 뜬다.
3. **그 상태에서 HPA 가 replica 소유권을 가져간다.** Deployment 는 `replicas` 를 렌더하지
   않으므로(그래야 `helm upgrade` 가 HPA 가 정한 수를 되돌리지 않는다), 아무도 수를 정하지
   않는 상태가 된다.

즉 "켜 두면 필요할 때 늘어난다"가 아니라 **"켜 두면 늘지도 줄지도 않으면서 수동 조절만
막는다"** 가 된다. 그래서 기본값이 꺼짐이고, 이건 보수적으로 잡은 것이 아니라 선행 조건이
안 갖춰졌기 때문이다.

### 켜려면 필요한 것

| 필요한 것 | 현재 |
|---|---|
| `metrics-server` 설치 | **있다**(2026-10-04, EKS 커뮤니티 애드온) |
| 부하 실측(어느 지표로 늘릴지) | 여전히 없다 — dev 에 트래픽이 없다. 지금은 CPU 70% |
| `deploy/eks` 소유자(백엔드) 동의 | dev 는 켬. **prd 는 아직** |

### 권고

종전 권고는 "metrics-server 가 들어가면 **prd 부터** 켠다"였다. prd 는 이미
ai·backend·gateway 가 replicas 2 로 고정돼 있어서 고정 2 를 "최소 2, 최대 4"로 바꾸는 것이
순이득이기 때문이고, **그 근거는 지금도 유효하다.**

**다만 순서를 뒤집어 dev 를 먼저 켰다(2026-10-04).** 두 가지 때문이다.

- prd 배포는 리뷰어 승인을 거치므로, 값만 미리 머지하면 **다음 prd 배포가 조용히 동작을
  바꾼다.** 켜는 사건과 머지하는 사건이 분리돼야 한다.
- dev 를 켜는 비용이 0 이다 — 트래픽이 없어 HPA 는 minReplicas 에 머문다. 그런데 **얻는
  것은 "목표치를 읽는가"에 대한 답**이고, 그게 prd 에서 확인하면 안 되는 바로 그 질문이다.

"dev 는 부하가 없어 켤 이유가 없다"고 적었던 것을 이렇게 정정한다 — 부하를 받으려고 켜는
것이 아니라 **배선을 보려고** 켠다. 증거는 배포 스모크가 남긴다(`report_autoscalers`).

**임베딩에는 어느 쪽이든 붙이지 않는다.** 파드가 5Gi 를 요청하고 모델 로드가 수십 초라
(startupProbe 최대 15분) 부하를 보고 늘리면 이미 늦고, 프로세스당 4.2 GiB 라 워커를 늘리는
길도 막혀 있다. 근거는 [[임베딩-사이징-근거]].

## Q2. GPU 매니페스트는 뭐 하는 건가?

> **2026-10-01 철회 — 이 매니페스트는 이제 리포에 없다.** 아래 설명은 "무엇이었나"로 읽는다.
> 지운 근거는 `서빙-의사결정-기록.md` §10(감사 결함 4건 + 운영 경로 이중화). 운영 경로는
> **Bedrock Custom Model Import 하나**다.

리마인드 문구를 쓰는 **우리가 직접 파인튜닝한 모델**(Qwen3-4B)을 쿠버네티스 안에서 돌리기
위한 배포 설정이었다. 파일은 `deploy/eks/chart/templates/reminder-llm.yaml` 이었다.

핵심은 **안 쓸 때 0으로 내려가는 것**이다.

```
요청 없음 → KEDA 가 replica 를 0 으로 → 파드가 사라짐 → Karpenter 가 GPU 노드를 반납
요청 도착 → replica 1 → 노드가 새로 뜸(수 분) → Triton 기동 → 응답
```

리마인드 문구 채움은 발송 **몇 시간~며칠 전에** 도는 배치라 사용자가 기다리는 경로가 아니다.
그래서 수 분짜리 콜드스타트를 감당할 수 있고, 그게 0으로 내릴 수 있는 이유다.

## Q3. 표의 나머지 둘은 뭔가?

### Triton 임베딩 경로

KB 검색에 쓰는 임베딩 모델(KURE-v1)을 지금과 **다른 엔진으로 돌려 보는 경로**다. 계약은
그대로이고(`POST /embed` 가 벡터·모델명·차원을 돌려준다) 내부 구현만 env 하나로 갈린다.
기본값은 현행이라 켜지 않으면 아무 변화가 없다.

### amd64 벤치 워크플로

위 두 엔진을 **배포 대상과 같은 CPU 아키텍처(amd64)에서** 비교하는 수동 실행 워크플로다.
개발 맥은 arm64 인데, 실측에서 **아키텍처에 따라 우열이 뒤집혔다** — 맥 네이티브에서는
ONNX 가 1.29배 빨랐고 맥 컨테이너에서는 1.60배 느렸다. 그 숫자로는 결정할 수 없어서
GitHub 러너(amd64)를 쓰는 길을 냈다. PR 에 `bench-embedding` 라벨을 붙이면 돈다.

## Q4. Triton 과 ONNX 가 뭐고, 둘이 어떻게 다른가?

**층이 다르다. 경쟁 관계가 아니다.**

| | ONNX / ONNX Runtime | Triton Inference Server |
|---|---|---|
| 무엇인가 | 모델 **파일 형식**(ONNX) + 그걸 실행하는 **엔진**(ONNX Runtime) | 모델을 얹어 두고 HTTP·gRPC 로 **요청을 받는 서버** |
| 어디서 도나 | 우리 프로세스 **안** | **별도 컨테이너** |
| 무엇을 대신하나 | PyTorch — 즉 계산하는 주체 | uvicorn 같은 서빙 껍데기 |
| 비유 | 엔진 | 엔진을 담는 차체 |

Triton 은 내부적으로 ONNX Runtime 을 쓸 수도, PyTorch 를 쓸 수도, LLM 이면 vLLM 을 쓸 수도
있다. 즉 **Triton 을 쓴다고 빨라지는 게 아니라, 그 안의 엔진이 빠르면 빨라진다.**

### 우리 측정이 실제로 말한 것

amd64 에서 두 번 쟀고 방향이 같았다.

| 측정 | 현행(PyTorch 계열) | ONNX Runtime | 비 |
|---|---:|---:|---:|
| 1차 | 8,652 ms | 7,538 ms | 0.87× |
| 2차 | 9,636 ms | 8,226 ms | 0.85× |

벡터는 두 번 다 완전히 같았다(코사인 1.00000 · top-4 24/24 위치 동일) — 재적재 없이 바꿀
수 있다는 뜻이다.

그리고 **이 13~15% 는 엔진이 준 것이지 서버가 준 것이 아니다.** Triton 서버 자체의 몫은
측정에서 queue 1.8ms 수준으로 소수점이었다. 그래서 결론이 이렇게 갈린다.

| 안 | 속도 | 대가 |
|---|---|---|
| 현행 유지 | 기준 | 없음 |
| **ONNX 를 우리 프로세스 안에서** | 13~15% 이득 | 모델 변환 단계 하나 |
| Triton 별도 컨테이너 | 13~15% − 네트워크 왕복 | 컨테이너 1개 + 모델 2.1GB 상주(현 임베딩 파드 6Gi 와 **별도**) |

**단일 모델이면 Triton 은 수지가 안 맞는다.** Triton 이 값을 하는 조건은 여러 모델을 한
제어면에 모아 버전·배치·지표를 한 곳에서 다룰 때다.

## 결정 기록 — Modal 대신 AWS (2026-09-26, 사용자 결정)

리마인드 모델 서빙을 **Modal 서버리스가 아니라 AWS 로 간다.**

> ### ⚠️ 정정 (2026-09-26, 같은 날) — AWS 경로가 **이미 둘이었다**
>
> 이 절을 처음 쓸 때 "AWS = EKS GPU" 로 적었는데 **틀렸다.** 확인해 보니 다른 트랙이
> 이미 **AWS Bedrock Custom Model Import** 로 실배포를 끝내 놓았다(PR #696, 09-23 머지).
> 아래 EKS GPU 계획은 그 사실을 모르고 세운 것이다.
>
> | | Bedrock CMI (**배포됨·실측 있음**) | EKS GPU (이 PR 의 매니페스트) |
> |---|---|---|
> | 상태 | develop 에 머지 · 실 호출 확인 | 매니페스트만 · 기본 꺼짐 |
> | 실측 | 문구 1건 **1,375ms**(in 602 / out 72 토큰) · CMU 1 · **5분 창 과금 · 무요청 0원** | 없음 |
> | GPU 쿼터 | **불필요** | 신청 수일 |
> | 선행 작업 | 없음 | NodePool · device plugin · KEDA · PVC |
> | 콜드스타트 | 첫 호출 `ModelNotReady` → 어댑터가 폴백 계단으로 넘김 | 노드 기동 수 분 |
>
> **우선순위 규칙이 이미 코드에 있다**: `main.py::_local_route` 는 `TRIPPILOT_BEDROCK_MODEL_ARN`
> 과 `TRIPPILOT_LOCAL_LLM_BASE_URL` 이 **둘 다 있으면 Bedrock 이 이긴다.** 즉 이 PR 의
> `reminder-llm` 을 켜도 Bedrock env 가 살아 있으면 트래픽은 Bedrock 으로 간다 — 켜 놓고
> "왜 안 쓰이지"를 뒤지게 되는 형태다.
>
> **결정(2026-10-01, 사용자가 판단을 위임 — "너의 추천대로 결정할게")**: **(a)** 다.
> Bedrock Custom Model Import 가 실서비스 경로이고, EKS GPU 는 전환 판정기가 비용 우위를
> 수치로 낼 때 다시 연다. 근거 세 가지 — ① Bedrock 경로는 이미 머지·실호출 확인됨이고
> 선행 작업이 0인데 EKS 경로는 NodePool·device plugin·KEDA·PVC 가 전부 남아 있다,
> ② 같은 일을 하는 운영 경로가 둘이면 "지금 어느 쪽이 트래픽을 받나"가 상시 운영 질문으로
> 남는다(바로 위 우선순위 함정이 그 질문의 첫 사례다), ③ 감사에서 매니페스트 결함 4건이
> 나와 지금 상태로는 켜도 동작하지 않는다. 아래 EKS 계획은 **참고 기록**으로 남긴다.
>
> 옮길 근거의 기준선은 이것이다 — **서버리스 4B 파인튜닝 1건 = 1.4초 · CMU 1 · 5분 창
> 과금.** 이 경계는 비동기 배치라 지연은 더 느려도 되지만, **비용이 이보다 싸야** 옮기는
> 이유가 선다.

이전 결정(2026-09-12, `ai/scripts/finetune_reminder/modal_app.py`)의 기각 근거는 둘이었다.
① EC2 GPU 는 끄는 걸 잊으면 예산이 계속 나간다(서울 리전 24/7 월 40~50만 원대)
② 신규 계정 GPU 쿼터가 0 이라 증설 신청에 수일이 걸린다.

이번 결정으로 ①은 **설계로 막는다** — KEDA 가 replica 를 0 까지 내리고 Karpenter 가 노드를
반납하므로, 무요청 구간에 GPU 요금이 붙지 않는다. 다만 이건 **매니페스트가 그렇게 돼 있다**
는 뜻이지 아직 실물로 확인한 것이 아니다. 첫 배포 후 **무요청 24시간 구간의 청구액이 0인지**
반드시 확인한다. 이 확인 전까지는 ①이 해소됐다고 보지 않는다.

②는 남아 있고, 리드타임이 가장 길다. 그래서 순서가 정해진다.

1. GPU 서비스 쿼터 신청 — 지금 바로 (수일)
2. GPU NodePool + NVIDIA device plugin + KEDA 설치 — 백엔드 (TRIP-961)
3. 모델 가중치를 클러스터에서 읽을 자리 마련(PVC) + 첫 배포
4. 무요청 청구액 0 확인 → 그때 ①이 닫힌다

### 이 결정이 바꾸는 것

- ~~**TRIP-961 의 성격이 바뀐다.** "조건 기록"으로 냈는데 이제 **착수 요청**이다.~~
  → 2026-10-01 결정 (a) 로 **조건 기록으로 되돌린다.** GPU 쿼터는 지금 신청하지 않는다.
- `modal_app.py` 와 런북 §4 는 **지우지 않는다.** 쿼터가 며칠 걸리고 그 사이 평가·시연이
  필요하면 Modal 이 유일한 길이다. 대신 머리말에 "운영 목표는 EKS"라고 적는다.
- 서빙 트랙 소유자(스케줄·로컬LLM 세션)에게 알린다 — 그쪽이 Modal 앱을 만들었다.
- 모델 이름 계약은 그대로다. `local-reminder-qwen3-4b-v1` 이 Triton 모델 디렉토리 ·
  요청의 `model=` · `TRIPPILOT_LLM_FEATURE_MODELS` 배정에서 **전부 같아야** 하고, `local`
  로 시작하지 않으면 앱이 로컬 라우트를 안 만들고 **예외 없이 외부 벤더로 나간다.**
