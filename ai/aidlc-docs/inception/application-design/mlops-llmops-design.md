# MLOps · LLMOps 설계 — 운영 체계 + ML 패턴 유형화

> 두 축을 구분해 설계한다:
> - **LLMOps** — LLM 호출(프롬프트·평가·비용·가드레일)의 운영 체계. **MVP부터 필수** (LLM이 핵심 경로에 이미 있음). 벤더는 Anthropic API 직접 (AI-D06 — 2026-08-25 "Bedrock" 표기 제거)
> - **MLOps** — 자체 학습 모델(선호 점수·체류시간 등)의 운영 체계. **지금은 "로깅 먼저", 모델은 DAU 1천 이후** (AI-D05 과설계 금지 유지)
>   - **정정 (2026-09-26, TRIP-967)**: 이 줄이 전제한 "모델"은 **행동 로그로 학습하는 랭킹·회귀**다. 그 축은 지금도 Phase L 그대로다. 다만 **다른 축이 이미 갔다** — 리마인드 문구용 Qwen3-4B 파인튜닝 모델이 2026-09 에 서빙까지 갔고(§3 유형 E 신설), 이쪽은 DAU 와 무관하다. 학습 라벨이 사용자 행동이 아니라 **교사 모델 출력**이라 데이터 축적을 기다릴 이유가 없었기 때문이다. 즉 단계를 어긴 것이 아니라 이 문서가 한 축만 보고 있었다.
>
> 공통 대전제 (AI-D05): ML/LLM은 **soft 신호에만**. 하드 제약은 어셈블리 결정론 유지. closed-set 게이트(INV-1)와 규칙 폴백(INV-4)은 어떤 모델로 바꿔도 그대로 적용.

## 1. LLMOps — MVP부터 가동하는 것

### 1.1 전체 구성

```
[개발 루프]                          [운영 루프]
프롬프트 레지스트리                    전량 트레이싱 (trace_id)
   | 버전 커밋                           | 구조화 로그
   v                                    v
오프라인 평가셋 실행 (CI, LLM fake)     지표 집계 (비용·지연·폴백율·F1/F2)
   | 게이트 통과                         | 대시보드 + 알람
   v                                    v
카나리/섀도 배포                       피드백 마이닝 (질문뱅크·평가셋 보강)
   |                                    |
   +------------- 개선 백로그 <----------+
```

### 1.2 프롬프트 관리 (Prompt Registry)

| 항목 | 정책 |
|---|---|
| 저장 | 프롬프트는 코드가 아니라 **버전 있는 리소스** — `ai/prompts/{feature}.yaml` **평면 배치**, 버전은 파일 안 `version:`(semver) 필드 (git 관리, ai-prompt-design.md의 template_id·version 체계 계승). 레이아웃·목록 정본은 `ai/prompts/` 와 로더 `ai/src/trippilot/llm_gateway/prompts.py` |
| 식별 | C1 호출 계약에 이미 있는 `prompt{version, template_id}` 필드를 전 호출에 강제 — 로그에서 어떤 버전이 어떤 결과를 냈는지 조인 가능 |
| 변경 절차 | 프롬프트 수정 = PR → 오프라인 평가셋 자동 실행 → 회귀 없으면 머지 → 카나리 |
| 롤백 | version 필드만 되돌리면 즉시 롤백 (배포 없이 설정 전환 가능하게) |
| 대상 | feature별 전부: score_preferences, explain_slot, select_alternatives, generate_reflection, parse_intent, paraphrase_query(신규), extract_places, Bedrock 어셈블리 프롬프트 |

### 1.3 평가 체계 (Evaluation)

| 층 | 내용 | 실행 시점 |
|---|---|---|
| **L1 스키마·불변식** | OutputSchema 파싱 성공률, closed-set 위반 0 (INV-1), duration 필드 부재 (INV-3) — 기존 PBT 19속성 + 신규 5속성(FRESH/CUR/SPEED) | CI 매 커밋 (LLM fake, D37) |
| **L2 기능 평가셋** | feature별 golden set — 입력/기대 출력(또는 채점 기준) 페어. 예: parse_intent 정확도, select_alternatives의 합리성 | CI (기록 재생) + 프롬프트 변경 시 실모델 배치 실행 |
| **L3 LLM-as-judge** | 회고 품질·설명 자연스러움 등 정답 없는 출력 — 채점 프롬프트로 자동 평가 (채점 프롬프트도 레지스트리 관리) | 야간 배치 (실모델, 비용 통제) |
| **L4 온라인 지표** | 최신성·신속도(evaluation-metrics-design.md), 폴백율, 사용자 행동(대안 수락률, 슬롯 교체율, 회고 편집율) | 상시 |

**CI 게이트 (D37 유지)**: CI에서 실 API 호출 0. L2까지가 머지 차단 게이트, L3·L4는 추세 감시.

### 1.4 트레이싱·로깅

| 항목 | 정책 |
|---|---|
| 상관관계 | `trace_id` 전 구간 전파 (orchestrator-delegation-design.md §7) — 사용자 요청 1건 = LLM 호출·어셈블리 실행·에이전트 위임 전체 트리 복원 가능 |
| LLM 호출 로그 | {trace_id, feature, prompt_version, model_id, tokens_in/out, latency, is_fallback, 파싱 성공 여부} — **전량** |
| 본문 로깅 | 프롬프트·응답 본문은 개인정보 마스킹 후 **샘플링 저장** (디버깅·평가셋 채굴용). 위치·이름은 백엔드 개인정보 정책(append-only 로그 체계)과 정렬 — 보존 기간 별도 합의 필요 |
| 어셈블리 로그 | {trace_id, solve_mode, or_tools_status, HC 위반·수리 내역, elapsed} — 하이브리드 체인의 어느 층에서 해결됐는지 추적. **정정 (2026-08-25)**: `is_bedrock` 필드는 코드에 없고 필요도 없다 — `SolveMode`(`OR_TOOLS`·`LLM`·`RULE_FALLBACK`·`MINIMAL`, `domain/itinerary.py`)가 층을 이미 식별한다 |
| 도구 스택 | 1차: 구조화 로그 + PostgreSQL/대시보드 자작 최소셋. 성장 시: Langfuse(LangChain 연동 자연스러움) 또는 CloudWatch + Bedrock 호출 로깅. **선정은 미확정 — 인터페이스(로그 스키마)만 고정하고 백엔드는 교체 가능하게** |

### 1.5 비용·쿼터 관리

| 항목 | 정책 |
|---|---|
| 예산 계측 | feature별·티어별 토큰/비용 일 단위 집계 (ai-cost-estimation.md의 추정치를 실측으로 대체하는 구조) |
| 상한 | 사용자당 일 호출 상한 + feature별 서킷 (예: 웹소싱 extract_places 폭주 방지) |
| 티어 라우팅 감시 | 경량/상위 모델 분기 비율 — 상위 모델 비중 급증 시 알람 |
| 절감 루프 | 질문뱅크 CONFIDENT 비중↑ → parse_intent 호출↓ / 에이전트별 tool 제한 → 토큰↓ (기존 설계의 효과를 지표로 검증) |

### 1.6 가드레일·배포

| 항목 | 정책 |
|---|---|
| 출구 게이트 | C1 closed-set 게이트(INV-1)·OutputSchema 파싱은 **코드 레벨 가드레일** — 모델·프롬프트와 독립적으로 항상 켜져 있음 |
| 카나리 | 프롬프트·모델 변경은 트래픽 5~10%부터. 지표(폴백율·파싱 실패율·대안 수락률) 이상 시 자동 롤백 |
| 섀도 실행 | 모델 교체(예: Claude 버전 업) 시 신모델을 섀도로 병행 호출 → 오프라인 비교 후 전환 |
| 모델 추상화 | **`LlmPort` 뒤 격리** — model_id는 항상 설정값(BR-U4-08, 하드코딩 금지). **정정 (2026-08-25)**: "Bedrock Port"·"벤더 미확정"은 스테일 — 벤더는 **AI-D06으로 확정**(Anthropic API 직접, 2026-07-21)이고 포트는 벤더 중립이다. 로그에 model_id를 항상 기록하는 규칙은 그대로 (티어·기능별 오버라이드가 있어 실제 모델이 갈린다) |

## 2. MLOps — "로깅 먼저, 모델은 나중"

### 2.1 단계 전략 (AI-D05 계승)

| 단계 | 시점 | 내용 |
|---|---|---|
| **Phase L (지금, MVP)** | 코드 착수부터 | **학습 데이터가 될 로그를 스키마 갖춰 쌓기** — 모델 없이. 이것을 안 하면 DAU 1천이 되어도 학습 불가 |
| **Phase M1** | DAU 1천 / 데이터 축적 후 | 첫 모델 1~2개 (선호 점수 LTR, 체류시간 회귀) 오프라인 학습 → 섀도 평가 |
| **Phase M2** | M1 검증 후 | ~~SageMaker 엔드포인트 서빙~~ → **AWS Bedrock Custom Model Import** (정정 2026-09-26) → C1/어셈블리 어댑터 뒤 스왑 → 정기 재학습 파이프라인 |

> **정정 (2026-09-26, TRIP-967) — SageMaker 는 쓰이지 않는다.** 실제로 간 경로는
> **MLX 로 개인 Mac(48GB)에서 LoRA 학습 → 병합 → Bedrock Custom Model Import 서빙**이다
> (PR #696, 09-23 머지 · 실측 문구 1건 1,375ms · CMU 1 · 5분 창 과금 · 무요청 0원).
> 서빙 전환·오토스케일링·캐시의 운영 규칙은 별도 유닛 FD 로 옮겼다 —
> `construction/mlops-serving/functional-design/`.
>
> 학습이 클라우드가 아니라 로컬 Mac 인 것도 이 표에 없던 축이다. 데이터가 자산이고
> 실행은 소모품이라는 판단(런북 §6 ⑤: "막히면 같은 JSONL 로 Colab T4 재학습")이라
> 학습 인프라를 고정 비용으로 두지 않았다.

### 2.2 Phase L — 지금 설계에 넣는 학습 로그 스키마

| 로그 | 스키마(핵심 필드) | 장차 학습시킬 것 |
|---|---|---|
| `preference_feedback` | {user, poi_id, context(시간대·동행·날씨), 노출→행동(선택/교체/거절/방문완료)} | 선호 점수 LTR |
| `dwell_actual` | {poi_id, category, user, 시간대, planned_dwell, actual_dwell(visit_record 유래)} | 체류시간 회귀 |
| `travel_actual` | {origin, dest, mode, 시간대, estimated(내부), actual(GPS 유래, L3 옵트인)} | 이동시간 보정 |
| `alternative_choice` | {trigger, 제시 대안 A/B/C 피처, 선택/거절/무시} | Plan-B 수락 예측 |
| `trigger_response` | {trigger type·value, 사용자 반응(대안 봄/dismiss)} | 트리거 오탐 필터 |
| `intent_resolution` | {utterance(마스킹), 매칭 경로, 확정 intent, 후속 성공 여부} | 의도 분류기 (질문뱅크→경량 모델) |

원칙: **라벨이 자동으로 생기는 구조** — 사용자의 자연스러운 행동(선택·교체·완료)이 라벨이 되도록 로그를 설계한다. 별도 라벨링 작업 최소화.

### 2.3 Phase M2 — 파이프라인 구성 (개요)

```
학습 로그 (PostgreSQL/S3)
   → 피처 추출 배치 (재현 가능: 코드+데이터 버전 고정)
   → 학습 (미정 — 아래 註. 리마인드 트랙은 로컬 Mac MLX 였다)
   → 오프라인 평가 (홀드아웃 + 기존 규칙 대비 개선폭)
   → 모델 레지스트리 (버전·계보·평가 결과)
   → 섀도 배포 (규칙 점수와 병행 산출, 로그만)
   → 카나리 → 전환 (어댑터 뒤 스왑)
   → 모니터링 (예측-실측 괴리 = 드리프트) → 재학습 트리거
```

- **폴백 불변**: ML 실패·드리프트 → 규칙 버전으로 즉시 복귀 (INV-4). 규칙 점수 코드는 ML 도입 후에도 삭제 금지
- **closed-set 불변**: ML 선호점수도 M7 화이트리스트 내 랭킹만 (INV-1)
- **학습 실행 환경은 미정이다 (정정 2026-09-26)** — 이 블록은 SageMaker Training 을 적었지만
  실제로 돈 유일한 학습(리마인드 유형 E)은 로컬 Mac MLX 였다. A-1·B-1 이 실제로 착수될 때
  다시 정한다. **서빙 쪽은 정해졌다** — Bedrock Custom Model Import(위 표).

## 3. ML 패턴 유형화 — "패턴화 가능한 것" 카탈로그

**ML 전환 가능성 판정 기준 3개** (모두 충족해야 후보):

1. **반복 구조** — 같은 형태의 입력→출력이 대량 반복되는가
2. **자동 라벨** — 정답이 사용자 행동·실측에서 공짜로 생기는가
3. **soft 신호** — 틀려도 품질 저하일 뿐, 제약 위반이 아닌가 (hard는 어셈블리 영역 — ML 금지)

### 유형 A. 점수·랭킹 (Learning-to-Rank / 분류)

| # | 후보 | 입력 → 출력 | 라벨 원천 | 현재 구현 | 우선순위 |
|---|---|---|---|---|---|
| A-1 | **선호 점수** (AI-D05 기존) | user+POI+컨텍스트 → 선호도 | preference_feedback | LLM/규칙 부트스트랩 | ★★★ M1 |
| A-2 | **Plan-B 대안 정렬** (신규) | 트리거+대안 피처 → 수락 확률 | alternative_choice | LLM select_alternatives | ★★ M2 |
| A-3 | **웹소싱 후보 품질 필터** (신규) | 소싱 POI 피처 → 게이트 통과 가치 | 수집 게이트 판정 이력 | 규칙 5단 게이트 | ★ 후순위 (게이트 보조만 — 게이트 자체는 규칙 유지) |

### 유형 B. 수치 예측 (회귀)

| # | 후보 | 입력 → 출력 | 라벨 원천 | 현재 구현 | 우선순위 |
|---|---|---|---|---|---|
| B-1 | **체류시간 예측** (AI-D05 기존) | POI+user+시간대 → 체류 분 | dwell_actual | 정적 테이블(G51) | ★★★ M1 |
| B-2 | **이동시간 보정** (AI-D05 기존) | 구간+시간대 → 보정 계수 | travel_actual | 고정 안전계수(G106) | ★★ 후순위 |

### 유형 C. 분류 (LLM 호출의 경량 모델 대체)

| # | 후보 | 입력 → 출력 | 라벨 원천 | 현재 구현 | 우선순위 |
|---|---|---|---|---|---|
| C-1 | **의도 분류** (신규) | 발화 임베딩 → intent | intent_resolution + 질문뱅크 | 하이브리드 매칭(intent-matching-design.md) | ★★ M2 — 뱅크가 곧 학습셋. 임베딩+경량 분류기(kNN/로지스틱)로 2·3차 LLM 호출 대체 → 비용·지연↓ |
| C-2 | **트리거 오탐 필터** (신규) | 트리거 피처+user → dismiss 확률 | trigger_response | 임계값 규칙(80%/30분) | ★★ M2 — 임계는 유지하되 "이 사용자에겐 알리지 말지"만 학습 (알림 피로 감소) |
| C-3 | **스타일 7축 분류** (기존 추후 항목) | 방문 이력 → 7축 비율 | 방문 통계(약라벨) | llm.analyze_style (예정) | ★ 후순위 — LLM으로 시작, 호출량 늘면 분류기 전환 |

### 유형 D. 표현 학습 (임베딩 기반)

| # | 후보 | 입력 → 출력 | 라벨 원천 | 현재 구현 | 우선순위 |
|---|---|---|---|---|---|
| D-1 | **콜드스타트 페르소나** (신규) | 온보딩 7축 → 유사 사용자 군집의 선호 프로파일 | 기존 사용자 행동 | COLD_START 폴백(일반 인기) | ★ M2 이후 — 군집 통계만으로 시작 가능 (모델 없이도 개선) |

### 유형 E. 생성 모델 자체 서빙 (신설 2026-09-26, TRIP-967)

**판정 기준 3개가 안 맞는 유형이다.** 라벨이 사용자 행동에서 공짜로 생기지 않고(기준 2),
대신 **교사 모델이 데이터를 만든다.** 그래서 DAU 와 무관하게 지금 할 수 있었고, 실제로
했다. 위 A~D 를 쓰던 틀로는 이 칸이 안 보였다.

| # | 후보 | 입력 → 출력 | 라벨 원천 | 현재 구현 | 상태 |
|---|---|---|---|---|---|
| E-1 | **리마인드 문구** | 그날 일정(장소·카테고리·날짜) → 제목·본문 1문장 | 교사 Qwen3-235B 생성분을 **서빙과 같은 게이트로** 필터 | 파인튜닝 Qwen3-4B, Bedrock CMI 서빙 | **가동** |

- **약관이 조합을 정한다**: 교사는 오픈 웨이트만(Qwen3-235B, Apache-2.0), 심판은 평가
  전용(Claude Sonnet). Anthropic·OpenAI 출력물로 어떤 모델이든 학습하는 것은 사전 승인 없이
  금지라, 심판 출력이 학습 루프에 흘러들면 학생 모델 전체가 약관 위반 산출물이 된다.
- **학습 데이터 필터 = 서빙 게이트 그 코드**다. 규칙을 두 벌로 구현하면 학습 분포와 서빙
  판정이 조용히 어긋난다.
- soft 신호 기준(기준 3)은 지킨다 — 문구가 틀려도 **백엔드 상수로 폴백**하고 일정 자체는
  안 건드린다. 게이트가 그날 슬롯 이름 집합으로 교차한다(INV-1 사영).
- 운영 규칙(전송로 선택·모델명 3중 계약·전환 절차)은 유닛 FD 소관 —
  `construction/mlops-serving/functional-design/`.

**다음 후보**: 없다. 유형 E 를 늘리는 기준은 "외부 API 호출을 줄이는 대가로 우리가 모델
수명주기를 떠안을 값이 있는가"이고, 지금은 리마인드 문구 하나만 그 선을 넘었다(짧은 정형
출력 · 호출량 예측 가능 · 품질 기준이 게이트로 이미 코드화됨).
