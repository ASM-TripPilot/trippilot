# 도우미 대화 — 비즈니스 로직 모델 (FD **초안**)

## 0. 설계 축 — "3단 라우터를 갈아엎지 않고 앞뒤를 붙인다"

도구 호출로 넘어가자는 논의가 있었고, 결론은 **하이브리드 유지**다. 근거는 실측이다.

| | 3단 뱅크 라우터 (현행) | 순수 도구 호출 |
|---|---|---|
| 발화 1건당 LLM | **0회가 32%** (87발화 중 28건, 뱅크 417문장) | 항상 1회 이상 |
| 지연 | CONFIDENT < 50ms | 경량 모델도 1s 대 |
| 개선 수단 | 뱅크에 문장을 넣으면 는다 — 사람이 고칠 수 있다 | 프롬프트·모델 교체뿐 |
| 인자 추출 | **못 한다** (지금 `slots={}`) | 잘한다 |
| 다중 의도 | **못 한다** (점 하나) | 잘한다 |

뱅크가 이기는 칸과 도구 호출이 이기는 칸이 정확히 갈린다 — **의도는 뱅크가, 인자와 분해는 도구 호출이** 잘한다.
그래서 도구 호출을 **3차 자리에** 넣는다. 1·2차를 건드리면 32%의 0회 경로가 사라지고 얻는 게 없다.

이 FD 는 그래서 라우터 내부를 거의 고치지 않는다. 고치는 것은 **앞**(보류 프레임 우선 채우기)과 **뒤**(프레임·실행 계획)다.

## 1. 모듈 배치

```
src/trippilot/
  domain/
    dialogue.py        IntentFrame · ArgumentKind · ArgumentSpec · ARGUMENT_TABLE
                       · ClarifyRequest · RouterOutcome · PendingFrame · DialogueContext   (신규)
    intent.py          (기존 — 무변경) Intent · ROUTING_TABLE · MatchRoute · IntentMatch · IntentDraft
    execution.py       (기존 — **드디어 소비자가 생긴다**) ExecutionPlan · ExecutionStep · AgentCall
    delegation.py      (기존 — 무변경) AgentTask · spawn · AgentResult
  ports/
    llm_port.py        ToolSpec · ToolCall + LlmRequest.tools/tool_choice + LlmResponse.tool_calls  (후미 확장)
  orchestrator/
    arguments.py       ArgumentKind 별 추출기 9종 + fill(frame, text)                       (신규)
    dialogue_router.py 한 턴의 오케스트레이션 — IntentRouter 를 감싼다                      (신규)
    intent_router.py   (기존 — `_extract_slots` 제거 외 무변경)
  llm_gateway/
    workers/intent.py  3차 워커에 도구 호출 분기 추가                                        (확장)
    gates/intent.py    (기존 — 도구 응답도 같은 게이트를 탄다)
```

`dialogue_router.py` 를 새로 두고 `intent_router.py` 를 **감싸는** 이유: 라우터는 "발화 → 의도" 한 가지만 하는 상태가
튜닝에 유리하다. 되묻기·보류·분해를 그 안에 넣으면 `scripts/trace_intents.py` 의 결정론 측정이 불가능해진다.

## 2. 한 턴의 흐름

```
입력: utterance + DialogueContext(pending, turn_index, clarify_count)
   |
   v
[A] 보류 프레임이 있나?
   ├ 있음 → [A1] 이 발화로 pending.asked_argument 를 채울 수 있나? (해당 종류 추출기 1개만 돌린다)
   │         ├ 채워짐 → 프레임 완성 → [E] 실행                      ★ LLM 0회
   │         └ 못 채움 → [A2] 이 발화가 **다른 의도로** CONFIDENT 확정되나?
   │                     ├ 예 → 보류 버림(BR-DLG-24①) → [B] 로 진행
   │                     └ 아니오 → clarify_count ≥ 1 이면 결정론 폴백(BR-DLG-23)
   │                                 아니면 같은 질문 재시도 없이 폴백 — 되묻기는 1회다
   └ 없음 → [B]
   |
   v
[B] IntentRouter 3단 (현행 그대로 — 손대지 않는다)
      1차 임베딩 → CONFIDENT | 2차 투표 → VOTED | 3차 LLM → LLM_DIRECT | 실패 → FALLBACK
      단, 3차 진입 조건에 **복합 의심**을 추가한다 (BR-DLG-12)
   |
   v
[C] 프레임 만들기
      CONFIDENT/VOTED → 프레임 1개, 인자는 **규칙 추출기만** (LLM 0회 유지)
      LLM_DIRECT      → 도구 호출 결과에서 프레임 1~2개, 인자 동봉
      FALLBACK        → OUT_OF_SCOPE 프레임 1개
   |
   v
[D] 필수 인자 점검 — missing 계산
   ├ 전부 찼다 → [E]
   ├ 비었는데 FREE_TEXT·해소 실패다 ∧ 아직 3차를 안 탔다 → 3차 승격(LLM 1회) → [D] 재점검
   └ 여전히 비었다 → ClarifyRequest 생성 → **되묻기로 응답**, 보류 프레임을 경계 밖으로 돌려준다
   |
   v
[E] 프레임 → ExecutionPlan 컴파일 → AgentTask.spawn 으로 시한 분배 → 위임
```

**[A] 가 [B] 앞에 있는 것이 ⑤의 핵심이다.** "여수" 한 마디는 뱅크 417문장 어디에도 안 맞는다 —
라우팅을 먼저 돌리면 반드시 FALLBACK 이거나, 더 나쁘게는 엉뚱한 의도에 붙는다. 채우기를 먼저 하면 그 턴은 **LLM 0회**로 끝난다.

### 2.1 왜 [A1] 에서 추출기를 하나만 돌리나

보류 프레임은 **어느 인자를 물었는지 알고 있다**(`asked_argument`). 그 종류의 추출기만 돌리면 된다.
전부 돌리면 "3박 4일"이 `DATE_RANGE` 와 `COUNT` 양쪽에 걸려 엉뚱한 칸이 채워진다.
질문이 좁혔으니 해석도 좁힌다 — 이것이 되묻기가 인자 정확도를 올리는 진짜 이유다.

## 3. ③ 인자 추출 — 무엇을 규칙으로, 무엇을 LLM 으로

결정 기준은 **경로**가 아니라 **인자 종류**다 (BR-DLG-07).

| 종류 | 1·2차에서 | 3차에서 | 그래도 비면 |
|---|---|---|---|
| `DATE` · `DATE_RANGE` · `ORDINAL` · `COUNT` · `ENUM` | 규칙 (결정론) | 도구 인자 | 되묻기 |
| `REGION` | 사전 최장일치 | 도구 인자 | 되묻기 |
| `PLACE_REF` · `SLOT_REF` | 규칙으로 부분만 | 도구 인자 + **현재 일정/후보 풀 교차 검증** | 되묻기 |
| `FREE_TEXT` | 시도하지 않는다 | 도구 인자 | **되묻지 않는다** — 선택 인자뿐이라 비워 둔다 |

`FREE_TEXT` 는 표(§2.1)에서 전부 선택 인자다. 필수로 승격하지 않는 편이 좋다 —
"왜 다시 짜드릴까요?"를 묻기 시작하면 대화가 길어지는데 그 값이 없어도 일은 된다.

### 3.1 `PLACE_REF` 교차 검증 — 베낄 것과 베끼지 말 것

`EditTranslationGate` 가 한 번 크게 틀린 자리가 여기다. 그 사고의 교훈은 anti-patterns 에 등재돼 있다:

> **고르는 행위**(새 POI)는 화이트리스트로, **가리키는 행위**(기존 슬롯)는 현재 상태로 검증한다.

인자에도 그대로 적용된다.

| 자리 | 검증 대상 | 틀리면 |
|---|---|---|
| `EDIT_SCHEDULE.replacement` · `SUGGEST_ALTERNATIVE` 결과 | **후보 풀** (고르는 행위) | INV-1 위반 — 지어낸 장소가 일정에 들어간다 |
| `EDIT_SCHEDULE.target` · `GET_DISTANCE.origin/destination` | **현재 일정** (가리키는 행위) | 후보 풀로 교차하면 **자연어로 영원히 편집 불가**해진다 — 풀은 매 요청 다시 잘리는 조각이라 원 일정 슬롯이 풀 밖인 것이 정상이다 |

그리고 검증 실패를 **예외로 던지지 않는다.** 폴백 밖에서 `raise` 하면 422 가 나가고, 백엔드는 4xx 를 최소일정 폴백 신호로 쓰므로
**편집 한 번이 일정을 통째로 갈아엎을 수 있다.** 실패는 `missing` 에 그 인자를 남기고 되묻기로 간다.

## 4. ⑤ 대화 상태를 누가 갖나 — 결정이 필요한 자리

**세 대안을 비교하고 A 를 추천한다.** 이 결정은 백엔드 합의가 필요하다(business-rules §5 미결 #1).

| | **A — 백엔드 소유 (추천)** | B — AI 서비스 소유 | C — 클라이언트 소유 |
|---|---|---|---|
| 어디에 둔다 | 백엔드 테이블 (신규) | AI 쪽 저장소 (신규 — 지금 없다) | 앱이 들고 매 턴 되보낸다 |
| AI 경계 | 무상태 유지 — `DialogueContext` 를 받고 돌려준다 | 상태 보유 → **고정 세션 필요** | 무상태 유지 |
| 수평 확장 | 영향 없음 | 컨테이너를 늘리면 턴이 갈린다 | 영향 없음 |
| 개인 발화 보존·삭제 | **이미 백엔드 책임** (동의 로그·append-only 규율이 있다) | AI 쪽에 개인정보 보관 체계를 새로 만들어야 한다 | 서버에 안 남는다 (가장 가볍다) |
| 기기 바꾸면 | 이어진다 | 이어진다 | **끊긴다** |
| 선례 | `replan_session` 테이블(재계획 초안)이 같은 모양 | 없음 | **`CONFIRM_REQUIRED` 왕복이 이미 이 방식** |
| 비용 | 테이블 1개 + 만료 배치 | 저장소 + 개인정보 체계 | 0 |

**A 를 추천하는 이유**는 확장성보다 **책임 소재**다. 제품 정본이 "대화 이력 보관 정책"을 운영 결정 미결(O3)로 걸어 뒀는데,
그 결정의 주체와 집행 지점은 이미 백엔드에 있다. AI 서비스가 발화를 들기 시작하면 **결정 전에 사실을 만들어 버린다.**

C 는 매력적이다 — 지금 `CONFIRM_REQUIRED` 가 그렇게 돌고 있고 비용이 0이다. 그런데 에픽 J 의 스토리 "5) **대화 이력**·세션"이
기기 간 연속성을 요구하면 C 로는 못 한다. **C 를 고르려면 그 스토리를 먼저 줄여야 한다** — 순서가 거꾸로다.

### 4.1 A 를 골랐을 때 백엔드가 지는 몫

- `DialogueContext` 를 저장하는 테이블 1개 (trip·user 스코프, 만료 컬럼)
- 턴 증가·만료 청소 — **AI 는 `turn_index` 를 읽기만 하고 올리지 않는다**
- 되묻기 응답을 사용자에게 보여주고 다음 발화와 함께 컨텍스트를 되싣는 것
- 보존 기간·삭제 요구 대응 (O3 결정에 따름)

AI 가 지는 몫은 하나다 — **받은 컨텍스트로 판단하고 갱신본을 돌려주는 것.** 그 외에 아무것도 기억하지 않는다.

## 5. ④ 다중 의도 — 분해와 컴파일

### 5.1 언제 분해를 시도하나

임베딩은 발화 하나를 점 하나로 만든다. "내일 날씨 어때? 비 오면 일정 좀 바꿔줘"는 두 의도 사이 어딘가에 찍히고,
**1차에서는 낮은 top1**, 2차에서는 **갈린 득표**로 나타난다. 2차는 이것을 "해소할 모호성"으로 다뤄 승자를 뽑으려 하므로
**LLM 1회를 헛쓴다** — 그래서 2차를 건너뛰고 3차로 보내는 신호가 필요하다.

제안 신호 (BR-DLG-12): **접속 표지**(`그리고`·`그다음`·`~고 나서`·`~면`)가 있고 `top1 < T_high` 이면 3차로 직행.

⚠️ **이 신호에는 실측 근거가 없다.** 평가셋 87건에 복합 발화가 **0건**이라 지금은 잴 수 없다.
착수 전에 평가셋에 복합 항목을 넣어야 한다(미결 #8). 근거 없는 임계를 코드에 박지 않는다 — 앞선 튜닝에서
"측정 없이 넣은 플래그가 엉뚱한 것을 쟀다"는 실패를 이미 한 번 했다.

### 5.2 프레임 → `ExecutionPlan` 컴파일

```
frames = [f0(GET_WEATHER), f1(REPLAN, depends_on=0)]

  → ExecutionPlan(steps=(
        ExecutionStep(agents=(AgentCall(ORCHESTRATOR_FAST, "GET_WEATHER", {...}),), timeout_sec=t0),
        ExecutionStep(agents=(AgentCall(PLANB,             "REPLAN",      {...}),), timeout_sec=t1),
    ))

frames = [f0(EDIT_SCHEDULE), f1(GENERATE_REFLECTION)]      # 독립 — 정본 예시

  → ExecutionPlan(steps=(
        ExecutionStep(agents=(AgentCall(EDIT, ...), AgentCall(REFLECT, ...)), timeout_sec=t),
    ))
```

규칙 한 줄 — **의존이 없으면 같은 step, 있으면 다음 step.** `AgentKind` 매핑은 `ROUTING_TABLE.handler` 에서 나온다
(Fast Path 5종은 전부 `ORCHESTRATOR_FAST`).

시한은 `AgentTask.spawn` 이 강제한다 — step 이 늘어도 **합이 부모 시한을 넘을 수 없고**, 잔여가 0이면 발행 자체가 불가능하다.
어셈블리 바닥 보장(`max(c2_reserved_ms, total−elapsed)`)은 **없애지 않는다**.

### 5.3 두 개를 넘기지 않는 이유

상한 2는 임의값이 아니다.

- 첫 응답 예산이 3초다(D38). 순차 step 2개면 경량 모델 2회로 이미 ~2s 다.
- 상태 변경이 둘이면 되돌리기가 사람이 이해할 수 없게 된다 — `DESTRUCTIVE_OPS` 가 확인을 강제하는 것과 같은 이유다.
- 실제로 3개 이상을 한 문장에 넣는 사용자가 있는지 **모른다.** 상한을 낮게 잡고 실사용에서 올리는 편이 낫다.

## 6. 도구 호출 — 무엇이 실제로 좋아지는지 재고 넣는다

도구 호출을 "요즘 다들 그렇게 한다"로 채택하지 않는다. 바뀌는 것과 안 바뀌는 것을 갈라 둔다.

| | 현행 (JSON 프롬프트 + `IntentGate`) | 도구 호출 |
|---|---|---|
| 라벨 closed-set | **게이트가 보증** | **게이트가 보증** (그대로 — BR-DLG-06) |
| 인자 스키마 | 없음 — 의도 무관 3칸 | **의도별 13종** ← 진짜 이득 |
| 파싱 실패 | 펜스·형식 이슈로 실제 사고 2건 | 벤더가 구조를 보장 ← 측정 대상 |
| 다중 산출 | 불가 | **도구 2회 호출** ← ④의 전제 |
| 벤더 중립 | 유지 | 어댑터마다 방언 → `LlmUnsupportedError` 로 강등 |
| 비용·지연 | 경량 1회 | 경량 1회 (동일) |

**실측할 것은 두 가지다** — 파싱 실패율과 인자 정확도. 정확도가 오를 것이라고 **가정하지 않는다.**
같은 세션에서 "Claude 는 temperature 0 에서 결정론"이라고 단정했다가 실측으로 뒤집힌 적이 있다(득표율 1.000/0.760/0.758).
최소 2회 측정 규칙이 여기도 그대로 적용된다.

도구 스키마를 `ARGUMENT_TABLE` 에서 **생성**하므로, 의도별 인자 스키마의 이득은 도구 호출을 채택하지 않아도 얻을 수 있다 —
JSON 프롬프트에 같은 스키마를 실으면 된다. **즉 ③의 핵심은 도구 호출이 아니라 표다.** 도구 호출은 그 표를 벤더에 맡기는 선택지일 뿐이다.

## 7. 착수 순서와 선행 조건

세 항목은 **의존 순서가 있다.** ③ 없이 ⑤가 불가능하고, ④는 봉투 이관을 기다린다.

| 순서 | 항목 | 선행 조건 | 막히면 |
|---|---|---|---|
| 1 | ③ `ARGUMENT_TABLE` + 규칙 추출기 | **없음** — 지금 착수 가능 | — |
| 2 | ③ 도구 호출 포트 확장 | 1 완료 (표가 있어야 스키마가 나온다) | 표만으로도 JSON 프롬프트 개선은 된다 |
