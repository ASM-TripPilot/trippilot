# U0 Foundation — NFR Design Patterns

> 입력: `../nfr-requirements/nfr-requirements.md`(35 요구) · `../functional-design/`(BR-U0-01~30). 결정 근거: `../../plans/u0-foundation-nfr-design-plan.md` Q1~Q9(2026-07-17 확정).
> 익스텐션: security-baseline **Full(blocking)** · resiliency-baseline **Full** · PBT **부분(02·03·07·08·09 blocking)**.
> 관통 원칙(사용자 캘리브레이션): **적당한 규모 + 쾌적한 UX** — 분산 인프라(Redis·읽기 복제본·메시지 브로커) U0 미도입. 도입 트리거는 실측 병목.

## 1. 복원력 패턴 (RES-01~04 · Q1)

### P-RES-1 — 재시도 경계 분리 (대화형 vs 비대화형)

**규칙**: 자동 재시도는 **비대화형 경로에만** 적용한다.

| 경로 | 패턴 | 근거 |
|---|---|---|
| 소셜 IdP 호출(로그인) · 부트스트랩 | **자동 재시도 없음** — 실패 = 즉시 사용자 가시 피드백 + 수동 재시도 경로 | 3초 타임아웃 예산(PERF-02·BR-U0-27) 내 재시도 불가 · IdP 장애 시 재시도가 부하 증폭 |
| 아웃박스 릴레이(골격) | 지수 백오프 + 지터, 최대 시도 초과 시 DLQ 상태 전이(무한 재시도 금지) | RES-02 · at-least-once |
| DB 커넥션 획득 | 커넥션 풀 내장 짧은 재시도만(획득 타임아웃 상한 = API p95 예산 이내) | PERF-01 |

**불변식**: 재시도를 도입하는 모든 지점은 **멱등**해야 한다. 아웃박스 소비는 이벤트 ID 기준 멱등(RES-02).

### P-RES-2 — IdP별 서킷 브레이커 격리

- **격리 단위 = 제공자별 인스턴스**(Google·카카오·네이버·Apple 각 1). 한 제공자 장애가 타 제공자 로그인을 막지 않는다(RES-01·벌크헤드).
- 파라미터: 호출 타임아웃 3초 · 실패율 임계 초과 시 open · half-open 탐침으로 복구 판정. 구체 수치는 운영 조정 가능하게 외부화(SEC-03 임계 외부화와 동일 규약).
- **open 상태 UX 계약**: 해당 제공자 버튼만 저하 안내 표시, 타 제공자는 정상 노출. 침묵 실패 금지(UX-01).

### P-RES-3 — 캐시 기반 제공자 의존 완화

JWKS·제공자 메타데이터를 인메모리 TTL 캐시(§3 P-PERF-1)로 보유 → **제공자 일시 장애가 기발급 세션 검증에 영향 없음**(RES-03). 캐시 만료 시 갱신 실패하면 **직전 값 유지(stale-if-error)** — 검증 자체를 중단시키지 않는다.

### P-RES-4 — fail-closed 인증, fail-open 게이트

방향이 반대인 두 결정을 명시 구분한다(혼동 방지):

| 대상 | 방향 | 근거 |
|---|---|---|
| 인증·자격 증명 검증 | **fail-closed** — 판정 불가 시 거부(401) | AVAIL-02·SEC-06 — 보안 결정 |
| 앱 버전 업데이트 게이트 | **fail-open** — 버전 확인 불가 시 게이트 미발동 | BR-U0-27 — 게이트는 UX 안내이지 보안 통제가 아님 |
| 스플래시 부트스트랩(3초 초과) | **로컬 폴백** — 마지막 로컬 세션 기준 분기, 온라인 복구 시 재검증 | BR-U0-27 — 무한 스플래시 금지 |

## 2. 확장성 패턴 (SCALE-01~03 · Q2)

### P-SCALE-1 — 무상태 수평 확장

- 앱 컨테이너 **무상태**(액세스 토큰 무상태 검증이 전제 — 서버 세션 저장 없음) → 수평 오토스케일.
- **min 2 인스턴스(다중 AZ 분산)** = 가용성 하한(AVAIL-01)이자 롤링 배포(§5)의 전제. 스케일 기준 = CPU/요청 수, 상한은 인프라 설계.
- **금지**: 인스턴스 로컬 상태에 정합성을 의존하는 설계(캐시는 §3 규약대로 불일치 허용분만).

### P-SCALE-2 — 단일 프라이머리 DB (읽기 복제본 미도입)

U0 부하(~50 RPS, SCALE-01)에서 읽기 복제본은 과설계 — **단일 프라이머리만**. 복제 지연에 따른 read-after-write 문제를 애초에 만들지 않는다(온보딩 저장 직후 재조회가 잦음 — PERF-04와 정합).
**재평가 트리거**: DB CPU 상시 60% 초과 또는 읽기 p95가 API 예산(PERF-01)을 잠식할 때.

### P-SCALE-3 — 스파이크 흡수 = 오토스케일 + 부하 차단(429)

10x 마케팅 스파이크(SCALE-02)는 ① 오토스케일 확장 ② 레이트리밋 429 저하로 흡수한다. **오류율 급증이 아니라 제어된 저하**여야 하며, 429는 `retryAfter`를 동반해 클라가 백오프 가능해야 한다(SEC-03·UX-01).

## 3. 성능 패턴 (PERF-01~04 · UX-01~05 · Q3)

### P-PERF-1 — 프로세스 로컬 TTL 캐시만 (분산 캐시 미도입)

| 대상 | TTL | 불일치 허용 근거 |
|---|---|---|
| JWKS · 제공자 메타 | 10분 | 키 롤오버는 2키 중첩(§4 P-SEC-2)이 전파 시간을 흡수 |
| 약관 현행 버전 | 5분 | 즉시성 요구 없음 — 최대 5분 지연 동의 노출 허용 |
| 금칙어 사전 | 5분 | 동일 |

**규약**: 인스턴스 간 최대 TTL만큼의 불일치를 **명시적으로 허용**한다. 정합성이 필요한 판정(토큰 회전·동의 증적)은 캐시를 경유하지 않고 DB 정본을 읽는다.

### P-PERF-2 — 응답 예산 배분 (부트스트랩)

`/bootstrap` p95 500ms(PERF-01) 예산: 캐시 히트 경로(약관 버전·앱 버전 정책) + DB 조회 1~2회(세션·온보딩 상태). **외부 IdP 호출을 부트스트랩 경로에 포함시키지 않는다**(제공자 지연이 콜드 스타트를 잠식하는 것 방지).

### P-PERF-3 — 낙관적 UI (체감 성능)

- 화면 전환은 **서버 완료를 기다리지 않는다** — 즉시 전환 + 스켈레톤(PERF-03·UX-02). 200ms 미만 응답은 로딩 표시 생략(깜빡임 방지).
- 온보딩 단계 저장 = **낙관적 진행**(다음 단계 즉시 전환, 실패 시 복귀 + 재시도 + 입력 보존 — PERF-04·UX-03).
- **경계**: 낙관적 UI는 **되돌릴 수 있는 것에만**. 인증·동의·삭제 요청은 서버 확정 후 전환(증적·보안 결정이라 낙관적 처리 금지).

### P-PERF-4 — 클라이언트 리프레시 single-flight

동시 401 다발 시 리프레시 요청을 단일 큐로 직렬화 → **자기 재사용 오탐 방지**(BR-U0-08 재사용 감지가 정상 사용자를 로그아웃시키는 것 차단). 회전 체인(INV-R1)과 클라 HTTP 계층의 계약.

## 4. 보안 패턴 (SEC-01~10 · Q4)

### P-SEC-1 — 토큰 검증 파이프라인 (fail-closed)

서명(ES256, kid 조회) → `alg` 화이트리스트(**`none`·대칭 거부 고정**) → `iss`·`aud`·`exp` → 주체 확정. 어느 단계든 판정 불가 = 401. 알고리즘은 **토큰의 헤더가 아니라 서버 정책이 결정**한다(알고리즘 혼동 공격 차단).

### P-SEC-2 — JWK 2키 중첩 롤오버 (무중단)

**상태**: 서명키(현행 1) + 검증 전용키(직전 1) = JWK 셋 최대 2.

**절차**:
1. 신규 kid를 **검증 셋에만** 추가 → 전 인스턴스 전파 대기(캐시 TTL 10분 초과분)
2. 서명키를 신규 kid로 전환
3. **액세스 토큰 TTL(1h) 경과 후** 구키 제거

**불변식**: 어느 시점에도 *유효 기간이 남은 토큰의 서명 검증키가 셋에 존재*한다 → 롤오버가 로그아웃을 유발하지 않는다. 정기 주기·트리거는 운영 정책(Infra Design)이되 **절차·불변식은 U0 고정**.

### P-SEC-3 — 2축 레이트리밋 (DB 카운터 정본)

- 축: **IP · 계정** 2축 독립 판정(한쪽만 걸려도 429). 대상 = `/auth/social/*` · `/auth/token/refresh` · 닉네임 검사.
- 정본 = PostgreSQL 카운터(Redis 미도입 — SCALE-01 규모 전제). 임계는 **재배포 없이 조정 가능하게 외부화**.
- **재평가 트리거**: 카운터 쓰기가 DB 부하 상위 요인이 되거나 인증 p95를 잠식할 때.

### P-SEC-4 — deny-by-default + CI 강제

공개 엔드포인트는 **명시적 화이트리스트만**(소셜 로그인·토큰 갱신·약관 조회·부트스트랩 비세션부·liveness). "가드 없는 공개 핸들러"를 **아키텍처 테스트로 CI 검출**(SEC-04) — 리뷰 의존이 아니라 자동 게이트(TRIP-150 자산 활용).

### P-SEC-5 — 객체 수준 인가 단일 관문

자기 리소스 접근은 **토큰 주체 accountId로만** 해석한다. 요청 본문·쿼리의 accountId를 신뢰하지 않는다(IDOR 원천 차단, SEC-05). 조회 술어에 주체 조건을 **누락할 수 없는 구조**(공용 조회 경로에 주체 바인딩 강제).

### P-SEC-6 — PII 마스킹은 프레임워크 레벨

금지 항목(전 토큰류·소셜 코드/SDK 토큰·이메일·생년월일·Authorization 헤더 — SEC-07)을 **호출부 규율이 아니라 로깅 프레임워크 컨버터**로 마스킹(TRIP-148 자산에 추가). 이유: 호출부 규율은 반드시 새며, 유출은 되돌릴 수 없다.

### P-SEC-7 — append-only 증적

동의·법정 증적은 append-only + **app DB 역할의 UPDATE/DELETE 권한 회수**(V1.7 기존재)로 강제. 파기(30일) 시에도 증적은 캐스케이드 제외(BR-U0-13·LEGAL-03). 애플리케이션 버그로도 증적을 훼손할 수 없는 **DB 권한 수준 통제**.

## 5. 배포·롤백 (RESILIENCY-04 — Q6=A · Q7=추천 · Q8=추천 확정)

### P-DEP-1 — CI/CD = GitHub Actions (기존 자산, Q6=A)

`.github/workflows/{backend,frontend,ai}-ci.yml` 실재 → **기존 파이프라인 사용**(신규 도구 도입 없음). 조직 프로세스(Jira·Slack·Git) 사용 지시와 정합. U0 산출물은 이 파이프라인과 호환되게 작성.

### P-DEP-2 — 롤링 배포 (Q8=B)

- 점진 인스턴스 교체 + **readiness 게이트**(신규 인스턴스가 준비되기 전 트래픽 미유입) + **그레이스풀 셧다운**(진행 중 요청 완료 후 종료) = AVAIL-03 무중단 내성.
- 블루/그린·카나리는 현 규모에 비용·복잡도 과다로 **미채택**(캘리브레이션). 재평가 트리거: 배포 실패의 사용자 영향이 실측으로 문제화될 때.
- **전제**: min 2 인스턴스(P-SCALE-1) — 1 인스턴스면 롤링이 성립하지 않는다.

### P-DEP-3 — 버전 핀 롤백 + 스키마 전방호환 규약 (Q7=A + DB 규약) ⚠️ 핵심

**메커니즘**: 이전 아티팩트 버전 재배포(버전 핀).

**제약**: Flyway가 **forward-only**(V1.x 정본)라 "마이그레이션 역실행"(선택지 D)은 **구조적으로 불가**. 따라서 롤백 가능성은 **스키마가 앱보다 앞서도 안전함**에 의존한다 → 규약이 곧 전제 조건이다.

**확장-후-수축(expand-and-contract) 규약** — U0부터 강제:

| 변경 | 규약 |
|---|---|
| 컬럼 추가 | **nullable 또는 기본값 필수** — 구버전 앱의 INSERT가 실패하면 안 됨 |
| 컬럼 삭제·개명 | **배포 분리 필수** — ① 신규 컬럼 추가+양쪽 쓰기 ② 앱 전환 ③ 별도 배포에서 구컬럼 제거. 한 배포에 묶지 않는다 |
| 제약 강화(NOT NULL·UNIQUE) | 데이터 보정 → 다음 배포에서 제약 추가(2단계) |
| 파괴적 변경 | 롤백 창(최소 1 배포 주기) 경과 후에만 |

**불변식**: *스키마 버전 N에서 앱 버전 N-1이 정상 동작한다.* 이걸 깨는 마이그레이션은 롤백 불가 배포이므로 명시 승인 대상.

**검증**: CI에서 **구버전 앱 ↔ 신스키마 호환 테스트**(Testcontainers — 최신 마이그레이션 적용 후 직전 앱 리비전 테스트 실행)로 규약 위반을 자동 검출.

## 6. 복원력 테스트 (RESILIENCY-14 — Q9=B 경량 제안 확정)

기존 DR/카오스 관행 없음(2026-07-12 기확정) → **CI 자동 검증 위주 + 게임데이 1회**. 상시 카오스 엔지니어링은 현 규모에 미채택.
