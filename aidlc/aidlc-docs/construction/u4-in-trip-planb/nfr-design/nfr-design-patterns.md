# U4 In-trip & Plan-B — NFR Design Patterns

> 입력: `u4-in-trip-planb/nfr-requirements/` 2종. 답변 확정 2026-08-09 — **Q1=A**(서킷 미도입) · **Q2=A′**(지오펜스 다음 **2곳**, 사용자 제안).
> U0 패턴(24종) + U1 패턴(P-*-U1) 위에 **U4 델타만** 추가. 명명 `P-{영역}-U4-#`.
> **재서술 금지**: NFR Requirements에 배치까지 적힌 것(DB 캐시·409·sweeper 재사용·이벤트 기반 평가·법정 로그 구간 단위·다운샘플링·낙관적 갱신)은 여기서 다시 쓰지 않는다.

## 1. 감지 패턴 (P-DET-U4)

### P-DET-U4-1 — 신호 수집과 판정의 분리
**클라는 신호만 모으고 임계를 모른다. 판정은 서버가 한다.**

```
클라 (신호)                       서버 C9 (판정)
 위치 · 시각 · 방문 체크 ──POST──→ 정규화 → 영향 판정 → 노이즈 폐기 → 억제 조회 → TriggerEvalResult
 앱 포그라운드 복귀                                                      │
 지오펜스 wake                     ←──── shouldReplan + scope + reason ──┘
```

- 임계값이 클라에 없으므로 **앱 배포 없이 임계를 바꿀 수 있다**(BR-U4-03).
- 억제 상태가 서버에 있으므로 **기기를 바꿔도 억제가 유지된다**.
- 클라가 자체 판단으로 배너를 띄우지 않는다 — 화면은 서버 판정의 사영일 뿐이다.

### P-DET-U4-2 — 무발화 기본값 (silence-by-default)
**판정에 필요한 근거가 없으면 발화하지 않는다.** 외부 실패·데이터 결측·정확도 미달은 전부 무발화로 수렴한다(BR-U4-05).

> **U0·U1의 "침묵 실패 금지"와 모순되지 않는다.** 두 규칙의 대상이 다르다:
> - **사용자가 요청한 동작**이 실패하면 **반드시 표면화**한다(재계획 실패 → `i22`·수동 전환).
> - **사용자가 요청하지 않은 선제 알림**은 근거가 없으면 **아예 만들지 않는다**(허위 알림 금지).
>
> 침묵의 대가는 **관측으로 갚는다** — P-OBS-U4-1.

### P-DET-U4-3 — 억제 3축을 감지 단계에서 집행
| 축 | 규칙 | 원본 |
|---|---|---|
| 중복 | 동일 `kind` × 동일 `slotKey` 1회 | BR-U4-07 |
| 총량 | 일일 상한(민감도별 `LOW=1`·`NORMAL=3`·`HIGH=6`, **근거 없는 초기값**·설정값) | NFR §5 |
| 사용자 의사 | `[끄기]` → `plan_b_suppression` 레코드 | BR-U4-15 |

세 축 모두 **`TriggerEvalResult` 산출 전에** 적용한다. 화면 단계에서 거르면 알림은 이미 나간 뒤다(INV-U4-02).

## 2. 복원력 패턴 (P-RES-U4)

### P-RES-U4-1 — 서킷 브레이커 미도입 · 타임아웃 + 실패율 지표로 시작 (Q1=A)

**드리프트 정리**: U1 `nfr-design-patterns.md` P-RES-U1-1과 `logical-components.md`는 **Resilience4j 벤더별 서킷**을 전제하지만, `backend/gradle/libs.versions.toml`에 **라이브러리가 없다**(2026-08-09 실측). U4가 벤더를 하나 더 들이는 시점에 이를 정면으로 정리한다.

| | |
|---|---|
| 결정 | **지금 도입하지 않는다.** 외부 포트마다 **짧은 타임아웃 + 재시도 없음**(P-RES-U1-2 승계) + **벤더별 실패율 지표**(OBS-U4-04)로 시작 |
| 근거 | 서킷이 막는 것은 "장애 벤더에 계속 매달려 자원 소진"인데, **재시도가 없어서** 이미 크게 완화돼 있다. 게다가 U4의 외부 실패는 전부 **무발화(P-DET-U4-2)** 또는 **수동 전환(BR-U4-43)** 으로 끝나 사용자 경로가 막히지 않는다 |
| 대가 | 벤더가 **느리게 실패**할 때(타임아웃 직전까지 매달림) 스레드가 잠깐 묶인다. 타임아웃을 짧게 두는 것이 유일한 방어다 |
| 재평가 | 벤더 실패율이 실측으로 문제가 되거나, 느린 실패로 응답 예산이 깨질 때 → Resilience4j 도입 + **U1 패턴 문서 소급** |
| 문서 조치 | U1 `nfr-design-patterns.md`·`logical-components.md`의 Resilience4j 표기에 **"미실장 · U4에서 재확인(2026-08-09)"** 주석 상신 |

### P-RES-U4-2 — 날씨의 stale-if-error **역방향 예외**
U0·U1의 `stale-if-error`(P-RES-U1-3)는 "실패 시 마지막 값을 보여준다"이다. **날씨는 반대로 간다.**

| 용도 | 만료 스냅숏 |
|---|---|
| **발화**(트리거 생성) | **금지** — 만료값으로 알림을 만들지 않는다(INV-U4-09) |
| **표시**(`i09` 감시 항목) | 허용하되 **"확인 불가"** 로 표기 |

> 이유: 표시는 사용자가 스스로 판단할 재료지만, 발화는 **앱이 대신 판단해 개입**하는 것이다. 낡은 근거로 개입하면 그게 허위 알림이다.

### P-MOBILE-U4-1 — 지오펜스 슬라이딩 창(2) + 강등 사슬 (Q2=A′)

```
등록 대상 = 다음 예정지 2곳 (슬라이딩 창)
  방문 완료 · 시각 경과 → 맨 앞 해제 → 다음 1곳 추가 → 항상 2개 유지
  하루 마지막 슬롯이면 1개, 남은 슬롯 0이면 0개
```

- **리전 상한(iOS 20 · Android 100)을 원천적으로 안 건드린다.** 창을 2로 둬도 여유가 압도적이다.
- **창 크기 2를 고른 이유**: 1이면 순서를 건너뛰어 다음 다음 장소에 먼저 도착했을 때 감지가 통째로 빠진다. 2면 그 경우가 대부분 덮이고, wake 비용 증가는 실질적으로 무시할 수준이다.
- ⚠️ **중복 진입 판정 필수**: 두 리전이 가까우면(반경 합보다 짧은 거리) 한 번 이동에 **둘 다 진입 이벤트**가 뜬다. 서버는 `(tripId, slotKey)` 기준으로 **먼저 도달한 하나만** 도착으로 확정하고 나머지는 폐기한다. 클라도 같은 wake 안에서 중복 요청을 보내지 않는다.
- **강등 사슬**: `지오펜스` → (권한 없음·등록 실패·정확도 미달) → `포그라운드 감지` → (앱 미실행) → `수동 체크인`. 어느 단계로 내려가도 **기능이 막히지 않는다**(MOBILE-U4-03).

## 3. 동시성 패턴 (P-CON-U4)

### P-CON-U4-1 — 재계획 세션 단일성
한 여행에 열린 `replan_session`은 **최대 1개**(INV-U4-06). 새 진입은 기존 열린 세션을 `CANCELED`로 닫고 시작하며, **진행 중 같은 여행의 중복 요청은 409**로 거부한다(COST-U4-01).

- 이것이 **호출 상한이자 동시성 제어**다. 별도 rate-limit 라이브러리·분산 락을 두지 않는다.
- 확정(`APPLIED`)은 **비교 화면 1곳에서만** 호출된다(구조 가드 `planbApplyStructure.test.ts`가 잠금).
- 낙관적 잠금: 확정 시 기준 `itinerary` 버전을 함께 보내 **그 사이 일정이 바뀌었으면 거부**한다(부분 반영 금지 — BR-U4-32).

## 4. 성능 패턴 (P-PERF-U4)

### P-PERF-U4-1 — 캐시 키를 발표 주기에 맞춘다
`weather_snapshot` 키 = `(격자, 발표시각)`. 기상청 단기예보가 3시간 간격이므로 **TTL을 임의로 정하지 않고 다음 발표까지**로 둔다.
- 캐시 무효화 로직이 필요 없다 — 새 발표시각이 곧 새 키다.
- 동시 사용자가 늘어도 **호출은 격자 수만큼만** 는다(COST-U4-03).

### P-PERF-U4-2 — 평가 요청의 자연 상한
P-DET-U4-1의 평가는 **이벤트 기반**이라 주기 폴링이 없다(PERF-U4-01). 사용자 한 명이 만드는 평가 요청은 **화면 진입 + 포그라운드 복귀 + 슬롯 경계 + 방문 체크**로 상한이 자연히 잡힌다 — 별도 스로틀을 두지 않는다.

## 5. 데이터 패턴 (P-DATA-U4)

### P-DATA-U4-1 — 법정 로그는 구간 집계, 좌표는 본문 밖
수집 구간 시작·종료에 `COLLECTION` 1건씩(LEGAL-U4-02). `detail`에는 **구간 시각·점 개수·목적**만 싣고 **원시 좌표를 넣지 않는다**(LEGAL-U4-03 — `V1.3` 스키마 주석이 이미 요구).
- 좌표 본체는 `actual_route_point`에, 법적 사실은 `location_legal_log`에 — **두 계층을 섞지 않는다.**
- 파기 시 `PURGE` 로그가 짝을 이룬다(LEGAL-U4-04).

### P-DATA-U4-2 — 동의 축 재사용
실제 경로는 **기존 L3 `gps_recording_opt_in`** 에 걸린다. 재계획용 **일회성 현재 위치**는 이 축과 무관하며 적재하지 않는다(LEGAL-U4-05). 새 동의 축을 만들지 않는다.

## 6. 관측 패턴 (P-OBS-U4)

### P-OBS-U4-1 — 침묵의 근거를 남긴다
P-DET-U4-2가 침묵을 정상 동작으로 만들었으므로, **관측이 유일한 사후 근거**다.

| 지표 | 답하는 질문 |
|---|---|
| 판정 총수 / 발화 수 | "얼마나 자주 침묵했나" |
| 무발화 사유 분포(임계 미달·억제·외부 실패·영향 없음) | **"왜 알림이 안 왔나"** |
| 발화 후 `[끄기]`·`기존 유지` 비율 | "발화가 쓸모 있었나"(허위 알림 지표) |
| 세션 종료 상태 분포 | "재계획이 실제로 성립했나" |
| 지오펜스 wake / 발화 | "배터리 값을 했나" |

`plan_b_trigger`가 **발화하지 않은 판정도 저장**하는 것(DATA-U4-03)이 이 패턴의 저장 측면이다.

## 8. 미도입 결정 · 재평가 트리거

| 미도입 | 재평가 조건 |
|---|---|
| Resilience4j 서킷 브레이커 | 벤더 실패율이 실측 문제 · 느린 실패로 응답 예산 붕괴 → 도입 + **U1 패턴 문서 소급** |
| 분산 락 · rate-limit 라이브러리 | 세션 단일성(P-CON-U4-1) 우회 사례 실측 |
| 메시지 큐 · 워커 | 트리거 평가가 동기 응답으로 감당 안 될 때(현재는 이벤트 기반이라 부하가 자연 상한) |
| Redis | 격자 수 급증으로 DB 캐시가 부족할 때(U1 Q8=B 결정 실행) |
| 서버 스케줄러 기반 선제 평가 | 배포·클라우드 진입 결정 시(그때 FCM 서버 푸시와 함께) |
| 지오펜스 창 확대(2 → 전체) | 순서 건너뛰기 미감지가 실사용에서 문제로 실측될 때 |
