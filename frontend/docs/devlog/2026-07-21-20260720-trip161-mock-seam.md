**근본 원인** — jest와 실기가 `msw`를 서로 다른 파일로 해석한다:

| | jest | 실기(Metro + Hermes) |
| --- | --- | --- |
| `msw` 해석 | `moduleNameMapper`: `^msw$` → `lib/core/index.js` (**CJS**) | exports 맵 `react-native` 조건 → `lib/core/index.mjs` (**ESM**) |

| 결과 | 통과 | **크래시** |

ESM 배럴이 `sse.mjs`·`ws.mjs`를 함께 끌고 오고 그 파일들이 모듈 최상단에서 `MessageEvent`를 참조한다. SSE·WebSocket 목은 이 앱이 쓰지도 않는데 배럴이 통째로 딸려온다.

1. Hermes 크래시는 증상이고 근원은 **msw를 앱 번들에 넣으려는 시도 자체** — ①을 없애면 문제가 소멸한다(고치는 게 아니라 사라진다).
2. **이 앱에서 목은 한 번도 작동한 적이 없다.** 그럼에도 스플래시·로그인 화면이 완성됐다 → 목 없는 개발이 이미 성립해 왔고 잃을 것이 없다. (결정적 논거)
3. 엣지 케이스 화면은 정적 프리뷰가 더 싸고 확실하다(네트워크 계층을 아예 거치지 않는다).
4. 백엔드에 `/api/v1/bootstrap`·`/auth/social/*` 미구현(실측: `/api/health`·`/api/integration` 뿐). 다만 목이 애초에 안 돌았으므로 현 상태와 동일.

제거는 **별도 사이클**로 게이트를 새로 밟는다(이 사이클에서 구현을 교체하지 않는다).

## 남긴 교훈

1. **jest green은 Metro/Hermes 동작을 원리적으로 보장하지 못한다.** 해석 경로(moduleNameMapper vs exports 조건)와 런타임 전역(Node vs Hermes)이 **둘 다** 다르다. 이 사이클과 직전 사이클이 **연속 2회** 같은 틈에서 터졌다. → RN 런타임 관련 변경은 jest 통과와 무관하게 **실기 확인을 완료 조건에** 넣어야 한다(이번 사이클이 그렇게 잡아서 머지 전에 걸렀다).
2. **정적 분석 한계 2연속 실증** — ① 이번: 배럴 파일만 grep하고 **전이 의존 그래프 미추적** ② 직전: RN 소스만 읽고 **Expo winter의 `URL` 덮어쓰기** 미고려. 공통 실패 모드는 **"내가 읽은 파일 = 런타임이 로드하는 파일 집합"이라는 가정**이다. 의존성 판정은 전이 폐포를 봐야 한다.
3. **env 토글 실기 검증은 번들 인라인 값을 확인해야 한다** — `.env.local`이 셸 env를 덮는다. 1차 실기 시도가 이 함정에 빠져 무효였고(자진 신고), 그 상태에서는 코드가 **설계대로 동작한 것**이지 실패가 아니었다.

5. **게이트①-2가 "가짜 통과" 직전을 잡았다** — 동적 `import()`가 두 버킷 어디서도 실행되지 않아 성공 세계에서도 항상 실패 화면이 뜨는 상태였는데, F1 테스트는 "실패 화면이 뜬다"를 단언하므로 초록이었다. **이 사이클이 제거하려던 무성 실패가 테스트 자신에게 재현된 사례.**
