# PR 브리핑

열린 PR 을 사용자가 **이 보고 하나만 읽고** 무엇을 머지할지 정할 수 있게 정리한다. 형식은 끝 보고(`<리포 루트>/frontend/.claude/skills/trippilot-dev-cycle/reference/end-report.md`)의 결정 항목·근거 꼬리표를 그대로 쓴다. 출처: pstack `ketchup` 의 보고 형식을 범위만 "이 대화"에서 "열린 PR 전체"로 바꿨다.

## 모으기 — 기억이 아니라 gh 로만

```bash
gh pr list --state open --limit 50 --json number,title,headRefName,baseRefName,author,isDraft,mergeable,reviewDecision,createdAt,url
gh pr view <n> --json body,statusCheckRollup,files,commits,mergeStateStatus
gh pr diff <n> --name-only        # 바뀐 파일(층 파악용)
```

- **쌓인 순서**: PR 의 head 브랜치가 다른 열린 PR 의 head 를 조상으로 가지면 그 위에 쌓인 것이다 — `git merge-base --is-ancestor origin/<다른 head> origin/<이 head>`. squash 머지 리포라 아래 PR 이 들어가면 위 PR 은 `git rebase --onto` 가 필요하다고 적는다.
- **CI**: `statusCheckRollup` 의 conclusion 묶음(통과/실패/진행 중/건너뜀). 실패면 실패한 job 이름까지. 취소(CANCELLED)는 실패와 구별한다(다른 job 실패로 끊긴 것일 수 있다).
- **충돌**: `mergeable`(MERGEABLE/CONFLICTING/UNKNOWN). UNKNOWN 은 "확인 중"으로 쓰고 추측하지 않는다.
- **무슨 작업인가**: PR 본문 「요약」·「변경 사항」과 diff 파일 목록으로만 쓴다. 본문이 없거나 빈약하면 그렇다고 적고 파일 목록에서 **추론함** 꼬리표로 한 줄.

## 쓰는 방식 둘

- **PR 하나를 물으면**("1741 뭐야?", "#1677 설명해 줘") — 그 PR 만 깊게 설명한다. 아래 네 줄에 더해 ① 바뀐 파일을 층·역할별로 묶어 한 줄씩(앱 코드 / 테스트 / 하네스·문서) ② 테스트 절의 핵심(무엇을 먼저 실패시켰고 무엇을 망가뜨려 확인했는지) ③ 이 PR 과 같은 파일을 만지는 다른 열린 PR. 한국어로, 코드 초심자 눈높이.
- **전체를 물으면**("열린 PR 뭐 있어") — 아래 형식으로 PR 마다 한 덩어리.

## 보고 형식 — 기본은 "무슨 PR 인지 이해"

**사용자가 먼저 원하는 것은 머지 판단이 아니라 PR 을 이해하는 것이다**(2026-11-01 사용자 지적 — 첫 보고를 머지 순서 위주로 냈다가 "내가 뭔 PR 인지 우선 확인해야 한다"). 머지 순서·결정 항목은 사용자가 요청할 때만 붙인다.

PR 마다 한 덩어리, 아래 네 줄(코드 초심자 눈높이 — 용어는 한 줄 풀이를 붙인다):
- **무슨 문제였나** — 사용자가 겪던 증상으로(「큰 글자에서 토스트가 탭 바를 가렸다」).
- **어떻게 고쳤나** — 원리 한두 문장. 파일 이름은 꼭 필요할 때만.
- **어떻게 확인했나** — PR 「테스트」 절에서: 실패 테스트를 먼저 썼는지, 뮤테이션(일부러 망가뜨려 테스트가 잡는지)을 했는지, 실기기·시뮬레이터로 봤는지. 없으면 "실화면 미확인".
- **직접 보려면** — 앱 어느 화면에서 무엇을 하면 차이가 보이는지(기능 지도 `docs/feature-map/` 파일이 있으면 그 이름). 앱 변화가 없으면 "앱 변화 없음 — {무엇이 바뀌는지}".
- 끝에 상태 한 줄: CI · 충돌 · 작성자(내가 아닌 팀원 PR 은 표시).

머지 순서를 요청받으면 아래를 붙인다:

1. **첫 문장** — 열린 PR 수와 사용자가 정할 것이 있는지.
2. **PR 표** — 위험한 것·막힌 것(충돌·CI 실패)부터:

| PR | 무슨 작업 | 사용자에게 바뀌는 것 | CI | 충돌 | 쌓인 위치 | 위험 |
|---|---|---|---|---|---|---|

   - "무슨 작업"은 한 줄 평이한 말(「탭 바가 토스트를 가리지 않게」). 파일 이름·커밋 해시는 쓰지 않는다.
   - "사용자에게 바뀌는 것"은 앱 쓰는 사람 기준. 하네스·테스트·문서만이면 "앱 변화 없음".
   - 위험은 낮아도 적는다("낮음 — 테스트만 바뀜").
3. **추천 머지 순서** — 쌓인 순서·충돌·서로 같은 파일을 만지는지로 정한다. 같은 파일을 만지는 PR 끼리는 먼저 넣을 것을 이유와 함께.
4. **결정할 것** — 머지·리뷰·충돌 해결처럼 사용자만 할 수 있는 것. 항목마다 추천·근거·위험(끝 보고 형식).
5. 내가 더 할 수 있는 일 한 줄(예: 충돌 rebase, CI 재실행).

## 쓰지 않는 것

- 확인 안 한 CI 결과나 충돌을 "될 것"이라고 쓰지 않는다 — 모르면 "모름".
- PR 본문을 통째로 옮기지 않는다 — 한 줄로 줄인다.
- 머지·rebase 를 이 스킬 안에서 하지 않는다 — 보고까지다. 사용자가 고르면 그때 한다.

*유지 판정: 6회 관찰 — 보고 뒤 사용자가 "이 PR 뭐였지?"·"이거 머지해도 돼?" 류로 되물은 건수를 로그.md 한 줄에 `pr-briefing — 되물음 n`으로 남긴다. 0이 유지되면 형식을 유지하고, 늘면 빠진 칸을 더한다.*
