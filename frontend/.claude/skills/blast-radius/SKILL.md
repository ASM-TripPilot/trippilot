# 영향 반경

변경이 **다른 곳에서** 무엇을 깨뜨리는지 출시 전에 찾는다. 호출부 목록은 일이 아니다 — grep 한 번이면 나온다. 일은 grep이 못 보여 주는 파손을 찾는 것이다.

출처: pstack `blast-radius`(cursor/plugins `harness/pstack/`)를 이 리포에 맞춰 옮겼다.

## 내 글을 믿지 않는다

그럴듯한 영향 분석은 쓸모없다 — 참이든 거짓이든 똑같이 설득력 있게 읽힌다. 글을 넘기지 말고, **이 변경이 안전한 근거가 되는 사실 1~2개**를 찾아 코드를 돌려 증명한다.

사실마다 아래 어디까지 내려갔는지 적는다(싸게 갈 수 있는 데까지):

1. 내가 그렇다고 함 — 그 자체로는 가치 없음
2. `파일:줄`을 짚음 — 실제 줄, 또는 라이브러리 소스
3. 나쁜 경우가 일어날 수 없음을 단계별로 보임
4. **돌림** — 실제 코드를 부르고 틀리면 크게 실패하는 스크립트·테스트
5. **실행 중인 앱에서 재현** — 시뮬레이터(`trippilot-sim-qa`) 또는 웹(Aside, 같은 스킬 「웹 버전 QA」)

4는 보통 앱이 쓰는 라이브러리를 그대로 import해 걱정되는 함수 하나를 부르는 작은 스크립트다(`pnpm test:node <파일>`로 도는 임시 테스트면 충분 — 끝나면 지운다).

## 절차

1. **변경을 읽는다** — diff, 추가·변경·삭제된 심볼, diff가 말하지 않는 동작 변화까지. 커밋·PR 맥락은 `git log -p`.
2. **안전 근거 사실을 찾는다** — 위험해 보이는 변경 대부분은 사실 하나 때문에 안전하다(예: "앱에서 화면 안 진입이면 `canGoBack()`은 항상 true라 이 분기는 웹 콜드 진입에서만 탄다"). 그 사실이 서면 위험 경우 대부분이 한 번에 지워진다. **시간은 여기에 쓴다** — 가능성 목록을 길게 쓰는 데가 아니라.
3. **grep이 끝나는 곳을 본다** — 이 리포에서 자주 끝나는 곳:
   - **플랫폼 분기** — `Platform.OS`·`*.web.ts(x)`·`*.ios.ts(x)`. 웹 고치려다 네이티브 경로를 같이 바꿨나, 반대로 한쪽만 고쳤나
   - **통과형 목 뒤** — `__mocks__/@gorhom/bottom-sheet`·지도 목. 그 화면 jest가 green이어도 실제 열림·제스처는 안 본다(repo-traps 「바텀시트」)
   - **라이브러리 소스와 고정 버전** — `node_modules/<lib>` 실제 구현, `patches/`·pnpm patch 여부. expo-router·RN-web은 문서와 실제 동작이 다른 곳이 있다
   - **실행 시점** — 마이크로태스크, 언마운트·포커스 이탈, TanStack Query 캐시 무효화 순서, `useEffect` 정리
   - **선 밖의 소비자** — 서버 응답 JSON 모양(orval 생성 타입은 서버가 바꾸면 조용히 낡는다), 딥링크 경로, AsyncStorage/SecureStore 키, 푸시 payload
   - **세 단계 아래** — 공용 훅 → 위젯 → 화면. `src/shared/**`는 FSD상 모든 층이 쓴다
4. **위험마다 솔직하게** — 실제 일어날 확률과 일어났을 때 비용. 확인된 위험과 **확인하고 지운 것**을 따로 적는다. 실제 `파일:줄`을 인용하고, 검색 결과 0건도 답이다. 없는 호출부·API를 지어내지 않는다.
5. **근거 사실을 돌려서 증명한다** — 스크립트·테스트를 쓰고 돌리고 출력을 붙인다. 화면 동작이 근거면 5단계(앱)까지 간다.
6. 크고 넓은 변경이면 독립 판단을 하나 더 받는다 — `Agent(general-purpose)`에 diff와 이 절차만 주고(내 결론은 주지 않는다) 같은 질문을 던져 합친다.

- **머지 전에** — 진짜 버그를 잡는 가장 싼 테스트나 재현(쓴 스크립트 포함)
