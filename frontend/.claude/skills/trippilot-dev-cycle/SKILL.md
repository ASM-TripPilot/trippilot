# TripPilot Dev Cycle — 오케스트레이터

루프 엔지니어링 개발 사이클: 인지 → 메모리 → 설계 → 테스트(게이트①) → 구현(게이트②) → 검증 → 리팩토링 → 재검증 → 기록.

**실행 모드: 하이브리드** — 메인 세션이 오케스트레이터로서 사용자 게이트와 MCP 호출(Ouroboros/Obsidian/Figma)을 직접 관리하고, 단계별 전문 작업은 서브 에이전트(`Agent` 도구, 반드시 `model: "opus"`)에 위임한다. 사용자 검토 게이트가 2개 있어 실시간 팀 통신보다 순차 파이프라인이 적합하다.

**규모 분기 (경량 사이클)**: 단일 파일 수준 + 기존 테스트 유지 범위의 소규모 작업(오타·한 줄 버그픽스·문구 변경)은 [인지]·[설계]를 메인이 직접 축약하고(서브 에이전트·인터뷰 생략, 브리프·01b 즉석 작성) **게이트①·②를 1회 통합 제시**로 병합한다 — 00_gates.md 기록 형식(해시·red 로그)은 동일하게 유지한다. 작업 규모와 무관한 중량 사이클은 사용자의 하네스 우회를 유발하고, 우회는 전 장부에 구멍을 낸다.

## 경로 규약 (모든 단계 공통)

- **리포 루트**는 `git rev-parse --show-toplevel`로 확정한다 (예: `~/Desktop/dev/trippilot`).
- 사이클 작업 공간: `<리포 루트>/_workspace/{cycle-id}/` — **항상 리포 루트 기준**. cwd 기준 상대경로 금지.
- 서브 에이전트 프롬프트에는 작업 공간과 산출물 경로를 **절대 경로로** 전달한다 — 서브 에이전트의 cwd(frontend)에서 상대경로를 해석하면 생산자와 소비자가 서로 다른 디렉토리를 보게 된다.

## 게이트 원장 (00_gates.md)

게이트 승인은 `_workspace/{cycle-id}/00_gates.md`에 즉시 영속한다. **이 파일에 기록 없는 게이트는 산출물 파일이 있어도 미통과다** — 파일 존재는 "작성됨"이지 "승인됨"이 아니다.

```
## 게이트① — {승인 시각}
- 승인 테스트 파일: {경로}: {shasum 해시} ...
- red 실행 로그: (원문, 또는 "미실행 — 사유")
## 게이트② — {승인 시각}
- 승인 구현 파일: {경로}: {shasum 해시} ...
```

- **승인 기록의 필수 필드**: 사용자 승인 발화 원문 인용 + 제시 시점 해시의 전사. 해시는 게이트 제시 시점에 계산해 **채팅 요약에 명시**하고(채팅이 사후 수정 불가능한 유일한 채널이다), 00_gates.md에는 그 값을 옮겨 적는다 — 승인 후 재계산 금지. 승인은 "그 해시의 파일"에 대한 승인으로 정의된다.
- **해시는 포맷 후 상태로 박제한다**: 산출자(test-designer/implementer)가 게이트 제시 전 prettier를 통과시키는 것이 의무다. 검증 단계의 포매터는 멱등이므로 승인 해시를 바꾸지 않는다 — 해시 대조 불일치는 전부 진짜 변조다.
- 게이트① 제시 전에 오케스트레이터가 테스트를 직접 1회 실행해 red 로그를 첨부한다(**verify-gates §0 사전 점검 선행** — 설정 부재로 인한 전멸은 red가 아니라 "미실행 — 사유"로 기록). red 로그에는 실행 시점 테스트 파일 해시를 병기한다. [검증]에서 qa-verifier가 red 소급 확인을 **로그 유무와 무관하게 상시** 수행한다.
- **검증 판정도 원장에 append**한다(판정·차수·시각 — qa-verifier 수행). FAIL 카운터의 정본은 원장이다.
- **부분 재실행 시 하류 무효화**: 특정 게이트를 다시 열면 그 이후 게이트의 원장 항목에 "무효화(사유·시각)" 행을 append한다(기존 행 수정 금지). 해시 대조·재개 판별은 항상 **각 게이트의 최신 유효 섹션** 기준이다.
- 수정 루프·리팩토링으로 코드가 게이트② 승인 해시와 달라진 채 검증을 PASS하면, 기록으로 가기 전에 **게이트②를 재제시**한다(변경 diff와 사유 포함). 이 해시 대조는 qa-verifier의 04 필수 항목이다(오케스트레이터 자체 판단 금지). 재제시가 반려되면 [구현] 수정 루프로 복귀한다.

## 게이트 제시 규칙 (게이트①·② 공통 — 이해가 병목이다)

사용자의 이해 속도가 사이클의 실제 병목이다. 게이트가 "읽지 않은 승인"으로 변질되면 인지 부채가 쌓인다. 제시 형식으로 이를 방어한다:

- **서술형 우선**: 게이트 제시의 본문은 diff·코드 나열이 아니라 **개념 순서의 서술형 설명**이다 — 왜 이 설계인가 → 데이터/화면 흐름 → 의심해야 할 지점·트레이드오프 순. 원시 diff·코드는 첨부로 제공한다(diff는 코드 순서지 개념 순서가 아니라서 이해 비용이 높다).
- **줄단위 주해(학습 첨부)**: 추가·수정된 코드의 첨부는 원시 diff가 아니라 **주해 달린 코드**를 기본으로 한다 — 의미 있는 줄(또는 의미 단위 블록)마다 "무엇을 하는가 + 왜 필요한가"를 달고, 사용자가 처음 볼 가능성이 있는 개념(RN/Expo API·TanStack 패턴·fast-check 문법 등)은 이름만 쓰지 말고 한 줄 개념 설명을 병기한다. 주해는 산출자(test-designer/implementer)가 산출물 문서(02/03)에 작성한다 — 쓴 사람이 이유를 안다. **코드 파일 자체에는 학습 주해를 넣지 않는다**(리포 주석은 "주변 밀도 준수 + 코드가 말할 수 없는 제약만" 규칙 그대로).
- **주해 분량 통제**: 게이트 노트 최상단에 **"지금 배울 핵심 개념 5~7개"** 섹션을 강제하고 나머지 주해는 부록으로 격하한다. 보일러플레이트는 블록 단위, **도구 생성 파일(스캐폴딩 템플릿·orval 생성물)은 생성 명령·설정만 주해·해시 대상으로 하고 생성물 자체는 목록+건수만** 기재한다. 예상 열람 30분 초과면 차수 장치를 재사용해 분할 제시한다. 모를수록 주해가 길어지는 구조는 "읽지 않은 승인"을 제조한다 — 분량이 이해를 이기게 두지 마라.
- **이해 체크**: 제시 끝에 역질문 2개를 던진다. **출제 기준: 채팅 요약만으로는 답할 수 없고 게이트 노트의 주해 본문을 읽어야 답할 수 있는 지점에서 낸다** — 노트 열람이 답변의 전제 조건이 되게. 사용자가 답이 막히면 승인 보류가 아니라 **해당 부분을 더 설명하는 트리거**로 쓰고, **막힌 항목은 이해부채 후보로 자동 등재**한다(사용자 확인 후 장부화 — 막힌 답이 가장 확실한 부채 신호다). 답변 요지는 게이트 노트 결과 섹션에 기록한다 — 기록 없는 체크는 형해화를 관찰할 수 없다.
- **이해부채 수집 (즉시 영속)**: 사용자가 "동작은 믿고 승인하지만 아직 이해 못 함"을 표한 항목 + 이해 체크에서 막힌 항목은 **게이트 기록 시점에 즉시** 게이트 노트 결과 섹션과 00_gates.md에 쓴다 — [기록]까지 세션 메모리에만 두면 에스컬레이션 중단·세션 사망 시 부채가 증발한다([기록]의 scribe는 건별 노트화·정리만 담당). **장부화 필터**: 다음 작업을 막을 항목만 부채로 올리고, 나머지는 개발로그의 "참고 개념" 목록으로 격하한다. **파산 차단**: 미상환 부채 10건 초과 시 [메모리] 단계에서 새 사이클 대신 정리 세션(폐기/통합/상환)을 먼저 제안한다 — 적립이 상환을 초과하는 장부는 학습 도구가 아니라 빚 독촉이 된다.
- **열람 채널은 옵시디언**: 게이트 제시 전문(서술형 본문 + 줄단위 주해)은 오케스트레이터가 옵시디언 `TripPilot/게이트/{YYYY-MM-DD} {cycle-id} 게이트{①|②}-{n}.md`로 저장한다(`게이트 템플릿` 구조, n=제시 차수 — 재제시는 새 차수로, 덮어쓰기 금지). 채팅에는 핵심 요약 + 게이트 노트 위치 + 이해 체크 2개 + 승인 요청만 제시한다 — **옵시디언에서 읽고, 채팅에서 승인한다.** 쓰기 순서는 **원장 먼저, 노트 나중** — 갈라지면 원장이 단독 권위이고, 무효가 된 구 노트에는 "무효(재제시됨)"를 표기한다. 승인/반려 결과는 노트의 결과 섹션에 갱신한다. Obsidian MCP 불가 시 기존대로 채팅에 전문을 제시하고 폴백을 명시한다. (`_workspace/`의 02/03은 파이프라인 정본으로 그대로 유지 — 게이트 노트는 열람·학습용 스냅샷이다.)
- **채팅 요약의 생략 불가 항목**: ① 변경/테스트 파일 전체 목록 + 각 해시 ② 커버되지 않는 AC·경계 전부 ③ 의심 지점·트레이드오프. 요약에서 불리한 내용이 빠지면 "읽지 않은 승인"의 대상이 요약이 된다 — scribe가 [기록]에서 채팅 요약 ↔ 게이트 노트의 이 항목들 일치 여부를 대조·기록한다.

## Phase 0: 컨텍스트 확인

1. 사이클 ID 결정: `{YYYYMMDD}-{작업슬러그}` (예: `20260717-trip160-scaffold`). **같은 날 같은 슬러그의 새 작업은 순번 접미사를 붙인다**(`-2`, `-3`…) — 게이트 기록이 있는 기존 폴더의 재사용은 금지다(구 사이클의 승인이 새 작업에 상속되는 사고를 막는다).
2. `<리포 루트>/_workspace/` 확인:
   - 해당 사이클 폴더 존재 + 부분 수정 요청 → **부분 재실행** (해당 단계만 재호출)
   - 해당 사이클 폴더 존재 + 새 작업 → **새 사이클** (순번 접미사 새 폴더)
   - 미존재 → **초기 실행**. 단, 옵시디언 에러로그에 동일 슬러그의 에스컬레이션 기록이 있으면 FAIL 잔고를 승계 보고한다(폴더 삭제로 상한 카운터를 세탁할 수 없다).
3. 재개 시 진행 단계 판별: 산출물 파일 존재 **+ 00_gates.md의 승인 기록**을 함께 본다. 승인 기록 없는 게이트는 그 게이트부터 재개한다. 추가로 **현재 파일 해시 vs 원장의 게이트①·② 승인 해시를 대조**한다 — 게이트② 이후 코드가 승인본과 다르면 기존 04 리포트를 stale로 간주하고 [검증]부터 재개한다(미검증 반쪽 코드가 낡은 PASS를 증거로 기록되는 것을 막는다).
4. **재개·부분 재실행 진입 시 사용자에게 상태 요약을 먼저 제시한다**: 게이트별 승인 여부 + 이번 요청으로 무효화될 게이트(테스트 재작성은 게이트②도 무효화한다) → 확인 후 진행. 원장은 사용자 열람 채널 밖의 파일이므로, 상태는 하네스가 보여줘야 한다.

## 사이클 단계

### 1. [인지] — spec-analyst (서브)
`Agent(spec-analyst, model: "opus")` 호출, 대상 작업 설명 + 작업 공간 **절대 경로** 전달.
산출: `01_spec-analyst_brief.md`. 열린 질문이 있으면 다음 단계 전에 사용자에게 제시한다.

### 2. [메모리] — 메인 직접
`obsidian-second-brain` 조회 규칙대로 최근 개발로그·문제로그·미해결 항목 확인 + 리포 `frontend/docs/devlog/` 최근 파일 확인. 요약을 이후 단계 프롬프트에 반영한다(읽고 버리면 메모리가 아니다).
**미상환 이해부채 1~2건을 사용자에게 재노출한다**(간격 반복) — 이번 작업과 관련된 항목 우선. 사용자가 "이제 이해했다"고 하면 상환 처리(status 갱신)를 [기록] 단계에 포함한다.

### 3. [설계] — 메인 직접 (Ouroboros MCP)
0. **생략 조건**: 브리프의 열린 질문이 0건이고 정본 인용만으로 AC가 충족되면 인터뷰를 생략하고 곧장 폴백 경로(브리프 AC를 01b로 저장, "인터뷰 생략 — 정본 충족" 명시)를 쓴다 — 정본이 이미 답한 질문을 학습 중인 사용자에게 던지는 것은 부하이자 신뢰 손상이다.
1. `mcp__ouroboros__ouroboros_interview`로 브리프의 모호점을 인터뷰한다(세션 기반 — 위임 영수증이 반환되면 지시대로 처리).
2. 모호성 기준 도달 시 `ouroboros_generate_seed(session_id)`로 Seed를 생성한다. Seed는 인터뷰 대화에서 추출되므로 추적 코드가 빠질 수 있다 — 오케스트레이터가 브리프의 추적 코드(US/ADR/INV)를 병기해 보강한다.
3. 결과를 **`01b_ouroboros_seed.md`로 저장한다 — 폴백 포함 항상 생성**: Ouroboros 불가·모호성 게이트 미달 시 브리프의 AC 초안을 01b로 저장하고 "폴백"을 명시한다. (01b가 항상 존재해야 test-designer 입력 경로가 보장된다.)
4. 01b 요약을 사용자에게 제시한다(설계 방향 확인).

### 4. [테스트 작성] — test-designer (서브) → 🧑 게이트 ①
`Agent(test-designer, model: "opus")`, 입력: 01 + 01b (절대 경로).
산출: 실패 테스트 + `02_test-designer_map.md`.
**게이트 제시 규칙에 따라 제시한다 — 전문(02의 "테스트 설계 설명" + 매핑 표 + 주해 달린 테스트 코드)은 게이트 노트에 수록하고, 채팅은 열람 채널 규칙의 요약 형식(생략 불가 항목 포함) + 이해 체크 2개 → 승인 → 00_gates.md에 게이트① 기록(승인 발화 인용 + 포맷 후 파일 해시 + red 로그). 승인 전 구현 금지.**

### 5. [구현] — implementer (서브) → 🧑 게이트 ②
`Agent(implementer, model: "opus")`. 승인된 테스트를 green으로.
**게이트 제시 규칙에 따라 제시한다 — 전문(03의 "변경 설명" + 줄단위 주해)은 게이트 노트에 수록하고, 채팅은 열람 채널 규칙의 요약 형식 + 이해 체크 2개 → 승인 → 00_gates.md에 게이트② 기록(승인 발화 인용 + 포맷 후 파일 해시 — 테스트 인프라 파일 포함 변경 전체).**

### 6. [검증] — qa-verifier (서브)
`Agent(qa-verifier, model: "opus")`, 입력: 변경 파일 목록 + 00_gates.md **절대 경로**.
산출: `04_qa-verifier_report_{n}_{PASS|FAIL}.md` — n은 사이클 내 검증 차수(채번 = 기존 최대 n+1), **덮어쓰기·삭제 금지**. 판정·차수·시각을 00_gates.md에도 append한다(카운터의 정본은 원장).
- FAIL → implementer 재호출(수정 루프). **같은 게이트 3회 연속 FAIL 또는 사이클 누적 FAIL 리포트 5개(원장 기준 — PASS는 세지 않는다) 시 사용자 에스컬레이션 + 에러로그 기록.** 실패 게이트가 번갈아 나와도 누적 상한에 걸린다. 에스컬레이션 본문은 서술형 실패 요약 + 선택지 2~3개, 로그 원문은 첨부(verify-gates 판정 규칙 참조).
- 실행 불가(도구/설정 부재) → 수정 루프로 보내지 말고 필요한 설정을 사용자에게 보고한다. 단 **부재 원인이 이번 사이클 AC면 FAIL로 취급해 수정 루프로**(verify-gates §0 예외). 실행 불가 상태로 [기록]에 가면 "미검증" 플래그를 강제 명기한다.
- PASS → qa-verifier가 04에 기록한 게이트② 해시 대조 결과에 따라: 불일치("PASS(재제시 필요)")면 게이트② 재제시, 일치면 다음 단계.

### 7. [리팩토링] — implementer (서브, 선택)
동작 변경 없는 구조 개선. **완료 후 qa-verifier 재실행 필수(re-green) + 게이트② 재제시 규칙 적용.** 개선 여지가 없으면 건너뛴다.

### 8. [기록] — scribe (서브)
`Agent(scribe, model: "opus")`, 입력: `_workspace/{cycle-id}/` 절대 경로 + 문제/에러 발생 내역 + **게이트에서 수집한 이해부채 목록(상환된 항목 포함)** + **게이트 노트 경로·차수 목록**(개발로그가 링크 허브가 되기 위한 입력). 최신 04 리포트는 경로로 전달하지 않는다 — scribe가 `04_qa-verifier_report_*`를 직접 나열해 최대 n을 스스로 확정한다(선별 전달 오염 방지).
게이트 통과 현황은 scribe가 **04 리포트의 표를 원문 복사**한다 — 오케스트레이터의 요약 재서술로 대체 금지(심판받는 루프의 자기서술이 기록을 오염시킨다). 이해부채는 `TripPilot/이해부채/`에 건별 기록하고, 상환된 항목은 status를 갱신한다.

### 9. 사이클 종료
결과 요약(완료 내용, 게이트 현황 — 00_gates.md·최신 04 리포트 기준, 기록 위치) + 다음 사이클 후보 제시. 하네스 개선 피드백 기회를 제공한다.

## 에러 핸들링

- 에이전트 실패: 1회 재시도 → 재실패 시 해당 단계 결과 없이 사용자에게 보고한다(침묵 진행 금지)
