# 게이트 프로토콜

게이트①·② 제시 직전에 읽는다. 제시 순서, 원장 기록 형식, 해시 규약, 노트·요약 형식, 이해부채 수집이 여기 있다.

**주해 규칙은 이 파일에 없다** — 제시 순서 6에 해당하는 대화 주해 규칙은 같은 디렉토리의 `annotation.md`가 정본이다.

## 목차

- **게이트 제시 순서** — 복사해 체크하는 8단계 (먼저 읽어라)
- 게이트 원장 (00_gates.md) — 기록 형식·해시 규약·red 로그·무효화·재제시
- 게이트 노트 — 4계층 구조(§0 자리 지도) + **막힌 줄만** 남기는 §3 (주해 규칙 자체는 `annotation.md`)
- 채팅 요약 — 생략 불가 항목 + 형식 예시
- **대화 주해 → `annotation.md`** — 진행 방식·내용 규칙·함수 입자·줄 단위 승격·인라인 형식·비용 규약 (제시 순서 6, 별도 파일)
- 이해 체크와 이해부채 — 퀴즈 5문항(줄 단위 승격 트리거)·등재 기준·개념 노트
- 학습자 모드 — 학습자 프로필 주입·핵심 개념 선정
- 경량 사이클의 이해 체크 — 통합 제시 시 두 축 유지

## 게이트 제시 순서

응답에 복사해 체크하며 진행한다. **순서를 바꾸면 원장이 오염된다** — 특히 3(해시 계산)과 7·8(원장 먼저, 노트 나중).

```
게이트{①|②}-{n} 제시:
- [ ] 1. 산출자(test-designer/implementer)가 prettier 통과 — 해시 박제의 전제
- [ ] 2. [게이트①만] verify-gates 사전 점검 → **환경 지문 기록** → red 1회 실행 → 로그 확보
- [ ] 3. shasum으로 파일 해시 계산 — 이 시점 값이 곧 승인 대상
- [ ] 4. 등장 개념 선정 → "지금 배울 핵심 개념 5~7개" (3-a 맹점 훑기에서 "모른다"고 한 것이 1순위)
- [ ] 5. **게이트 설명 HTML 아티팩트 생성·게시** (요약 생략 불가 항목 + §0 지도[mermaid] + 핵심 개념 + 파일별 주해 본문[배경→직관→흐름 문답·★함정 표시]) → 링크를 채팅에 제시 (**아래 「게이트 설명 아티팩트」를 읽고 시작한다**)
- [ ] 6. **채팅 상호작용** — **퀴즈 5문항** → 틀린 함수만 줄 단위 승격(채팅) → '여기 자세히'·막힘 재설명(채팅) (**`annotation.md`를 읽고 시작한다**)
- [ ] 7. 승인 요청 → 승인 수령 → 00_gates.md 기록 (발화 인용 + 3에서 계산한 해시 전사)
- [ ] 8. 게이트 노트 작성 (§0~§2 + **막힌 줄만** §3 · 승인/반려 · 이해부채)
```

- **3 → 7의 해시는 같은 값이어야 한다.** 승인 후 재계산 금지 — 승인은 "그 해시의 파일"에 대한 승인으로 정의된다.
- **7이 8보다 먼저다.** 둘이 갈라지면 원장이 단독 권위다 — 노트는 열람용 스냅샷이고 원장은 감사 대상이라, 세션이 죽으면 살아남아야 하는 쪽이 원장이다.
- 반려되면 6으로 돌아가지 않고 산출 단계([테스트 작성]/[구현])로 복귀한 뒤 1부터 새 차수로 다시 탄다.

## 게이트 원장 (00_gates.md)

게이트 승인은 `_workspace/{cycle-id}/00_gates.md`에 즉시 영속한다. **이 파일에 기록 없는 게이트는 산출물 파일이 있어도 미통과다** — 파일 존재는 "작성됨"이지 "승인됨"이 아니다.

### 기록 형식

```
## 게이트① — {승인 시각}
- 승인 발화: "{사용자 원문 인용}"
- 승인 테스트 파일: {경로}: {shasum 해시} ...
- red 실행 로그: (원문, 또는 "미실행 — 사유")
- 환경 지문: {있는 설정 파일 목록 + node/pnpm 버전}
## 게이트② — {승인 시각}
- 승인 발화: "{사용자 원문 인용}"
- 승인 구현 파일: {경로}: {shasum 해시} ...
```

필수 필드는 셋이다:
- **사용자 승인 발화 원문 인용**
- **제시 시점 해시의 전사** — 제시 시점에 계산해 채팅 요약에 명시하고(채팅이 사후 수정 불가능한 유일한 채널이다), 원장에는 그 값을 옮겨 적는다
- **환경 지문**(게이트①만) — 제시 시점에 존재한 검증 설정의 목록. verify-gates §0 사전 점검을 돌면서 확인한 것을 그대로 적는다:

  ```bash
  ls package.json jest.config.js jest.integration.config.js eslint.config.js tsconfig.json \
     .prettierrc .prettierignore 2>/dev/null
  node -v; pnpm -v
  ```

  **이 필드가 없으면 "도구를 부숴 FAIL을 판정 불능으로 세탁하는 경로"가 열린다** — qa-verifier가 검증 시점에 이 목록과 대조해, 게이트① 때 있던 설정이 사라졌으면 실행 불가가 아니라 **FAIL + 변조 에스컬레이션**으로 판정한다(verify-gates "0. 사전 점검").

  **prettier 설정 2개가 목록에 있는 이유**(2026-07-21 추가): verify-gates §0이 prettier 설정을 실행 전제로 요구하는데 지문에는 빠져 있어, 게이트① 이후 지워도 대조에 안 걸리는 구멍이 있었다. 특히 `.prettierignore` 소실은 `pnpm format`이 `.claude/`·정본 md까지 재포맷해 **승인 해시를 무더기로 흔든다**.

### 해시 규약

- **포맷 후 상태로 박제한다.** 산출자가 게이트 제시 전 prettier를 통과시키는 것이 의무다.
- 검증 단계의 포매터는 멱등이므로 승인 해시를 바꾸지 않는다 — **해시 대조 불일치는 전부 진짜 변조다.**

### red 로그 (게이트①)

- 제시 전에 오케스트레이터가 테스트를 직접 1회 실행해 첨부한다. **verify-gates §0 사전 점검을 선행**한다.
- 설정 부재로 인한 전멸은 red가 아니라 `"미실행 — 사유"`로 기록한다.
- 로그에는 실행 시점 테스트 파일 해시를 병기한다.
- [검증]에서 qa-verifier가 red 소급 확인을 **로그 유무와 무관하게 상시** 수행한다.

### 검증 판정 append

- 판정·차수·시각을 원장에 append한다(qa-verifier 수행). **FAIL 카운터의 정본은 원장이다.**

### 무효화와 재제시

- **부분 재실행 시 하류 무효화**: 특정 게이트를 다시 열면 그 이후 게이트의 원장 항목에 `무효화(사유·시각)` 행을 append한다. **기존 행 수정 금지.** 해시 대조·재개 판별은 항상 각 게이트의 **최신 유효 섹션** 기준이다.
- **게이트② 재제시 조건**: 검증 FAIL 수정 루프로 코드가 게이트② 승인 해시와 달라진 채 검증을 PASS하면, [기록]으로 가기 전에 게이트②를 재제시한다(변경 diff와 사유 포함).
  - 이 해시 대조는 **qa-verifier의 04 필수 항목**이다 — 오케스트레이터 자체 판단 금지.
  - 재제시가 반려되면 [구현] 수정 루프로 복귀한다.

## 게이트 노트

게이트 제시는 **채팅에서 읽고 채팅에서 승인한다**(제시 순서 5~7). 옵시디언 노트는 그 뒤에 **남길 것만** 담는 복습 기록이다 — 대화는 `/clear`로 사라지고, 이해부채 상환 때 다시 읽을 곳은 볼트뿐이다.

- 경로: `TripPilot/게이트/{YYYY-MM-DD} {cycle-id} 게이트{①|②}-{n}.md` (`게이트 템플릿` 구조)
- `n`은 제시 차수. **재제시는 새 차수로, 덮어쓰기 금지.** 무효가 된 구 노트에는 `무효(재제시됨)`를 표기한다.
- 승인/반려 결과는 노트의 결과 섹션에 갱신한다(순서 8).
- Obsidian MCP 불가 시 채팅에 전문을 제시하고 폴백을 명시한다.
- `_workspace/`의 02/03은 파이프라인 정본으로 그대로 유지된다 — 게이트 노트는 열람·학습용 스냅샷이다.

### 4계층 구조 (위에서부터 읽다가 멈출 수 있게)

노트는 **위에서부터 읽다가 멈출 수 있게** 쌓는다 — §0 지도만 봐도 자리가 잡히고, 아래로 갈수록 세부다.

**네 계층은 게이트 노트 한 파일 안의 네 섹션이다** — 노트를 쪼개지 않는다. 사용자는 노트 하나만 열면 지도부터 막힌 줄 기록까지 다 있다.

| 계층 | 내용 | 분량 | 반복 단위 |
|---|---|---|---|
| **§0. 이번 변경이 붙는 자리** | 만진 조각의 흐름도 — 어느 파일이 무엇을 부르나 + **다음 수 한 줄** | 5~10줄 + 1 | 노트당 1회 |
| §1. 지금 배울 핵심 개념 | 이번 게이트의 신규/미소화 개념만 | 5~7개 | 노트당 1회 |
| §2. 파일별 요약 | 직관 한 줄 + 함수별 흐름 (+ 실적 `함수 n · 퀴즈승격 n · 자발승격 n`) | 파일당 3~5줄 | **변경 파일마다** |
| §3. 막힌 줄 기록 | 줄 단위로 승격된 함수에서 막힌 줄 + 재설명 | **막힌 줄만** | **변경 파일마다** |

"파일별"은 노트가 파일마다 쪼개진다는 뜻이 아니라, 변경된 소스 파일 수만큼 §2·§3 안에서 덩어리가 반복된다는 뜻이다(파일 4개 → 한 노트 안에 §2 4덩어리, §3 4덩어리).

#### §0 — 왜 필요한가

**대화 주해는 조각 단위라, 조각을 다 알아도 지도는 안 생긴다.** "이 파일이 왜 여기 있고 누가 부르나"는 어느 줄에도 안 적혀 있다. §0이 그 한 층 위를 담당한다. **그래서 §0은 대화보다 먼저 제시된다**(제시 순서 5) — 지도 없이 줄부터 걸으면 걸을 때마다 길을 잃는다.

**전체 지도가 아니라 이번에 만진 조각만.** 재료는 `docs/structure.md`와 03 구현 노트에 이미 있다 — 옮겨 그린다.

**형식은 매체를 따른다** — 채팅에는 아래 같은 ASCII 흐름도를, **게이트 노트에는 `mermaid` 코드펜스**를 쓴다(옵시디언이 렌더하므로 복습 때 그림으로 보인다). **채팅에 mermaid 소스를 내지 마라** — 터미널은 다이어그램을 렌더하지 않아 소스가 그대로 보인다. 그리는 것은 한 번이고 옮겨 적을 때 형식만 바꾼다.

```
[소셜 로그인 버튼]  features/auth/ui/
       │ 누름
       ▼
[useSocialLogin]    features/auth/hooks/     ← 화면은 여기까지만 안다
       │
       ▼
[makeAuthorize]     features/auth/lib/       ← 갈래 3개
       │              · fake 토글 on   → 가짜 응답
       │              · off + clientId → ▼ 동적 import
       │              · off + 설정없음 → throw (INV-4)
       ▼
[realAuthorize]     features/auth/lib/       ★ expo-auth-session을 아는 유일한 파일
       │
       ▼
[oauthConfig]       features/auth/lib/       ← env에서 clientId 읽기

이번에 새로 생긴 것: realAuthorize.ts · oauthConfig.ts
다음 수: 네이버 추가 = realAuthorize에 갈래 1개 + oauthConfig에 clientId 1줄. 화면·훅은 안 바뀐다.
```

**흐름도 끝에 "다음 수" 한 줄을 단다.** 흐름도는 *지금 무엇이 있나*까지만 답한다. 게이트의 이해가 승인으로 끝나지 않고 **다음 사이클의 아이디어**가 되려면 지도 위에서 다음 수가 보여야 한다 — 어느 상자를 늘리면 되나, 무엇을 바꾸면 어디가 깨지나. 이 한 줄이 게이트에서 유일하게 *승인이 아니라 참여*를 겨냥하는 자리다(나머지 장치는 전부 "이번 변경을 이해했나"를 잰다).

- **흐름도의 재서술이면 뺀 것과 같다.** *"realAuthorize가 expo-auth-session을 안다"*는 그림에 이미 있다 — 값은 *"네이버를 넣으면 여기 한 상자만 늘고 화면은 안 바뀐다"* 쪽에 있다. **무엇이 안 바뀌는지를 같이 적을 때** 경계가 드러난다.
- 재료는 §0을 그리면서 이미 다 나와 있다 — 새로 조사하지 마라. 안 보이면 *"이 지도로는 다음 수가 안 보인다"*가 정직한 값이고, 그건 지도가 덜 그려졌다는 신호다.

*유지 판정: 6사이클 관찰 — 이 줄이 비어 있거나 흐름도 재서술뿐인 건이 4사이클 이상이면 뗀다(지도만으로 다음 수가 안 나온다는 뜻이라, 고칠 곳은 이 줄이 아니라 §0의 재료다). 실적은 scribe가 개발로그에 `다음 수 — 기재 n / 재서술 n`으로 남긴다.*

§0은 **구조축 역질문의 출제 근거**이기도 하다(아래 "이해 체크").

- §1 본문은 **개념 순서의 서술형**이다 — 왜 이 설계인가 → 데이터/화면 흐름 → 의심해야 할 지점·트레이드오프 순. 원시 diff는 코드 순서지 개념 순서가 아니라서 이해 비용이 높다.
- **노트가 둘 이상이 되는 경우는 분할 제시뿐이다**: 30분 초과로 차수를 나누면 `게이트①-1`·`게이트①-2`가 되고 **각 노트가 다시 4계층을 갖는다**.
- 예상 열람 30분 초과면 차수 장치를 재사용해 분할 제시한다.
- 분량이 이해를 이기게 두지 마라 — 다만 **이기지 못하게 하는 수단은 요약의 질이지 주해의 누락이 아니다.**

### 주해 규칙은 `annotation.md`에 있다

§3(막힌 줄)에 쓰는 인라인 형식과, 그 줄을 여는 기준(줄 단위 승격)은 **`annotation.md`** 소관이다 — 게이트 노트는 주해의 *저장소*이지 주해 규칙의 자리가 아니다. 무엇을 담는가·어떤 입자로·언제 줄로 내려가는가는 전부 그쪽에 있다.

## 게이트 설명 아티팩트 (HTML)

**제시 순서 5의 산출물이다 — 요약·§0 지도·핵심 개념·파일별 주해 본문을 한 장의 HTML 아티팩트로 조립해 게시하고, 링크를 채팅에 낸다.** 이 사용자는 코드 초심자라 *채팅 텍스트 한 덩어리*로 받으면 이해가 어렵다는 판정이 서 있다(상세는 하네스 변경이력) — 렌더된 아티팩트(절 구분·mermaid 그림·코드 하이라이트)가 같은 내용을 읽기 쉽게 만든다. **매체만 바뀐다 — 담기는 내용과 그 규칙은 아래 「채팅 요약」·`annotation.md`가 그대로 정본이다.**

- **`Artifact` 도구로 게시한다.** 아티팩트는 mermaid를 네이티브로 렌더하므로 §0 지도는 ` ```mermaid ` 코드펜스로 넣는다(채팅 ASCII 대신 — 채팅 매체 규칙은 §0 형식 참조). 페이지 작성 전 `artifact-design` 스킬을 읽는다.
- **담는 것**: ① 요약 생략 불가 항목(아래 「채팅 요약」 ①~⑤ 전부 — 파일·해시 포함) ② §0 자리 지도(mermaid) ③ 지금 배울 핵심 개념 5~7 ④ 파일별 주해 본문(배경→직관→흐름 문답·★함정 표시 — 입자·어휘·문답 규칙은 `annotation.md` 그대로). **코드블록은 기본 접힘** — 줄 단위는 승격 시 채팅에서 편다.
- **상호작용은 아티팩트가 아니라 채팅이다(병행).** 퀴즈 5문항·틀린 함수 줄 승격·'여기 자세히'·막힘 재설명은 전부 채팅에서 한다 — "문서에만 적으면 도달하지 않는다"를 메우는 것이 이 채팅 층이다(`annotation.md` 「진행 방식」). **아티팩트는 읽기 표면, 채팅은 이해 검증.** 승인은 여전히 상호작용을 다 돈 뒤 1회(제시 순서 7)이며 대상은 순서 3에서 계산한 해시다.
- **게이트 노트(옵시디언 §0~§3)와 다르다** — 아티팩트는 *게이트 시점의 읽기 표면*이고, 게이트 노트는 *볼트 복습·부채 상환 기록*이다. 둘 다 남긴다(아티팩트는 세션에 게시, 노트는 순서 8에서 작성).

## 채팅 요약

이 요약은 **아티팩트 최상단 블록**이다(제시 순서 5, 위 「게이트 설명 아티팩트」) — 핵심 요약 + §0 자리 지도 + 핵심 개념 + 아래 생략 불가 항목. **승인 요청은 여기 붙이지 않는다**(상호작용을 다 돈 뒤 제시 순서 7).

### 생략 불가 항목

① 변경/테스트 파일 전체 목록 + 각 해시 ② 커버되지 않는 AC·경계 **전부** ③ 의심 지점·트레이드오프 **(산출자 자기 신고)** ④ **새로 만든 것 + 더 게으른 대안** ⑤ **독립 리뷰 결과**(게이트②만)

⑤는 ③의 한계를 메운다. **③은 피고인의 자백이다** — 산출자가 자기 약점을 스스로 고른다. ⑤는 code-critic이 5-b에서 낸 지적이고, 둘을 **따로** 적어야 사용자가 무엇이 자기 신고이고 무엇이 독립 지적인지 구분한다. 형식: `차단 0건 확인 + 경고·참고를 **처리함/미룸**으로 갈라 각 한 줄(미룸은 사유 병기) + 03b 경로`. **5-b는 경량·기본 모두 돈다**(규모 분기 개정) — 지적이 하나도 없었으면 **"차단·경고·참고 0건"을 명시**한다. 빈칸은 0건과 구별되지 않는다.

**⑤가 판단 요청이 아니라 보고인 이유**: 지적을 고치는 5-c가 이 게이트보다 **앞에** 있다(동결 전이라 고쳐도 재제시가 없다). 그래서 사용자가 보는 것은 "고칠까요?"가 아니라 "이건 고쳤고 이건 미뤘습니다"다. **사용자는 여전히 되돌릴 수 있다** — "미룬 걸 지금 고쳐"라고 하면 5-c로 돌아가 처리하고 게이트②를 새 차수로 제시한다(승인 전이라 재제시가 아니다). 미룸 사유를 빠뜨리면 그 되돌림 판단이 불가능해진다.

④의 앞 절반은 재구현 방지 장치이자 **implementer가 탄 사다리 2번 칸("이 리포에 이미 있나")의 결과 보고**다. 새 export를 추가했으면 `신규 {심볼} — {어디를} 찾았으나 없음`을 그대로 올린다. **이름이 다른 같은 기능은 grep으로 안 잡히므로**(`hasStoredToken`이 있는데 `isLoggedIn`을 새로 만드는 경우), 기계가 못 잡는 중복을 사람이 게이트에서 잡는 유일한 지점이다. 기존 것을 활용했으면 그것도 한 줄로 적는다(`기존 활용: compareVersion`) — 무엇을 재사용했는지가 코드베이스 학습이 된다.

**④의 뒤 절반은 ponytail이 낸 "더 게으른 대안"이고, 이건 보고가 아니라 선택지다.** lite의 계약 자체가 *"대안을 한 줄로 제시하고 고르는 것은 사용자"*인데, implementer가 03에 대안을 적고 "선택은 사용자 몫"이라고 끝내면 그 문장은 **03에서 죽는다** — 게이트에 올라오지 않은 선택지는 선택지가 아니다(실측 1건, 상세는 하네스 변경이력). 형식: `대안 {한 줄} · 채택/미채택 · 사유 한 줄`. **대안이 없었으면 "대안 없음"을 명시한다** — 빈칸은 *안 나옴*과 *안 옮김*을 구별하지 못하고, 배선 유지 판정이 정확히 그 구별 위에 서 있다. ⑤와 달리 이건 **판단 요청이다**: 사용자가 대안을 고르면 5-c로 돌아가 적용하고 게이트②를 새 차수로 제시한다(승인 전이라 재제시가 아니다).

요약에서 불리한 내용이 빠지면 **"읽지 않은 승인"의 대상이 요약이 된다.** scribe가 [기록]에서 채팅 요약 ↔ 게이트 노트의 이 항목들 일치 여부를 대조·기록한다.

### 형식 예시


## 대화 주해 → `annotation.md`

주해 **본문은 HTML 아티팩트로 읽고, 이해 검증(퀴즈·줄 승격·막힘)은 대화로 한다**(병행 — 위 「게이트 설명 아티팩트」). 진행 방식·내용 규칙·기본 입자(함수)·줄 단위 승격·인라인 형식·비용 규약이 전부 **`annotation.md`**에 있다 — 제시 순서 5(아티팩트 조립)·6(채팅 상호작용)에 들어가기 직전 그 파일을 읽어라.

여기 남는 것은 게이트 절차와의 접점 둘뿐이다:

- **퀴즈는 게이트당 1회**이고 그 출제·이해부채 등재는 아래 「이해 체크와 이해부채」가 정본이다.
- **중간 확인은 승인이 아니다.** `ㄱㄱ`가 20번 나와도 승인은 대화를 다 돈 뒤 1회이며, 대상은 제시 순서 3에서 계산한 해시다.

## 이해 체크와 이해부채

사용자의 이해 속도가 사이클의 실제 병목이다. 게이트가 "읽지 않은 승인"으로 변질되면 인지 부채가 쌓인다.

### 이해 체크 — 객관식 5문항 (제시 순서 6의 마지막)

**게이트당 5문항, 객관식, 대화를 다 돈 뒤 승인 요청 전에 낸다.** 자기보고(§3 막힌 줄)는 *막혔다고 느낀 것*만 잡고 **막혔다고 느끼지 못한 것은 원리적으로 못 잡는다** — 이 장치가 메우는 구멍이 정확히 거기다. 그리고 이 문항들이 **줄 단위 승격을 발동시킨다**(`annotation.md` 「줄 단위 승격」) — 틀린 문항이 곧 예산을 쓸 자리다.

- **파일당이 아니라 게이트당 5문항이다.** 파일별로 내면 문항이 두 자릿수가 되어 받는 쪽이 통째로 접는다. **받는 비용이 우회 비용보다 싸야 실제로 치러진다** — 이 장치의 성패가 거기 달려 있다.
- **객관식으로 낸다 — 서술형 금지.** 선택지 3~4개 + 고른 뒤 정오와 이유를 함께 준다. 서술형은 답하는 데 문장을 써야 해서 건너뛰어지고, 대화형에서는 그 문장이 이후 모든 턴에 재과금된다.
- **난도는 중간, 함정은 금지.** *"실질을 이해해야 답할 수 있되 말장난은 아닌 것."* 문항이 트집이면 사용자는 장치를 신뢰하지 않고, 신뢰를 잃은 장치는 형식만 남는다.
- **출제 지점은 이미 있는 산출물에서 도출한다** — 오케의 인상이 아니다. 아래에서 5개를 고른다:
  1. `02a`의 **★장치·함정 목록** (★가 비면 애초에 반려 사유라 이 재료는 항상 있다)
  2. `03`의 **의심해야 할 지점**
  3. `03b` code-critic 지적
  4. 3-a 맹점 훑기에서 사용자가 **"모른다"**고 한 개념이 쓰인 자리
  5. 이 사이클에 처음 등장하는 API·패턴
- **축을 섞는다 — 전부 한 종류로 내지 마라.** 역질문이 **전부 "왜 이렇게 짰나" 한 종류**였던 실측이 있다(상세는 하네스 변경이력). 설계 근거는 이해의 입구지 전부가 아니다.

  | 축 | 무엇을 재나 | 어디서 |
  |---|---|---|
  | **근거축** | 왜 이렇게 짰나 | 신규 함수 · 새 개념이 등장하는 자리 |
  | **구조축** | 흐름·위치·경계 — 코드 *사이*의 관계 | 이음매·경계 · 기존 파일 수정 |

  **구조축이 최소 1문항은 나와야 한다.** 함수 하나하나의 "왜"를 다 알아도 그 사이의 관계는 안 생긴다. 출제 기준은 **"흐름 절을 다 들어도 바로 안 나오고, 코드 사이의 관계를 봐야 답할 수 있는 것"**이다:
  - *"이 단언 한 줄을 지우면 어떤 잘못된 구현이 통과하나?"* (심판 강도)
  - *"`saveTokens` 호출을 지우면 어느 테스트가 빨개지나? 왜?"* (추적)
  - *"네이버를 추가하면 어느 상자가 늘고 어느 상자는 그대로인가?"* (위치)

- **선택지를 고르기 어렵게 만든다.** 정답이 늘 가장 길거나 늘 같은 자리에 있으면 **읽지 않고도 맞힌다** — 그러면 이 장치는 통과율만 만들고 이해는 안 만든다. **선택지 길이를 서로 비슷하게 맞추고, 5문항의 정답 위치를 흩는다.**
- ⚠️ **정답 선택지에 서식을 주지 마라 — 볼드·기울임·이모지 전부.** 출제자가 초안에서 정답을 표시해 두고 그대로 내보내면 **문항이 통째로 무효**가 되고, 무효는 사후에 되돌릴 수 없다(재출제해야 한다). 실측 1건에서 5문항 중 **4문항이 무효**가 됐다(상세는 하네스 변경이력). **내보내기 직전에 선택지 줄에 `**`가 있는지 훑는다** — 이것이 이 규칙의 실행 형태다.
  - 사용자가 굵은 쪽을 **안 고른** 문항은 실질 오답으로 처리하고 설명·승격을 수행한다(서식이 아니라 내용을 읽었다는 증거다). 굵은 쪽을 고른 문항은 **결과를 신뢰할 수 없으므로 깨끗한 형태로 재출제**한다.
  - 출제 사고는 게이트 노트 결과 절과 원장에 **그대로 적는다.** 숨기면 `3회 연속 전문 정답이면 뗀다`는 유지 판정이 오염된다.
- **전부 답할 의무는 없다 — 막히는 것만 짚어 주면 된다.** 사용자가 막히면 승인 보류가 아니라 **그 함수를 줄 단위로 펼치는 트리거**다.
- **"막힘·오답"과 "무응답"을 가른다 — 부채 등재는 앞의 둘만이다.** 몰이해를 표했거나 틀린 문항만 이해부채 후보로 올린다. 무응답은 **[메모리]의 넘겨짚기 금지 규칙과 다르다**: 저기서 기본값이 등재인 것은 사용자가 *몰이해를 표했을 때*이고, 여기 무응답은 읽었는지조차 모르는 상태다.
- **결과를 게이트 노트 결과 섹션에 기록한다** — `이해 체크 5문항 중 {M}답변 · 오답 {W} · 막힘 {K} · 줄 승격 {P}`. 기록 없는 체크는 형해화를 관찰할 수 없다.

*유지 판정: 3사이클 관찰 — **3회 연속 전문 정답이면 이 장치를 뗀다**(부채가 장부상 부채였다는 뜻). 반대로 **게이트당 답변이 1문항 이하로 유지되면** 5문항도 비싼 것이므로 2문항(근거축·구조축 각 1)으로 줄인다. 한 문항이라도 오답·막힘이 나오는 동안은 유지한다.*

### 이해부채 수집 (즉시 영속)

사용자가 "동작은 믿고 승인하지만 아직 이해 못 함"을 표한 항목 + 이해 체크에서 막힌 항목은 **게이트 기록 시점에 즉시** 게이트 노트 결과 섹션과 00_gates.md에 쓴다 — [기록]까지 세션 메모리에만 두면 에스컬레이션 중단·세션 사망 시 부채가 증발한다([기록]의 scribe는 건별 노트화·정리만 담당).

- **기본값은 등재 (넘겨짚기 금지)**: 사용자가 개념 몰이해를 표하면(질문·"모르겠다"·이해 체크 막힘 포함), 명시적 "이해했다" 발화가 없는 한 **기본값은 부채 등재**다. 재설명 후 "이해했겠지"로 넘겨짚어 부채를 소멸시키는 것을 금지한다(넘겨짚기 = "읽지 않은 승인"의 재생산). 애매하면 되묻고, 되물을 수 없는 상태(세션 종료 등)면 등재 쪽으로 판정한다.
- **개념 노트 링크 (재방문 학습)**: 부채 등재 시 그 개념의 설명을 담은 개념 노트(`TripPilot/개념/{개념명}.md`)를 생성·링크한다(obsidian-second-brain 개념 규칙). 부채 노트는 장부일 뿐이라, 재방문 시 배울 설명이 없으면 상환이 구조적으로 불가능하다. 설명이 가장 신선한 등재 시점에 오케스트레이터가 담고, [기록]에서 scribe가 정리·확정한다.
- **장부화 필터**: 다음 작업을 막을 항목만 부채로 올리고, 나머지는 개발로그의 "참고 개념" 목록으로 격하한다.
- **파산 차단**(미상환 10건 초과 시 정리 세션 선행)은 **[메모리] 단계 규칙이라 SKILL.md에 있다** — 이 파일은 게이트 시점에 읽히므로 여기 두면 판정 시점을 이미 지나쳤다.

## 학습자 모드

이 사용자는 코드 초심자다(TS/Jest/RN 테스트 코드를 아직 유창하게 못 읽음). "이해가 병목" 원칙을 이 수준에 맞춰 구체화한다.

- **학습자 톤**: 게이트 노트·주해도 서브 에이전트와 같은 학습자 톤을 쓴다. 톤 3원칙과 주입 시점은 SKILL.md "서브 에이전트 호출 공통"에 있다(1단계부터 적용되므로 이 파일에 두면 늦다). 프로필 근거: [[user-learner-profile]].
- **"지금 배울 핵심 개념 5~7개" 선정**: 이번 게이트에 등장하는 개념 중 **처음 등장하거나 사용자가 아직 이해를 표명하지 않은 것**을 오케스트레이터가 판단해 채운다. 이미 설명했고 사용자가 이해를 표명한 개념은 재설명하지 않고 한 줄 리마인드 + `[[개념 노트]]` 링크만 단다.
  - 판단 근거: 미상환 이해부채 목록(`TripPilot/이해부채/`)과 기존 개념 노트의 존재 여부 — 부채로 남아 있으면 아직 모르는 것이고, 개념 노트가 이미 있으면 최소한 한 번은 설명한 것이다.
  - **이 선정이 곧 배경 절 ①단(초심자 배경)의 개인화다**(`annotation.md` 「기본 입자 — 함수」). 아는 것은 링크로 줄어들고 모르는 것만 펼쳐지므로, 배경 절이 매번 같은 길이로 반복되지 않는다.
- **분할 제시는 기본 강제 아님**: 필요 시 차수 분할을 재사용하되 기본값은 아니다.

## 경량 사이클의 이해 체크

규모 분기로 게이트①·②를 1회 통합 제시할 때에도 **깎는 것은 절차뿐이다**. 원장 기록 형식(해시·red 로그)과 이해 체크의 두 축은 그대로 유지한다 — 규모와 무관한 중량 사이클은 하네스 우회를 부르고 우회는 전 장부에 구멍을 내지만, 반대로 제시만 합치고 검토 축까지 비우면 경량화가 그대로 이해부채로 되돌아온다(경량 통합 제시 사이클의 부채가 **전부** 통합 이해 체크에서 발생한 실측 1건, 상세는 하네스 변경이력):

- **대화 주해 전수는 경량에서도 그대로다**(파일이 1~2개라 자연히 짧게 끝난다). 통합 제시라도 **게이트①축**(이 테스트가 무엇을 보장하나)과 **게이트②축**(구현이 그 테스트를 어떻게 통과시키나) **양쪽을 다 돈다** — 한 축만 돌고 승인하면 통합의 이득을 이해부채로 되돌려받는다.
- **퀴즈도 통합 1회 5문항이고, 두 축이 모두 나와야 한다.** 통합 제시라고 5문항을 한 축으로 몰면 안 걷은 축이 그대로 부채가 된다 — 경량 사이클의 부채가 **전부** 통합 이해 체크에서 발생한 실측이 이 자리를 가리킨다.
- 답변·오답·막힘을 축별로 구분해 기록해, 한 축만 막혀도 그 축을 부채로 등재한다.
- **근거축/구조축과 충돌하면 게이트①②축 배분이 우선한다.** §0 지도는 경량 사이클에서도 생략하지 않는다(5줄이라 부담이 아니고, 통합 제시일수록 지도가 더 필요하다).
