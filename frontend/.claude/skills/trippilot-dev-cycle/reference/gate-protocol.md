# 게이트 프로토콜

게이트①·② 제시 직전에 읽는다. 제시 순서, 원장 기록 형식, 해시 규약, 노트·요약 형식, 이해부채 수집이 여기 있다.

## 목차

- **게이트 제시 순서** — 복사해 체크하는 8단계 (먼저 읽어라)
- 게이트 원장 (00_gates.md) — 기록 형식·해시 규약·red 로그·무효화·재제시
- 게이트 노트 — 4계층 구조(§0 자리 지도) + **막힌 줄만** 남기는 §3
- 채팅 요약 — 생략 불가 항목 + 형식 예시
- **대화 주해** — 선별 단위(덩어리)·중요도 2단·건너뛰기 권한·비용 규약 (제시 순서 6)
- 이해 체크와 이해부채 — 등재 기준·개념 노트 (문항 출제는 대화로 대체·보류)
- 학습자 모드 — 학습자 프로필 주입·핵심 개념 선정
- 경량 사이클의 이해 체크 — 통합 제시 시 두 축 유지

## 게이트 제시 순서

응답에 복사해 체크하며 진행한다. **순서를 바꾸면 원장이 오염된다** — 특히 3(해시 계산)과 7·8(원장 먼저, 노트 나중).

```
게이트{①|②}-{n} 제시:
- [ ] 1. 산출자(test-designer/implementer)가 prettier 통과 — 해시 박제의 전제
- [ ] 2. [게이트①만] verify-gates 사전 점검 → **환경 지문 기록** → red 1회 실행 → 로그 확보
- [ ] 3. shasum으로 파일 해시 계산 — 이 시점 값이 곧 승인 대상
- [ ] 4. 등장 개념 선정 → "지금 배울 핵심 개념 5~7개" (3-a 맹점 훑기에서 "모른다"고 한 것이 1순위)
- [ ] 5. 채팅에 요약 제시 (생략 불가 항목 + §0 자리 지도 + 핵심 개념)
- [ ] 6. **대화 주해** — 덩어리 지도 제시 → 정독/흐름 단별 진행, 막힘은 그 자리에서 재설명 (아래 "대화 주해")
- [ ] 7. 승인 요청 → 승인 수령 → 00_gates.md 기록 (발화 인용 + 3에서 계산한 해시 전사)
- [ ] 8. 게이트 노트 작성 (§0~§2 + **막힌 줄만** §3 · 승인/반려 · 이해부채)
```

- **3 → 7의 해시는 같은 값이어야 한다.** 승인 후 재계산 금지 — 승인은 "그 해시의 파일"에 대한 승인으로 정의된다.
- **7이 8보다 먼저다.** 둘이 갈라지면 원장이 단독 권위다 — 노트는 열람용 스냅샷이고 원장은 감사 대상이라, 세션이 죽으면 살아남아야 하는 쪽이 원장이다.
- 반려되면 6으로 돌아가지 않고 산출 단계([테스트 작성]/[구현])로 복귀한 뒤 1부터 새 차수로 다시 탄다.

## 게이트 원장 (00_gates.md)

게이트 승인은 `_workspace/{cycle-id}/00_gates.md`에 즉시 영속한다. **이 파일에 기록 없는 게이트는 산출물 파일이 있어도 미통과다** — 파일 존재는 "작성됨"이지 "승인됨"이 아니다.

### 기록 형식

```
## 게이트① — {승인 시각}
- 승인 발화: "{사용자 원문 인용}"
- 승인 테스트 파일: {경로}: {shasum 해시} ...
- red 실행 로그: (원문, 또는 "미실행 — 사유")
- 환경 지문: {있는 설정 파일 목록 + node/pnpm 버전}
## 게이트② — {승인 시각}
- 승인 발화: "{사용자 원문 인용}"
- 승인 구현 파일: {경로}: {shasum 해시} ...
```

필수 필드는 셋이다:
- **사용자 승인 발화 원문 인용**
- **제시 시점 해시의 전사** — 제시 시점에 계산해 채팅 요약에 명시하고(채팅이 사후 수정 불가능한 유일한 채널이다), 원장에는 그 값을 옮겨 적는다
- **환경 지문**(게이트①만) — 제시 시점에 존재한 검증 설정의 목록. verify-gates §0 사전 점검을 돌면서 확인한 것을 그대로 적는다:

  ```bash
  ls package.json jest.config.js jest.integration.config.js eslint.config.js tsconfig.json \
     .prettierrc .prettierignore 2>/dev/null
  node -v; pnpm -v
  ```

  **이 필드가 없으면 "도구를 부숴 FAIL을 판정 불능으로 세탁하는 경로"가 열린다** — qa-verifier가 검증 시점에 이 목록과 대조해, 게이트① 때 있던 설정이 사라졌으면 실행 불가가 아니라 **FAIL + 변조 에스컬레이션**으로 판정한다(verify-gates "0. 사전 점검").

  **prettier 설정 2개가 목록에 있는 이유**(2026-07-21 추가): verify-gates §0이 prettier 설정을 실행 전제로 요구하는데 지문에는 빠져 있어, 게이트① 이후 지워도 대조에 안 걸리는 구멍이 있었다. 특히 `.prettierignore` 소실은 `pnpm format`이 `.claude/`·정본 md까지 재포맷해 **승인 해시를 무더기로 흔든다**.

### 해시 규약

- **포맷 후 상태로 박제한다.** 산출자가 게이트 제시 전 prettier를 통과시키는 것이 의무다.
- 검증 단계의 포매터는 멱등이므로 승인 해시를 바꾸지 않는다 — **해시 대조 불일치는 전부 진짜 변조다.**

### red 로그 (게이트①)

- 제시 전에 오케스트레이터가 테스트를 직접 1회 실행해 첨부한다. **verify-gates §0 사전 점검을 선행**한다.
- 설정 부재로 인한 전멸은 red가 아니라 `"미실행 — 사유"`로 기록한다.
- 로그에는 실행 시점 테스트 파일 해시를 병기한다.
- [검증]에서 qa-verifier가 red 소급 확인을 **로그 유무와 무관하게 상시** 수행한다.

### 검증 판정 append

- 판정·차수·시각을 원장에 append한다(qa-verifier 수행). **FAIL 카운터의 정본은 원장이다.**

### 무효화와 재제시

- **부분 재실행 시 하류 무효화**: 특정 게이트를 다시 열면 그 이후 게이트의 원장 항목에 `무효화(사유·시각)` 행을 append한다. **기존 행 수정 금지.** 해시 대조·재개 판별은 항상 각 게이트의 **최신 유효 섹션** 기준이다.
- **게이트② 재제시 조건**: 검증 FAIL 수정 루프로 코드가 게이트② 승인 해시와 달라진 채 검증을 PASS하면, [기록]으로 가기 전에 게이트②를 재제시한다(변경 diff와 사유 포함).
  - 이 해시 대조는 **qa-verifier의 04 필수 항목**이다 — 오케스트레이터 자체 판단 금지.
  - 재제시가 반려되면 [구현] 수정 루프로 복귀한다.

## 게이트 노트

게이트 제시는 **채팅에서 읽고 채팅에서 승인한다**(제시 순서 5~7). 옵시디언 노트는 그 뒤에 **남길 것만** 담는 복습 기록이다 — 대화는 `/clear`로 사라지고, 이해부채 상환 때 다시 읽을 곳은 볼트뿐이다.

- 경로: `TripPilot/게이트/{YYYY-MM-DD} {cycle-id} 게이트{①|②}-{n}.md` (`게이트 템플릿` 구조)
- `n`은 제시 차수. **재제시는 새 차수로, 덮어쓰기 금지.** 무효가 된 구 노트에는 `무효(재제시됨)`를 표기한다.
- 승인/반려 결과는 노트의 결과 섹션에 갱신한다(순서 8).
- Obsidian MCP 불가 시 채팅에 전문을 제시하고 폴백을 명시한다.
- `_workspace/`의 02/03은 파이프라인 정본으로 그대로 유지된다 — 게이트 노트는 열람·학습용 스냅샷이다.

### 4계층 구조 (위에서부터 읽다가 멈출 수 있게)

노트는 **위에서부터 읽다가 멈출 수 있게** 쌓는다 — §0 지도만 봐도 자리가 잡히고, 아래로 갈수록 세부다.

**네 계층은 게이트 노트 한 파일 안의 네 섹션이다** — 노트를 쪼개지 않는다. 사용자는 노트 하나만 열면 지도부터 막힌 줄 기록까지 다 있다.

| 계층 | 내용 | 분량 | 반복 단위 |
|---|---|---|---|
| **§0. 이번 변경이 붙는 자리** | 만진 조각의 흐름도 — 어느 파일이 무엇을 부르나 + **다음 수 한 줄** | 5~10줄 + 1 | 노트당 1회 |
| §1. 지금 배울 핵심 개념 | 이번 게이트의 신규/미소화 개념만 | 5~7개 | 노트당 1회 |
| §2. 파일별 요약 | 이 파일이 무엇을 하는가 | 파일당 3~5줄 | **변경 파일마다** |
| §3. 막힌 줄 기록 | 대화에서 막힌 줄 + 재설명 | **막힌 줄만** | **변경 파일마다** |

"파일별"은 노트가 파일마다 쪼개진다는 뜻이 아니라, 변경된 소스 파일 수만큼 §2·§3 안에서 덩어리가 반복된다는 뜻이다(파일 4개 → 한 노트 안에 §2 4덩어리, §3 4덩어리).

#### §0 — 왜 필요한가

**대화 주해는 조각 단위라, 조각을 다 알아도 지도는 안 생긴다.** "이 파일이 왜 여기 있고 누가 부르나"는 어느 줄에도 안 적혀 있다. §0이 그 한 층 위를 담당한다. **그래서 §0은 대화보다 먼저 제시된다**(제시 순서 5) — 지도 없이 줄부터 걸으면 걸을 때마다 길을 잃는다.

**전체 지도가 아니라 이번에 만진 조각만.** 재료는 `docs/structure.md`와 03 구현 노트에 이미 있다 — 옮겨 그린다.

**형식은 매체를 따른다** — 채팅에는 아래 같은 ASCII 흐름도를, **게이트 노트에는 `mermaid` 코드펜스**를 쓴다(옵시디언이 렌더하므로 복습 때 그림으로 보인다). **채팅에 mermaid 소스를 내지 마라** — 터미널은 다이어그램을 렌더하지 않아 소스가 그대로 보인다. 그리는 것은 한 번이고 옮겨 적을 때 형식만 바꾼다.

```
[소셜 로그인 버튼]  features/auth/ui/
       │ 누름
       ▼
[useSocialLogin]    features/auth/hooks/     ← 화면은 여기까지만 안다
       │
       ▼
[makeAuthorize]     features/auth/lib/       ← 갈래 3개
       │              · fake 토글 on   → 가짜 응답
       │              · off + clientId → ▼ 동적 import
       │              · off + 설정없음 → throw (INV-4)
       ▼
[realAuthorize]     features/auth/lib/       ★ expo-auth-session을 아는 유일한 파일
       │
       ▼
[oauthConfig]       features/auth/lib/       ← env에서 clientId 읽기

이번에 새로 생긴 것: realAuthorize.ts · oauthConfig.ts
다음 수: 네이버 추가 = realAuthorize에 갈래 1개 + oauthConfig에 clientId 1줄. 화면·훅은 안 바뀐다.
```

**흐름도 끝에 "다음 수" 한 줄을 단다.** 흐름도는 *지금 무엇이 있나*까지만 답한다. 게이트의 이해가 승인으로 끝나지 않고 **다음 사이클의 아이디어**가 되려면 지도 위에서 다음 수가 보여야 한다 — 어느 상자를 늘리면 되나, 무엇을 바꾸면 어디가 깨지나. 이 한 줄이 게이트에서 유일하게 *승인이 아니라 참여*를 겨냥하는 자리다(나머지 장치는 전부 "이번 변경을 이해했나"를 잰다).

- **흐름도의 재서술이면 뺀 것과 같다.** *"realAuthorize가 expo-auth-session을 안다"*는 그림에 이미 있다 — 값은 *"네이버를 넣으면 여기 한 상자만 늘고 화면은 안 바뀐다"* 쪽에 있다. **무엇이 안 바뀌는지를 같이 적을 때** 경계가 드러난다.
- 재료는 §0을 그리면서 이미 다 나와 있다 — 새로 조사하지 마라. 안 보이면 *"이 지도로는 다음 수가 안 보인다"*가 정직한 값이고, 그건 지도가 덜 그려졌다는 신호다.

*유지 판정: 6사이클 관찰 — 이 줄이 비어 있거나 흐름도 재서술뿐인 건이 4사이클 이상이면 뗀다(지도만으로 다음 수가 안 나온다는 뜻이라, 고칠 곳은 이 줄이 아니라 §0의 재료다). 실적은 scribe가 개발로그에 `다음 수 — 기재 n / 재서술 n`으로 남긴다.*

§0은 **구조축 역질문의 출제 근거**이기도 하다(아래 "이해 체크").

- §1 본문은 **개념 순서의 서술형**이다 — 왜 이 설계인가 → 데이터/화면 흐름 → 의심해야 할 지점·트레이드오프 순. 원시 diff는 코드 순서지 개념 순서가 아니라서 이해 비용이 높다.
- **노트가 둘 이상이 되는 경우는 분할 제시뿐이다**: 30분 초과로 차수를 나누면 `게이트①-1`·`게이트①-2`가 되고 **각 노트가 다시 4계층을 갖는다**.
- 예상 열람 30분 초과면 차수 장치를 재사용해 분할 제시한다.
- 분량이 이해를 이기게 두지 마라 — 다만 **이기지 못하게 하는 수단은 요약의 질이지 주해의 누락이 아니다.**

### 주해 내용 규칙

주해가 **어디서** 이뤄지는지는 아래 "대화 주해"에 있다. 이 절은 **무엇을 담는가**만 규정한다.

- **이번 사이클에서 사람이 작성한 코드는 빠짐없이 전 줄이 대상이다.** 빈 줄·닫는 괄호처럼 설명할 것이 없는 줄을 제외하면 **어느 덩어리에도 안 속한 줄이 남아서는 안 된다** — 전수인 것은 **커버리지**이고, 2단으로 갈리는 것은 **밀도**다(아래 "중요도 2단"). 건너뛰기는 사용자가 명시할 때만이다(아래 건너뛰기 권한).
- **정독 덩어리**는 코드를 펼쳐 **한 줄마다** "무엇을 하는가 + 왜 필요한가"를 단다 — 중요한 자리에서는 줄 단위가 그대로 유지된다. **흐름 덩어리**는 코드를 펼치지 않고 **설명 문장이나 흐름도**로 "이 덩어리가 무엇을 하는가"만 전한다. 줄 단위로 내려가지 않는다.
- 처음 볼 가능성이 있는 개념(RN/Expo API·TanStack 패턴·fast-check 문법 등)은 이름만 쓰지 말고 **한 줄 개념 설명을 병기**한다.
- import·타입 선언·설정 객체처럼 "당연해 보이는" 줄도 **덩어리에서 빠지지 않는다** — 흐름 단으로 내려갈 수는 있어도 목록에서 사라지지는 않는다. 초심자에게 당연한 줄은 없고, **무엇을 자세히 볼지 판단하는 주체는 읽는 사람이어야 한다.**
- **02/03 산출물 문서에는 전줄 주해를 쓰지 않는다.** 같은 주해를 문서·노트·대화 세 번 생산하던 것을 대화 1회 + 막힌 줄 저장 1회로 줄인 것이다(2026-07-26 전환, 상세는 하네스 변경이력). 02/03은 파이프라인 정본으로 남되 담는 것은 매핑·설계 근거·변경 설명이다.
- **그래서 주해 재료는 02a의 설계 근거와 02/03의 매핑·변경 설명이다.** 산출자가 주해 본문을 미리 쓰지 않으므로 *"쓴 사람이 이유를 안다"*는 이점이 사라지고, **근거가 02a에 없으면 대화에서 오케가 추정하게 된다.** 02a의 ★장치·함정 목록이 비면 반려 사유인 이유가 여기서 하나 더 늘어난다.
- **리포의 실제 소스 파일에는 학습 주해를 넣지 않는다.** 리포 주석은 "주변 밀도 준수 + 코드가 말할 수 없는 제약만" 규칙 그대로.
  - 주해가 들어가는 곳은 **02/03 문서와 게이트 노트의 코드블록**이다. 이 코드블록은 읽으라고 만든 **학습용 사본**이라 주석을 달아도 리포 파일은 변하지 않는다.
  - 이 둘을 헷갈려 실제 `.ts`/`.tsx` 파일에 학습 주석을 커밋하면 **게이트② 해시가 달라져 재제시 사유가 된다.** 사본에만 단다.
- **유일한 예외 — 도구 생성 파일**: 스캐폴딩 템플릿·orval 생성물 등 사람이 쓰지 않은 코드는 생성 명령·설정만 주해·해시 대상으로 하고 생성물 자체는 목록+건수만 기재한다. 사람이 그 생성물을 손댔다면 손댄 줄은 주해 대상으로 복귀한다.

### 중요도 2단 — 정독 / 흐름

전수 커버리지는 그대로 두고 **밀도만 가른다.** 사용자가 코드를 실제로 확인할 자리에 시간을 몰아주기 위한 것이다.

| 단 | 무엇을 내나 | 대화 비용 |
|---|---|---|
| **정독** | 코드블록을 펼치고 **한 줄씩** `// ▸` 주해 | 줄당 1~3줄 |
| **흐름** | 코드를 안 펼친다 — 설명 한 줄 **또는 흐름도 한 장** | 덩어리당 1~5줄 |

**판정은 오케의 취향이 아니라 이미 있는 산출물에서 도출한다.** 아래 중 하나라도 걸리면 정독, 아니면 흐름:

1. `02a`의 **★장치·함정 목록**에 걸린 덩어리 (★가 비면 애초에 반려 사유라 이 재료는 항상 있다)
2. `03`의 **의심해야 할 지점**
3. `03b` code-critic 지적 (차단·경고·참고 전부)
4. 3-a 맹점 훑기에서 사용자가 **"모른다"**고 한 개념이 쓰인 자리
5. 이 사이클에 처음 등장하는 API·패턴

**흐름 단은 문장이거나 그림이다.** 덩어리 하나로 끝나면 설명 한 줄, **연속한 흐름 덩어리가 3개를 넘거나 갈래가 지면 문장 대신 흐름도 한 장**을 그린다 — 줄줄이 나열한 문장보다 그림 하나가 짧고, 흐름 단의 목적은 "이 구간이 어떻게 이어지나"이지 각 줄이 무엇이냐가 아니다.

- **§0 자리 지도와 겹치지 않는다** — §0은 **파일 사이**(어느 파일이 무엇을 부르나), 흐름 단 그림은 **파일 안**(이 파일의 덩어리들이 어떻게 이어지나)이다. 형식은 §0의 매체 규칙을 그대로 따른다 — 채팅은 ASCII, 게이트 노트는 `mermaid`.
- 그림에도 **정독 덩어리가 어디인지 표시**한다(`★`). 사용자가 지금 어느 지점을 자세히 볼 참인지 그림 위에서 보이게 하기 위한 것이다.

**덩어리 지도를 먼저 낸다.** 파일 주해를 시작할 때 덩어리 목록 + 각 단 + **정독 사유(위 1~5 중 어느 것)**를 한 번에 제시하고, 사용자가 승격·격하한다. 이것이 건너뛰기 권한의 확장이다 — 기본값이 근거 기반일 때만 조정 권한이 의미를 갖는다. 사유를 안 적으면 지도가 오케의 인상 평가로 내려앉는다.

**흐름으로 내려간 코드도 승인 대상이다.** 게이트 해시는 파일 전체에 걸리므로 **대화에서 눈으로 보지 않은 줄도 승인에 포함된다** — 이것이 밀도를 가르는 대가다. 완충은 셋뿐이다: 판정 근거 1~5가 위험한 자리를 정독으로 끌어올리고, code-critic(5-b)·qa-verifier(6-a)가 코드를 따로 보고, 사용자가 언제든 승격할 수 있다. **셋 다 못 잡는 종류의 결함이 흐름 단에서 나오면**(계약·경계면처럼 테스트도 리뷰도 통과하는데 사람 눈에만 걸리는 것) 그것이 판정 근거를 넓히라는 신호다 — 아래 유지 판정의 "승격 요청"과 같은 장부에 센다.

**흐름 덩어리도 승격된다.** "여기 자세히"라고 하면 그 자리에서 정독으로 올린다. 승격 요청은 판정 근거가 좁다는 신호라 세어 둔다.

*유지 판정: 3사이클 관찰 — 양쪽으로 센다. **정독 비율이 8할을 넘으면** 근거 1~5가 변별을 못 하는 것이므로 목록을 좁힌다(2·3을 "재현 시나리오가 있는 것만"으로). 반대로 **사용자 승격 요청이 사이클당 3건 이상이면** 근거가 좁은 것이므로 넓힌다. 실적은 게이트 노트 §2에 `덩어리 — 정독 n / 흐름 n / 승격 n`으로 남긴다.*

### 주해 형식 — 인라인 (대화·§3 공통)

**코드 바로 아래에 설명을 붙인다.** 표로 빼거나 뒤에 몰아쓰지 않는다 — 코드와 설명 사이 거리가 벌어지면 눈이 왕복한다. 대화에서 정독 덩어리를 제시할 때와 §3에 막힌 줄을 남길 때 같은 형태를 쓴다.

- 주해 주석은 **`// ▸` 마커**로 시작한다. 원본 코드에 없는 줄임을 한눈에 구분하기 위해서다.
- 설명이 길면 이어지는 줄은 `//` 들여쓰기로 잇는다.
- "준비(Arrange)→실행(Act)→단언(Assert)" 3동작이 어디인지 보이게 쓴다(학습자 모드).
- 파일 제목 줄에 그 파일이 무엇을 하는지 한 줄을 먼저 단다.

대화에서는 **정독 덩어리 안을 한 줄씩** 이 형태로 내고, §3에는 그중 **막힌 줄만** 남긴다(아래는 파일 전체를 펼친 예시 — 대화에서는 한 번에 한 줄이고, 흐름 덩어리는 코드블록 없이 설명이나 흐름도로 지나간다):

````markdown
**`hooks/useAuthBootstrap.test.ts`** — 앱 시작 시 저장된 토큰으로 로그인 상태를 복원하는지 검증
> 아래 코드블록은 학습용 사본이다(`// ▸`는 설명용 추가 줄). 해시 대상은 주석 없는 원본 파일.

```ts
import { renderHook, waitFor } from '@testing-library/react-native'
// ▸ RNTL(React Native Testing Library)에서 도구 두 개를 가져온다.
//   renderHook = 화면을 그리지 않고 훅만 따로 실행해 보는 도구
//   waitFor = 비동기 결과가 나올 때까지 기다려 주는 도구

import { useAuthBootstrap } from './useAuthBootstrap'
// ▸ 검증 대상 훅을 가져온다 — 이 테스트가 무엇을 겨냥하는지 선언하는 줄

it('저장된 토큰이 있으면 인증 상태로 복원된다', async () => {
// ▸ 테스트 1건을 연다. 따옴표 안 문장이 곧 이 테스트가 보장하는 내용이다.
//   async = 이 안에서 "기다림(await)"을 쓰겠다는 표시. 토큰 읽기가 비동기라 필요하다.

  const store = makeTokenStore({ accessToken: 'tok_1' })
  // ▸ 준비(Arrange) — 토큰이 들어 있는 가짜 저장소를 만든다.
  //   실제 SecureStore를 쓰면 기기에 뭐가 저장돼 있느냐에 따라 결과가 흔들린다.

  const { result } = renderHook(() => useAuthBootstrap(store))
  // ▸ 실행(Act) — 가짜 저장소를 넣어 훅을 돌린다.
  //   DI(의존성 주입) = 훅이 저장소를 스스로 만들지 않고 인자로 받게 해서,
  //   테스트에서 가짜로 갈아끼울 수 있게 한 구조.

  await waitFor(() => expect(result.current.settled).toBe(true))
  // ▸ 부트스트랩이 끝났다는 신호(settled)가 true가 될 때까지 기다린다.
  //   기다리지 않으면 아직 로딩 중인 상태를 단언하게 된다.

  expect(result.current.isAuthed).toBe(true)
  // ▸ 단언(Assert) — 인증된 상태로 복원됐는지 확인한다. 이 테스트의 결론.
})
```
````

원본 코드는 한 줄도 바꾸지 않는다 — **주석 줄만 사이에 끼워 넣는다.** 원본과 대조하면 `// ▸` 줄만 빼면 실제 파일과 정확히 같아야 한다.

## 채팅 요약

채팅 요약은 **대화 주해에 들어가기 전의 지도**다 — 핵심 요약 + §0 자리 지도 + 핵심 개념 + 아래 생략 불가 항목. **승인 요청은 여기 붙이지 않는다**(대화를 다 돈 뒤 제시 순서 7).

### 생략 불가 항목

① 변경/테스트 파일 전체 목록 + 각 해시 ② 커버되지 않는 AC·경계 **전부** ③ 의심 지점·트레이드오프 **(산출자 자기 신고)** ④ **새로 만든 것 + 더 게으른 대안** ⑤ **독립 리뷰 결과**(게이트②만)

⑤는 ③의 한계를 메운다. **③은 피고인의 자백이다** — 산출자가 자기 약점을 스스로 고른다. ⑤는 code-critic이 5-b에서 낸 지적이고, 둘을 **따로** 적어야 사용자가 무엇이 자기 신고이고 무엇이 독립 지적인지 구분한다. 형식: `차단 0건 확인 + 경고·참고를 **처리함/미룸**으로 갈라 각 한 줄(미룸은 사유 병기) + 03b 경로`. 리뷰를 생략했으면(경량 사이클) **"리뷰 생략"을 명시**한다 — 빈칸은 0건과 구별되지 않는다.

**⑤가 판단 요청이 아니라 보고인 이유**: 지적을 고치는 5-c가 이 게이트보다 **앞에** 있다(동결 전이라 고쳐도 재제시가 없다). 그래서 사용자가 보는 것은 "고칠까요?"가 아니라 "이건 고쳤고 이건 미뤘습니다"다. **사용자는 여전히 되돌릴 수 있다** — "미룬 걸 지금 고쳐"라고 하면 5-c로 돌아가 처리하고 게이트②를 새 차수로 제시한다(승인 전이라 재제시가 아니다). 미룸 사유를 빠뜨리면 그 되돌림 판단이 불가능해진다.

④의 앞 절반은 재구현 방지 장치이자 **implementer가 탄 사다리 2번 칸("이 리포에 이미 있나")의 결과 보고**다. 새 export를 추가했으면 `신규 {심볼} — {어디를} 찾았으나 없음`을 그대로 올린다. **이름이 다른 같은 기능은 grep으로 안 잡히므로**(`hasStoredToken`이 있는데 `isLoggedIn`을 새로 만드는 경우), 기계가 못 잡는 중복을 사람이 게이트에서 잡는 유일한 지점이다. 기존 것을 활용했으면 그것도 한 줄로 적는다(`기존 활용: compareVersion`) — 무엇을 재사용했는지가 코드베이스 학습이 된다.

**④의 뒤 절반은 ponytail이 낸 "더 게으른 대안"이고, 이건 보고가 아니라 선택지다.** lite의 계약 자체가 *"대안을 한 줄로 제시하고 고르는 것은 사용자"*인데, implementer가 03에 대안을 적고 "선택은 사용자 몫"이라고 끝내면 그 문장은 **03에서 죽는다** — 게이트에 올라오지 않은 선택지는 선택지가 아니다(실측 1건, 상세는 하네스 변경이력). 형식: `대안 {한 줄} · 채택/미채택 · 사유 한 줄`. **대안이 없었으면 "대안 없음"을 명시한다** — 빈칸은 *안 나옴*과 *안 옮김*을 구별하지 못하고, 배선 유지 판정이 정확히 그 구별 위에 서 있다. ⑤와 달리 이건 **판단 요청이다**: 사용자가 대안을 고르면 5-c로 돌아가 적용하고 게이트②를 새 차수로 제시한다(승인 전이라 재제시가 아니다).

요약에서 불리한 내용이 빠지면 **"읽지 않은 승인"의 대상이 요약이 된다.** scribe가 [기록]에서 채팅 요약 ↔ 게이트 노트의 이 항목들 일치 여부를 대조·기록한다.

### 형식 예시

```markdown

**파일 · 해시**

- 토큰 만료 경계(정확히 0초)는 미검증

**의심 지점·트레이드오프**

정독 덩어리는 **한 줄씩**, 흐름 덩어리는 설명이나 흐름도로 지나갑니다.
막히면 `막힘`, 알면 `ㄱㄱ`, 흐름 덩어리도 "여기 자세히"라고 하면 펼칩니다.
```

승인 요청은 대화를 다 돈 뒤에 한다 — 요약 끝에 붙이지 않는다.

## 대화 주해 (제시 순서 6)

**주해는 문서가 아니라 대화로 전달한다**(2026-07-26 전환, 사용자 판정: 문서 한 덩어리로 받으면 이해가 어렵다). 근거는 3-a 맹점 훑기와 같다 — **문서에만 적으면 도달하지 않는다.** 노트에 있던 전줄 주해가 실제로 다 읽히는지는 끝까지 확인되지 않았고, 대화는 막힌 지점이 **즉시** 드러난다.

- **덩어리는 선별의 단위이고, 주해의 단위는 단마다 다르다.** 코드를 의미 단위 덩어리(3~8줄)로 갈라 정독/흐름을 매긴 뒤 — **정독 덩어리는 그 안을 한 줄씩** 걷고(원래 규칙 그대로), **흐름 덩어리는 통째로 설명 하나나 흐름도 한 장**으로 끝낸다. import 묶음·타입 선언·`describe`/`it` 껍데기도 각각 한 덩어리로 친다 — 포함은 되고, 대개 흐름 단으로 간다(내용 규칙은 위 "주해 내용 규칙", 밀도는 "중요도 2단").
- **건너뛰기 권한은 사용자에게 있다.** "여기부터 N줄은 안다"고 하면 그 구간은 확인 없이 넘어간다. 이것은 전수 원칙의 예외가 아니라 그 원칙의 실행 형태다 — **무엇을 건너뛸지 판단하는 주체는 읽는 사람**이고, 기본값이 전수일 때만 그 권한이 성립한다.
- **반복 덩어리는 묶어 제안한다** — `이 3덩어리는 앞과 같은 형태입니다, 한꺼번에 넘어갈까요?` 오케가 임의로 접지 말고 **묶음 여부를 물어본다.**
- **앞 줄을 재인용하지 않는다.** 되돌아보기는 사용자가 요청할 때만.
- **막히면 그 자리에서 재설명한다.** 해소되면 계속, 안 되면 이해부채 등재 후보다(등재 기본값은 아래 "이해부채 수집" 그대로 — 넘겨짚기 금지).
- **중간 확인은 승인이 아니다.** `ㄱㄱ`가 20번 나와도 승인은 대화를 다 돈 뒤 **1회**이며, 대상은 제시 순서 3에서 계산한 해시다. 원장 규약("*그 해시의 파일*에 대한 승인")이 그대로 적용된다.

*이 조정은 다른 해법으로 실행됐다 — 조건이 예정한 "단위 격하"(모든 줄을 덩어리로 묶기) 대신 **대상을 가르는 쪽**을 택했다. 정독 덩어리 안은 여전히 한 줄씩이고, 덩어리는 정독/흐름을 매기는 선별 단위로만 쓴다. 전수 커버리지와 건너뛰기 권한은 그대로다. 다음 판정 조건은 위 "중요도 2단"에 있다.*

### 비용 규약

대화형의 비용은 내가 보내는 줄이 아니라 **매 턴 재전송되는 대화 히스토리**다(N번째 턴이 앞의 N-1턴을 다시 읽는다). 그래서 절약은 전부 히스토리를 짧게 유지하는 데서 나온다:

- **전용 세션에서 한다.** 사이클 본 세션은 게이트 시점에 브리프·설계·구현 노트·툴 결과가 쌓여 있고, 그 프리픽스가 왕복마다 곱해진다. `/clear` 후 RESUME.md + 대상 파일만 들고 시작한다.
- **파일 1개 = 대화 1회차.** 끝나면 `/clear`. 여러 파일을 한 세션에 몰면 뒷 파일이 앞 파일의 대화를 계속 재전송한다(차수 분할 장치를 그대로 재사용한다).
- **한 파일은 끊지 않고 끝낸다.** 중간에 오래 쉬면 캐시가 식어 그때까지의 히스토리 전체를 정가로 다시 낸다.
- **사용자 응답은 짧을수록 싸다** — `ㄱㄱ` 한 글자가 최적이고, 긴 문장은 이후 모든 턴에서 재과금된다. 막힘도 `막힘` + 한 단어.
- **주해는 정독에서 줄당 1~3줄, 흐름 덩어리는 통째로 1~5줄**(흐름도 포함). 대화형에서 주해 길이는 곧 히스토리 누적 속도이고, **절약은 정독을 줄여서가 아니라 흐름으로 내려보내서 얻는다.**
- **02/03에 전줄 주해를 쓰지 않는다**(위 "주해 내용 규칙") — 3중 생산 제거가 가장 큰 절약이다.

## 이해 체크와 이해부채

사용자의 이해 속도가 사이클의 실제 병목이다. 게이트가 "읽지 않은 승인"으로 변질되면 인지 부채가 쌓인다.

### 이해 체크 — **보류 (대화로 대체)**

**파일당 1문항 출제는 대화 주해 도입으로 보류 상태다** — 모든 줄을 걸으며 막힘을 확인하고 나서 다시 문항을 내는 것은 중복이다. 폐지 여부는 미결이고, 아래 규칙은 **덩어리 단위로 격하했을 때**(위 조정 조건) 되살릴 원문으로 남긴다. 답변률 졸업 조건도 그때까지 카운터가 멈춘다.

- **승인 대상 파일마다 1문항씩** 낸다. **파일 목록이 곧 문항 목록이다** — 게이트 노트 §2·§3가 파일마다 반복되는데 문항이 2개뿐이면 나머지 파일은 안 읽고도 승인이 통과한다. 문항을 같은 단위로 붙여야 노트 열람이 답변의 전제가 된다.
- **출제 기준**: 채팅 요약만으로는 답할 수 없고 **그 파일의 §2·§3를 읽어야 답할 수 있는 지점**에서 낸다.
- **한 줄로 낸다** — `파일명 — 한 문장 (축)`. 파일이 많으면 목록이 길어지므로 문항 자체가 짧아야 훑을 수 있다.
- **축을 파일 성격에 맞춘다 — 전부 한 종류로 내지 마라.** 전수 확인에서 역질문이 **전부 "왜 이렇게 짰나"(설계 근거) 한 종류**였다(실측, 상세는 하네스 변경이력). 설계 근거는 이해의 입구지 전부가 아니다.

  | 축 | 무엇을 재나 | 어떤 파일에 |
  |---|---|---|
  | **근거축** | 왜 이렇게 짰나 | 신규 파일 · 새 개념이 등장하는 파일 |
  | **구조축** | §0 지도 위의 흐름·위치·경계 | 이음매·경계 파일 · 기존 파일 수정 |

  **구조축이 최소 1문항은 나와야 한다.** 파일이 많을수록 근거축으로 쏠리기 쉬운데, 파일 하나하나의 "왜"를 다 알아도 그 사이의 관계는 안 생긴다.

  구조축 출제 기준은 **"주해를 다 읽어도 바로 안 나오고, 코드 사이의 관계를 봐야 답할 수 있는 것"**이다:
  - *"이 그림에서 `expo-auth-session`을 아는 파일이 하나뿐인데, 두 개가 되면 무엇이 깨지나?"* (경계)
  - *"`saveTokens` 호출을 지우면 어느 테스트가 빨개지나? 왜?"* (추적)
  - *"네이버를 추가하면 이 그림에서 어느 상자가 늘고 어느 상자는 그대로인가?"* (위치)

  세 번째 유형이 특히 값싸다 — 답하려면 지도를 직접 그려봐야 하고, 답하고 나면 다음 사이클의 작업 방식이 눈에 들어온다.
- **전부 답할 의무는 없다 — 막히는 것만 짚어 주면 된다.** 사용자가 막히면 승인 보류가 아니라 **해당 부분을 더 설명하는 트리거**로 쓴다.
- **"막힘"과 "무응답"을 가른다 — 부채 등재는 막힘만이다.** 사용자가 몰이해를 표한 문항만 이해부채 후보로 올린다(막힌 답이 가장 확실한 부채 신호다). **무응답 문항을 전부 등재하지 마라** — 파일별 출제라 게이트 한 번이 두 자릿수 문항을 내고, 그걸 다 등재하면 파산 상한(10건)을 한 게이트에서 넘겨 장부가 무너진다. 다만 무응답은 **[메모리]의 넘겨짚기 금지 규칙과 다르다**: 저기서 기본값이 등재인 것은 사용자가 *몰이해를 표했을 때*이고, 여기 무응답은 읽었는지조차 모르는 상태다.
- **답변 요지 + 답변률을 게이트 노트 결과 섹션에 기록한다** — `이해 체크 {N}문항 중 {M}답변 · 막힘 {K}`. 기록 없는 체크는 형해화를 관찰할 수 없고, **무응답이 쌓이는 것 자체가 이 장치의 유지 판정 재료다.** *유지 판정: 6사이클 관찰 — 게이트당 답변이 1문항 이하로 유지되면 파일별 출제를 접고 대표 2문항(근거축·구조축 각 1)으로 되돌린다.*

### 이해부채 수집 (즉시 영속)

사용자가 "동작은 믿고 승인하지만 아직 이해 못 함"을 표한 항목 + 이해 체크에서 막힌 항목은 **게이트 기록 시점에 즉시** 게이트 노트 결과 섹션과 00_gates.md에 쓴다 — [기록]까지 세션 메모리에만 두면 에스컬레이션 중단·세션 사망 시 부채가 증발한다([기록]의 scribe는 건별 노트화·정리만 담당).

- **기본값은 등재 (넘겨짚기 금지)**: 사용자가 개념 몰이해를 표하면(질문·"모르겠다"·이해 체크 막힘 포함), 명시적 "이해했다" 발화가 없는 한 **기본값은 부채 등재**다. 재설명 후 "이해했겠지"로 넘겨짚어 부채를 소멸시키는 것을 금지한다(넘겨짚기 = "읽지 않은 승인"의 재생산). 애매하면 되묻고, 되물을 수 없는 상태(세션 종료 등)면 등재 쪽으로 판정한다.
- **개념 노트 링크 (재방문 학습)**: 부채 등재 시 그 개념의 설명을 담은 개념 노트(`TripPilot/개념/{개념명}.md`)를 생성·링크한다(obsidian-second-brain 개념 규칙). 부채 노트는 장부일 뿐이라, 재방문 시 배울 설명이 없으면 상환이 구조적으로 불가능하다. 설명이 가장 신선한 등재 시점에 오케스트레이터가 담고, [기록]에서 scribe가 정리·확정한다.
- **장부화 필터**: 다음 작업을 막을 항목만 부채로 올리고, 나머지는 개발로그의 "참고 개념" 목록으로 격하한다.
- **파산 차단**(미상환 10건 초과 시 정리 세션 선행)은 **[메모리] 단계 규칙이라 SKILL.md에 있다** — 이 파일은 게이트 시점에 읽히므로 여기 두면 판정 시점을 이미 지나쳤다.

## 경량 사이클의 이해 체크

규모 분기로 게이트①·②를 1회 통합 제시할 때에도 **깎는 것은 절차뿐이다**. 원장 기록 형식(해시·red 로그)과 이해 체크의 두 축은 그대로 유지한다 — 규모와 무관한 중량 사이클은 하네스 우회를 부르고 우회는 전 장부에 구멍을 내지만, 반대로 제시만 합치고 검토 축까지 비우면 경량화가 그대로 이해부채로 되돌아온다(경량 통합 제시 사이클의 부채가 **전부** 통합 이해 체크에서 발생한 실측 1건, 상세는 하네스 변경이력):

- **대화 주해 전수는 경량에서도 그대로다**(파일이 1~2개라 자연히 짧게 끝난다). 통합 제시라도 **게이트①축**(이 테스트가 무엇을 보장하나)과 **게이트②축**(구현이 그 테스트를 어떻게 통과시키나) **양쪽 줄을 다 걷는다** — 한 축만 걷고 승인하면 통합의 이득을 이해부채로 되돌려받는다.
- 답변·막힘을 축별로 구분해 기록해, 한 축만 막혀도 그 축을 부채로 등재한다.
- **문항 출제 규칙은 보류 상태다**(위 "이해 체크 — 보류") — 아래 두 줄은 덩어리 단위로 격하했을 때 되살릴 원문이다.
- **근거축/구조축과 충돌하면 게이트①②축 배분이 우선한다.** §0 지도는 경량 사이클에서도 생략하지 않는다(5줄이라 부담이 아니고, 통합 제시일수록 지도가 더 필요하다).
