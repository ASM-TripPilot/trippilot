이 파일은 repo-traps.md에서 경로별로 쪼갠 함정이다 — 해당 경로 만질 때만 로드된다.

- **react-query 캐시 알림을 읽는 통합테스트는 `act` 직후 곧바로 `result.current`를 읽지 마라 — flush 헬퍼로 순서를 기다린다.** `notifyManager`가 알림을 `setTimeout(cb, 0)`으로 예약해서 보내므로, `act` 직후 즉시 읽으면 재렌더 전(구값)을 관측할 확률적 flake가 난다(원인 확증 TRIP-884, `useVisitCheck.integration.test.tsx` 11/20 재현 — 개념 [[테스트 워커 강제종료 flake (원인 미상)]]). 의심되면 `beforeAll`에 `notifyManager.setScheduler((cb) => setTimeout(cb, 5))`로 재현해 확인한다. **TRIP-953(2026-09-25)이 같은 모양인 `savedStays`(stay)·`savedPlaces`(explore)·`useToggles`(notification)·`useAdjustVisitTimes`(record, 이 파일) 4곳에 처방을 확산했고, 로컬 중복이던 헬퍼를 `src/test-support/flushNotifications.ts`(공용, path-scoped 잠금은 각 파일 인라인 유지 — 공용 setup으로 옮기면 108파일에 번진다)로 승격했다.** ⚠️ **롤백 단언(기대값=호출 전 값) 앞의 flush는 지워도 파일이 green으로 남는다** — 그 flush가 없으면 잠금 아래서 롤백 심판이 조용히 공허해지는데(TRIP-953 03b 경고-1, savedPlaces/savedStays/useToggles 각 파일에 3자리씩), 기계가 못 잡아 "필요 없어 보이는 줄"로 정리하면 사고가 난다. ⚠️ **`waitFor(() => expect(hitCount).toBe(1))`은 "정확히 1회"를 보장하지 않는다** — 문(gate)은 응답만 막고 요청 카운트는 막지 않으므로, `waitFor`가 첫 시도에 1을 보고 끝난 뒤 지연된 두 번째 요청이 카운트를 올려도 못 잡는다(TRIP-953 03b가 02a ★5의 "문이 막아 1을 못 넘는다" 서술이 틀렸음을 실측 정정 — HEAD도 원래 못 잡던 것이라 후퇴는 아니다).
- **월 그리드 순수 함수는 `shared/date/monthGrid.ts`가 유일한 정본이다** — TRIP-575(j07 여행 캘린더)가 `daysInMonth`·`firstWeekdayOfMonth`·`shiftMonth`·`isDateInRange`·`buildMonthGrid`를 신설했고(`formatKoreanDate` 승격 선례 따름), **TRIP-639로 `features/stay/model/stayDates`·`features/trip/model/tripDatePicker`의 옛 사본 4개(재수출 shim 없이)가 삭제돼 세 벌 → 한 벌로 통합됐다.** 새 record 파일을 만들 때는 `shared/date/monthGrid.ts`부터 확인한다. record 안에서 이 산술을 다시 짜면 다시 세 벌째가 된다.
- **`recordsCalendar.ts`의 `formatTripDateRange`·`nightsLabel`은 TRIP-808로 `entities/trip/lib/{formatTripPeriod,formatNights}.ts`로 바이트 그대로 이관됐다** → 이 파일이 `buildPastTripCards` 내부에서도 이관 함수를 쓰므로 옛 자리는 `import`+로컬 재수출(순수 `export … from`이 아님 — 안 그러면 내부 호출이 깨진다. shim 제거는 TRIP-810 정리 범위 밖으로 확정돼 남아 있다 — `layer-entities.md` entities/trip 절). `PastTripList.tsx`는 `entities/trip/ui/PastTripRow`에 위임하며 완성 full `testID` 리터럴(`record-calendar-past-trip-{id}`)을 그대로 조립해 넘긴다 — 선재 `recordsCalendarStructure` G3 앵커가 재조준 없이 산다.
- **`GET /trips/{tripId}/change-log`는 여전히 미개통이다(생산자 없음, 항상 빈 목록) — 변경 이력은 `GET /trips/{tripId}/records` 응답의 `TripRecord.changes[]`에 임베드돼 내려온다.** TRIP-570 티켓 원문은 "TRIP-275로 `/change-log`가 개통돼 실제 변경 행이 내려온다"고 적었으나, origin/develop `openapi.yaml`(1405–1424행)은 그대로 "생산자 없어 항상 빈 목록, 붙이지 말 것"이다. **정정(TRIP-953 [기록], `--stale` 실측): j02 비교 화면은 TRIP-769로 화면·훅·조립 함수·세그 컴포넌트째 전부 삭제됐다(`features/record/model`·`ui`에 j02 전용 코드 0).** 옛 j02는 `/records`만 호출하고 standalone `/change-log`는 붙이지 않았다 — 붙였다면 항상 빈 배열만 받았을 것. `aidlc` 정본 BR-U5-29 원문("읽을 진입점이 아직 없다, G-U5-12")도 이 드리프트만큼 낡아 있으나 3-a 사용자 선택 없이는(자율 세션) 미반영 상태다(관측만, 2026-09-01). 다음에 변경 이력을 조회하는 화면을 또 만들 때 티켓 설명만 보고 `/change-log`를 잡으면 이 함정을 재발한다 — 실제 데이터 원천은 `/records.changes[]`다.
