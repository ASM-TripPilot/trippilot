GitHub Actions가 AWS에 아무 권한도 없다면 첫 IAM Role을 스스로 만들 수 없다. AWS 계정 관리자가 최초 OIDC provider와 bootstrap Role을 준비한 뒤, bootstrap workflow가 환경별 state 버킷과 일반 배포 Role을 만든다. 이후의 배포는 수명이 짧은 OIDC 자격증명을 사용한다. 저장소에 장기 AWS 액세스 키를 넣는 절차가 아니다. GitHub Actions의 AWS OIDC 인증.

CloudFormation을 먼저 사용하는 이유는 Terraform이 사용할 원격 backend 자체가 아직 없기 때문이다. bootstrap stack과 앱 Terraform state를 따로 두면 앱 인프라 변경과 state 보관소의 수명도 분리된다. 현재 state 버킷은 versioning·암호화·TLS·public 차단을 적용하고 terraform.tfstate.tflock을 이용해 동시 수정을 막는다.

강사 사전 준비 순서

  1. 계정에 token.actions.githubusercontent.com OIDC provider가 있는지 확인한다. audience는 sts.amazonaws.com이며 기존 provider를 중복 생성하지 않는다.
  2. bootstrap trust 예제와 권한 예제를 실제 계정·리전·환경에 맞춰 검토한다. 저장소는 현재 ASM-TripPilot/trippilot을 기준으로 검증하므로 포크 실습은 관련 trust와 저장소 검사도 일관되게 바꿔야 한다.
  3. GitHub Settings → Environments에서 dev, prd를 명시적으로 만든다. DEV는 develop, PRD는 main branch만 허용하도록 설정한다.
  4. 아래 표의 bootstrap 변수를 등록하고 AWS bootstrap (manual) workflow를 환경별로 실행한다. workflow 파일은 GitHub 저장소의 기본 branch에도 존재해야 Run workflow 버튼을 사용할 수 있다.
  5. Summary의 DeploymentRoleArn을 같은 Environment의 AWS_ROLE_ARN에 등록한다. state 버킷과 Role이 환경과 계정에 맞는지 확인한다.
  6. ACM에서 API 도메인 인증서를 요청하고 DNS 검증을 끝낸다. EKS/NLB와 같은 AWS 계정·리전의 인증서 ARN과 API hostname을 등록한다.

일반 Role ARN이나 도메인은 비밀값이 아니므로 Environment Variables에 넣는다. 외부 서비스 API 키는 이후 Secrets Manager에 넣는다. PRD에는 사용 가능한 GitHub 요금제·저장소 공개 범위에서 required reviewers와 self-review 방지를 설정한다. 해당 보호 기능의 제공 범위는 계정 플랜에 따라 다르므로 실제 Settings에서 확인한다. GitHub Environment 보호 규칙과 제공 범위.

승인이 검사하는 지점

현재 deploy job 전체가 Environment를 참조하므로 reviewer 승인은 그 job이 시작하기 전이다. 그 job 안에서 Terraform plan과 apply가 연속 실행된다. 이 승인은 방금 만들어진 plan 파일을 읽고 누른 승인이 아니다. 운영에서는 별도 plan 실행의 결과와 대상 SHA를 먼저 검토하고 apply 실행을 승인하되, apply 실행은 새 plan을 만든다는 점까지 확인해야 한다. 정확히 검토한 plan을 승인 후 적용하려면 job 분리, 동일 SHA 고정, 제한된 plan 저장·전달과 만료 정책을 추가 설계해야 한다.

OIDC subject가 repo:ASM-TripPilot/trippilot:environment:prd 형태이면 environment는 제한하지만 branch나 workflow 파일명까지 증명하지는 않는다. Environment branch 보호와 workflow 코드 리뷰를 함께 적용한다. bootstrap Role은 배포 Role의 권한을 만들 수 있으므로 초기 준비가 끝난 뒤 접근을 제한한다. DEV·PRD를 같은 계정에 두어도 이름·state·VPC 분리만으로 완전한 계정 수준 격리가 생기지 않는다.
