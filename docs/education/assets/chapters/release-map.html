Kubernetes 용어 네 가지

Pod는 하나 이상의 컨테이너를 함께 실행하는 기본 단위다. Deployment는 원하는 Pod 복제본 수를 유지하고 새 버전으로 교체하는 rollout을 관리한다. Service는 Pod가 교체되어 주소가 바뀌어도 사용할 수 있는 안정적인 접근 주소를 제공한다. Namespace는 한 클러스터 안에서 리소스 이름의 범위를 나눈다. 이 저장소는 로컬과 각 AWS 클러스터에서 trippilot namespace를 사용하며 같은 namespace 이름이라고 해서 같은 클러스터를 가리키는 것은 아니다.

로컬 개발에서는 코드 수정 결과를 빠르게 확인하는 것이 중요하다. 운영에서는 누가 어떤 코드를 어떤 권한으로 배포했는지 추적하고 데이터와 비밀값을 유지하면서 실행 중인 앱을 교체해야 한다. 두 환경은 Kubernetes라는 공통 API를 사용하지만 이미지 전달, 데이터베이스, 외부 접근과 인증 방식이 다르다.

여기서 Terraform은 네트워크와 AWS 서비스를 준비하고 Helm은 준비된 EKS 위의 Deployment·Service·ConfigMap 등을 구성한다. EKS Auto Mode는 Helm이 만든 LoadBalancer Service를 관찰하여 NLB를 생성한다. 인프라만 apply한 시점에는 아직 앱 Service와 NLB가 없을 수 있다. Terraform, Kubernetes, EKS Auto Mode가 각각 관리하는 대상을 구분해야 변경 위치를 찾을 수 있다. EKS Auto Mode의 NLB 생성 동작.

PRD의 Redis 3노드는 primary와 replica를 합한 수다. Redis 인프라와 TLS 설정은 준비하지만 현재 backend에는 실제 Redis adapter 구현이 없어 캐시 사용까지 완성된 것은 아니다. 선택형 embedding은 기본 비활성이고 켜면 별도 이미지와 약 5GiB 메모리 요청이 추가된다. 임베딩 서비스와 pgvector 테이블 생성만으로 지식 데이터가 자동 적재되지는 않는다.

모바일 Expo 앱은 별도 앱 배포 절차를 따른다. AWS workflow는 frontend 이미지를 빌드하거나 배포하지 않는다. 로컬 nginx frontend는 통합 확인용 정적 스텁이다. AWS에서 모바일 앱을 연결하려면 앱이 사용하는 API base URL을 DEV·PRD의 HTTPS 도메인에 맞게 설정해야 한다.
