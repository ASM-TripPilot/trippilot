문제 1. validate job에서 export RESULT=ok를 실행했다. 다른 deploy job에서 $RESULT를 읽을 수 있는가? 전달 방법을 쓰라.

해설 보기

자동으로 전달되지 않는다. 같은 job에서도 별도 shell step 사이에는 단순 export가 유지되지 않는다. 같은 job의 다음 step이면 GITHUB_ENV에 쓰고 다른 job이면 GITHUB_OUTPUT으로 step output을 만들고 job의 outputs에 매핑한 뒤 needs.validate.outputs.RESULT로 읽는다.

문제 2. PRD required reviewer가 승인했다. “리뷰어가 Terraform plan의 변경사항까지 승인했다”라고 실행 기록에 써도 되는가?

해설 보기

현재 구조에서는 그렇게 단정할 수 없다. 승인은 deploy job 시작 전이고 plan은 이후에 생성된다. 사전 plan 실행을 검토했더라도 apply 실행은 새 plan을 만든다는 점까지 기록해야 한다.

문제 3. mode=plan, deploy_application=true로 실행하면 ECR 이미지와 Helm 배포가 수행되는가?

해설 보기

수행되지 않는다. 입력 검증 스크립트가 실제 배포 여부를 mode == 'apply' and requested_deploy로 계산하므로 step output은 문자열 'false'가 된다. 후속 앱 관련 step은 이 output을 검사한다.

문제 4. id-token: write를 추가했는데 AWS가 AccessDenied를 반환한다. 이 설정을 contents: write로 바꾸면 해결되는가?

해설 보기

그렇지 않다. OIDC 토큰 발급 여부, 토큰 subject·audience와 Role 신뢰 조건의 일치, Role의 AWS API 권한, 계정·리전 및 조직 정책을 확인한다. GitHub 콘텐츠 쓰기 권한은 AWS 리소스 변경 권한과 별개다.

문제 5. 새 DEV 배포를 세 번 요청했다. cancel-in-progress: false이므로 세 번 모두 차례로 배포된다고 설명해도 되는가?

해설 보기

안 된다. 현재 설정은 실행 중인 작업을 새 요청으로 취소하지 않지만 기본 pending 슬롯의 기존 요청은 새 요청으로 교체될 수 있다. GitHub 실행 화면에서 실제로 남아 있는 요청을 확인해야 한다.

문제 6. AWS validate가 통과했다. 해당 commit의 AI 생성 API 테스트까지 통과했다고 볼 수 있는가?

해설 보기

아니다. AWS validate는 배포 코드·chart·mock Terraform과 제한된 backend 종료 설정 검사를 수행한다. AI의 생성 API smoke는 별도 ai-ci.yml에 있다. 배포 대상 commit에 대해 필요한 CI가 실행되고 성공했는지 별도로 확인한다.

이 강의의 코드 기준: AWS 배포 workflow, bootstrap workflow, 입력 검증 스크립트, 배포 운영 가이드, bootstrap 가이드. 공식 문서 확인일: 2026-09-19. 다음 강의에서는 이 실행 구조를 로컬 Kubernetes → DEV → PRD 작업 흐름에 연결한다.
