문항 1. dev.tfvars를 prd.tfvars로 바꾸기만 하면 환경이 완전히 분리되는가?
정답과 해설

아니다. 환경별 state bucket, AWS 역할, GitHub Environment, 리소스 이름과 네트워크도 맞아야 한다. 강한 격리가 필요하면 AWS 계정도 나눈다. tfvars는 설정 값을 고를 뿐이다.

문항 2. .terraform.lock.hcl을 지우면 다른 실행의 S3 잠금이 풀리는가?
정답과 해설

아니다. 이 파일은 provider 버전·해시 기록이다. state 실행 잠금은 S3의 .tflock 객체가 담당한다. 두 lock의 대상과 목적이 다르다.

문항 3. 현재 Terraform 코드만 apply하면 api.example.com이 바로 서비스되는가?
정답과 해설

아니다. 앱 이미지와 Helm 배포, ACM 인증서 발급·검증, Service가 만드는 NLB, 도메인의 DNS 연결이 필요하다. 현재 브랜치는 Cloudflare와 ACM 발급을 Terraform으로 자동화하지 않는다.

문항 4. mock 테스트가 통과하면 실제 AWS 배포 성공이 보장되는가?
정답과 해설

아니다. 코드에 표현된 설계 조건은 검증하지만 실제 IAM·SCP·quota·리전 지원·네트워크·앱 연결은 별도 검증 대상이다. mock 검증, 원격 plan, 실제 적용, 배포 후 연결 확인을 단계별로 수행한다.

다음 수업으로 연결: 사람이 로컬에서 위 명령을 실행하는 대신, GitHub Actions가 어떤 이벤트로 시작하고 어느 runner에서 어떤 권한으로 각 단계를 수행할지 작성한다. 다음 장에서 Terraform 검증과 AWS 변경을 서로 다른 job으로 나누는 이유를 살펴본다.
