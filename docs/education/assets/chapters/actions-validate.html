aws-deploy.yml에는 validate와 deploy 두 job이 있다. 앞 job에는 OIDC 토큰 요청 권한이 없고 뒤 job은 needs: validate로 연결된다. 먼저 무엇을 테스트하는지, 무엇까지 보장하지 않는지 읽는다.

validate 순서실제 명령 / 설정확인하는 내용
1. 실행 도구checkout, Python 3.13, Terraform 1.13.5, Helm 3.19.0CI에서 사용할 도구 버전 준비
2. 배포 계약infra 및 deploy/eks Python 테스트, coverage 합산입력 검증, workflow 계약, 비밀값·렌더링 로직 회귀
3. 정책·chartbootstrap 테스트, chart 테스트, DEV/PRD helm lint --strict권한·리소스 구조와 chart 렌더링 규칙
4. 조건부 backendapply + 앱 배포일 때 Java 25 준비, AsyncConfigTestbackend 종료 설정의 제한된 회귀 검증
5. Terraformfmt -check, init -backend=false, validate, test형식·구문과 mock provider 기반 DEV/PRD 구조

infra/.coveragerc는 infra/scripts와 deploy/eks를 측정하며 fail_under = 80을 둔다. 첫 coverage 실행 후 두 번째 실행에 --append를 붙여 결과를 합친다. 이 80%는 지정한 Python 배포 코드 범위의 기준이다. Java·AI·frontend 전체 테스트 커버리지가 80%라는 뜻은 아니다.

helm lint의 이미지·DB 주소·인증서 ARN에는 예시값을 넣는다. 템플릿이 요구하는 필드를 갖췄는지 점검할 수 있지만 실제 DB나 인증서의 존재는 확인하지 않는다. Terraform 테스트도 mock_provider "aws"를 사용하므로 AWS에 EKS를 만드는 검사가 아니다. init -backend=false는 원격 state 연결을 생략하며 provider 패키지 다운로드에는 인터넷이 필요할 수 있다.

검증 범위 해석: 이 job의 성공이 backend·AI·frontend 전체 CI 완료를 자동으로 보장하지 않는다. backend 검사는 AsyncConfigTest로 한정되고 AWS workflow가 다른 CI workflow의 성공 상태를 조회하거나 needs로 연결하지 않는다. 실제 배포 전에는 대상 commit의 기존 CI 결과를 확인해야 한다. CI가 경로 필터로 생략된 경우도 성공과 구분해 판단한다.
