배포 실패는 한 종류가 아니다. 권한 오류, 인프라 생성 오류, 이미지 pull 오류, 앱 시작 오류와 외부 DNS 오류를 서로 구분해야 한다. 먼저 GitHub 실행에서 처음 실패한 step을 찾고 그 step이 변경하기 전과 후의 상태를 확인한다. 실패했으니 모든 것이 처음 상태로 돌아갔다고 가정하지 않는다.

로그는 공유 전에 민감한 값을 확인하고 kubectl get secret -o yaml로 Secret 전체를 제출하지 않는다. 현재 DB 초기화와 smoke 도구는 Job을 끝에서 정리하므로 완료 뒤 Job이 남아 있지 않을 수 있다. 실제 장애 관측을 강화하려면 민감정보를 제외한 Job 상태·종료 원인·이벤트를 정리 전에 수집하는 작업도 별도로 설계해야 한다.

Helm atomic이 되돌리는 범위

기존 release의 Helm upgrade 실패에는 이전 revision으로 되돌리는 동작이 적용되지만 최초 설치에는 돌아갈 이전 revision이 없다. 더구나 현재 내부 smoke는 Helm 성공 다음의 별도 step이다. smoke step에서만 실패했다면 앞서 성공한 Helm 변경이 자동으로 rollback되지는 않는다. Terraform 변경, Secrets Manager/Kubernetes Secret 동기화, 이미 실행된 DB migration도 Helm rollback 범위 밖이다.

현재 저장소의 일반 앱 복구 절차는 배포 branch에 revert commit을 만들고 CI 검증 후 수동 배포를 다시 실행하는 것이다. 이 역시 이미지를 새로 빌드하는 복구이며 예전 digest를 그대로 재사용하는 기능은 아니다. 운영자가 즉시 이전 Helm revision으로 복구해야 한다면 조직의 장애 대응 권한과 runbook 아래에서 아래 작업을 수행하고 Git의 배포 정의도 후속 수정해 다음 배포가 다시 잘못된 상태를 만들지 않게 한다.

교육용 장애 대응 예시 · 실제 실행은 지정 운영자만

# history에서 정상 상태였던 revision을 확인한 뒤 지정한다.
helm --kube-context "$EKS_CONTEXT" -n trippilot history trippilot
helm --kube-context "$EKS_CONTEXT" -n trippilot rollback \
  trippilot "$GOOD_REVISION" --wait --timeout 20m

Helm revision은 chart·values를 되돌리지만 외부에서 이미 바뀐 DB 스키마·암호·서비스 데이터는 되돌리지 못한다. 이전 앱이 현재 DB와 호환되는지 확인하고 외부·내부 검증을 반복한다. DB 복구는 백업·시점 복원과 데이터 손실 허용 범위를 판단하는 별도 운영 절차다. PRD RDS는 평소 삭제 보호를 유지한다. 환경 정리는 AWS 수동 삭제 런북에 따라 service 계획·삭제를 마친 뒤 bootstrap을 별도로 실행한다. 기본값은 plan, 최종 RDS 스냅샷 보존, state S3 보존이다. 실제 삭제에는 환경·계정 확인 문자열과 검증된 SHA가 필요하다. Redis 데이터·ECR 이미지는 삭제되며 코드 revert로 복구되지 않는다. 로컬 just down은 kind 데이터까지 삭제하지만 AWS 정리 명령은 아니다. Helm rollback 동작.
