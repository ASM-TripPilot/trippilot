${{ ... }}는 GitHub Actions 표현식이고 Bash의 $NAME은 runner에서 읽는 환경변수다. 둘은 평가하는 주체가 다르다. Workflow에서 env: DEPLOY_MODE: ${{ inputs.mode }}로 입력을 넘기면 Python은 os.environ['DEPLOY_MODE']로, Bash는 "$DEPLOY_MODE"로 읽는다. 외부 입력을 shell 코드에 직접 이어 붙이지 않고 값으로 전달하면 코드와 데이터를 구분하기 쉽다.

표현식 / 값생산자이 저장소의 사용 예
github.sha, github.ref현재 실행의 Git 정보배포 commit 식별, 브랜치 검증
inputs.environment수동 실행 입력dev 또는 prd 선택
vars.AWS_ROLE_ARN저장소·Environment 설정 변수선택한 환경의 Role ARN
secrets.GITHUB_TOKENGitHub가 제공하는 job 토큰기존 CI의 GHCR 로그인
env.IMAGE_TAGworkflow 또는 job 환경변수새 ECR 이미지의 태그
steps.config.outputs.state_bucket같은 job의 id: config stepTerraform S3 backend 선택
needs.validate.outputs.revision선행 job이 공개한 output연습 예제의 검증 commit 전달

Context는 사용할 수 있는 YAML 위치가 정해져 있다. 예를 들어 아직 실행하지 않은 step의 output으로 workflow 전체의 시작 조건을 정할 수는 없다. Contexts reference

Runner는 특별한 파일 경로를 환경변수로 제공한다. GITHUB_OUTPUT에 name=value를 덧붙이면 step의 결과가 된다. GITHUB_ENV에 쓰면 같은 job의 다음 step들이 읽을 환경변수가 된다. 작성한 step 안에서 즉시 변수를 쓰려면 shell 변수도 별도로 지정해야 한다. GITHUB_STEP_SUMMARY는 사람이 읽는 실행 요약에 Markdown을 추가한다. 세 파일의 목적이 다르므로 요약에 쓴 값을 프로그램이 output처럼 참조할 수는 없다. Environment files와 workflow commands

실제 코드 발췌 · 문자열로 전달되는 step output
- name: Validate environment and branch before AWS access
  id: config
  run: python3 infra/scripts/workflow_config.py

# 이후 Terraform init step에서 사용
env:
  TF_STATE_BUCKET: ${{ steps.config.outputs.state_bucket }}

# 이후 앱 배포 관련 step에서 사용
if: steps.config.outputs.deploy_application == 'true'

workflow_config.py는 GITHUB_OUTPUT 파일에 state_bucket=...와 deploy_application=false 같은 결과를 쓴다. inputs.deploy_application은 boolean 입력이지만 step output은 문자열이므로 후속 조건은 == 'true'로 비교한다. 문자열 'false' 자체를 boolean인 것처럼 평가하면 의도와 어긋날 수 있다.

기초 예제에서 step output을 다른 job으로 옮기는 연결은 steps.check.outputs.revision → jobs.validate.outputs.revision → needs.validate.outputs.revision이다. GITHUB_ENV의 CHECK_LABEL은 이 연결을 거치지 않았으므로 report job에 전달되지 않는다. Job 사이 output 전달
