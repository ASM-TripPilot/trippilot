workflow Summary의 NLB DNS 이름을 API 도메인과 연결한다. 여기에는 두 종류의 DNS 레코드가 있다. ACM 검증 CNAME은 도메인 소유권을 증명하고 갱신에 쓰인다. API CNAME은 실제 요청을 NLB로 보낸다. 서로 대체할 수 없으며 ACM 검증 레코드를 API 접속 주소로 사용하면 안 된다. ACM DNS 검증.

이 강의는 서브도메인을 사용한다. Cloudflare의 프록시를 켜면 요청이 Cloudflare를 거쳐 origin으로 가므로 인증서·origin TLS·timeout·클라이언트 IP 정책이 추가된다. 먼저 DNS only로 NLB의 TLS를 확인한 뒤 별도 확장으로 다룬다. 현재 브랜치에는 Cloudflare provider나 DNS 자동 연결이 구현되어 있지 않다. 1강의 Cloudflare 예제는 NLB 주소가 준비된 뒤 연결할 확장이다. Cloudflare DNS only와 Proxied의 차이.

관찰 과제: 아래 읽기 명령은 강사가 접근 권한을 준 EKS 컨텍스트에서 실행한다. EKS_CONTEXT와 API_HOSTNAME은 실제 승인된 값으로 설정한다. 외부 curl 예제는 Bash 기준이다.

배포 결과 관찰 · 변경하지 않는 명령

kubectl config get-contexts
# 지정된 DEV EKS 컨텍스트 이름으로 바꾼다.
export EKS_CONTEXT='강사가-지정한-DEV-EKS-컨텍스트'
export API_HOSTNAME='api-dev.example.com'

kubectl --context "$EKS_CONTEXT" -n trippilot get pods,svc
kubectl --context "$EKS_CONTEXT" -n trippilot \
  get service gateway -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'
helm --kube-context "$EKS_CONTEXT" -n trippilot status trippilot

curl --fail --show-error "https://$API_HOSTNAME/healthz"
curl --silent --output /dev/null --write-out '%{http_code}\n' \
  "https://$API_HOSTNAME/internal/health"
curl --silent --output /dev/null --write-out '%{http_code}\n' \
  "https://$API_HOSTNAME/actuator/health"

기대 결과: 앱 Pod가 Ready이고 Service에 NLB hostname이 표시된다. 외부 /healthz는 HTTP 200과 ok, /internal/health 및 /actuator/health는 404여야 한다. curl -k로 인증서 오류를 숨기지 않는다. /healthz는 gateway의 응답이므로 별도로 인증된 사용자 흐름·일정 생성 같은 업무 API까지 검증한다.

현재 smoke Job은 클러스터 안에서 gateway·backend readiness·AI health에 접근하고 gateway의 차단 경로가 404인지 확인한다. NLB가 TLS를 종료하고 gateway에는 HTTP를 전달하므로 내부 검사에 http://gateway:443/healthz가 등장한다. port 번호가 443이라고 해서 그 내부 구간까지 HTTPS라는 뜻은 아니다. 외부 DNS와 NLB 인증서는 이 smoke 경로가 지나지 않으므로 별도로 확인해야 한다.

배포 확인은 세 층으로 기록하면 좋다. 첫째, Kubernetes desired 상태와 실제 Ready 수가 맞는가. 둘째, 내부 backend·AI·DB 연결이 맞는가. 셋째, 사용자가 접근하는 hostname·TLS와 업무 요청이 맞는가. 어느 한 층의 성공만으로 나머지를 추정하지 않는다.
