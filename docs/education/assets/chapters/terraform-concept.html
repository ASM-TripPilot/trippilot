다음 상황을 생각해 보자. 개발 환경에서 AWS 콘솔로 VPC, 서브넷, 데이터베이스를 만들었다. 일주일 뒤 운영 환경을 만들려는데 어느 옵션을 켰는지 기억나지 않는다. 콘솔 캡처가 있어도 생성 순서, 숨겨진 기본값, 나중에 바꾼 설정을 모두 복원하기는 어렵다. Terraform은 이런 인프라 설정을 버전 관리 가능한 코드로 표현한다. 이 방식을 Infrastructure as Code, IaC라고 부른다.

TripPilot의 resource "aws_vpc" "this"는 이 명령을 한 번 실행하라는 지시가 아니라 이 CIDR과 DNS 설정을 가진 VPC가 이 구성에 존재해야 한다는 선언이다. Terraform은 코드, 저장된 상태 정보, provider가 조회한 실제 리소스를 비교해 필요한 변경을 계산한다. 코드가 같아도 콘솔에서 누군가 설정을 바꿨다면 차이가 나타날 수 있다. 이런 불일치를 drift라고 한다.

여기서 역할을 구분하면 이해가 빨라진다. Terraform CLI는 구성 해석과 변경 계획을 담당한다. Provider는 AWS나 Cloudflare API와 통신하며 각 리소스의 스키마와 동작을 제공한다. Backend는 Terraform의 state를 어디에 보관하고 어떻게 잠글지 정한다. AWS Provider를 쓴다고 state가 자동으로 S3에 저장되지는 않는다.

코드로 기록한 인프라는 PR에서 검토할 수 있고 같은 구조를 다른 환경에 적용하기 쉽다. 그러나 Git 커밋을 되돌렸다고 데이터베이스 안의 데이터도 돌아오지는 않는다. 선언을 되돌리면 Terraform은 그 선언에 맞추는 새 변경을 계획할 뿐이다. 리소스 교체, 데이터 복구, DB 스키마 변경은 각각 다른 문제로 다뤄야 한다.
