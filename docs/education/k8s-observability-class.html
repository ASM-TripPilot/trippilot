Part 1Kubernetes

왜 Kubernetes인가

컨테이너 하나를 띄우는 건 쉽습니다. 어려운 건 그 다음입니다.

강사 노트 "docker run으로 충분한데 왜?"라는 질문에서 출발하세요.
Part 1문제 정의

docker run만으로 안 되는 것들

  • 죽으면 누가 살리나 — 프로세스가 꺼지면 그걸로 끝입니다.
  • 몇 개를 띄울 건가 — 트래픽이 늘면 손으로 하나씩 늘려야 합니다.
  • 어디로 보낼 건가 — 컨테이너 IP는 재시작마다 바뀝니다.
  • 무중단 배포는 — 새 버전을 띄우고 옛 버전을 내리는 순서를 직접 관리해야 합니다.
  • 설정과 비밀은 — 이미지에 구우면 환경마다 다시 빌드해야 합니다.

Kubernetes는 이걸 "원하는 상태를 선언하면 시스템이 맞춰준다"는 하나의 모델로 풉니다.

강사 노트 각 항목마다 "여러분 프로젝트에서는 이걸 어떻게 하고 있나요?" 물어보면 좋습니다.
Part 1핵심 개념

선언적 모델

명령형은 방법을 말합니다. 선언형은 결과를 말합니다.

명령형

# 3개 띄워라
docker run app &
docker run app &
docker run app &

하나 죽으면? 내가 알아채고 다시 띄워야 합니다.

선언형

replicas: 3

하나 죽으면? 컨트롤러가 알아서 채웁니다. 계속.

이게 k8s를 이해하는 열쇠입니다. YAML은 "명령"이 아니라 "내가 원하는 상태"입니다. 시스템은 현재 상태와 원하는 상태의 차이를 계속 줄입니다.

강사 노트 나중에 kubectl delete pod <name>을 해보게 하면 이 개념이 몸으로 이해됩니다 — 곧바로 새 파드가 뜹니다.
Part 1오브젝트

알아야 할 다섯 가지

오브젝트한 줄 정의왜 필요한가
Pod컨테이너 1개 이상을 묶은 최소 배포 단위k8s는 컨테이너가 아니라 파드를 스케줄합니다
Deployment"파드를 N개 유지하라"는 선언자가 치유 · 롤링 업데이트 · 롤백
Service파드 집합에 붙는 고정 주소파드 IP는 바뀝니다. 서비스 이름은 안 바뀝니다
ConfigMap설정값 묶음환경이 달라도 이미지는 하나
Namespace리소스를 나누는 논리적 구획이름 충돌 방지 · 권한 · 정리 단위
Deployment관리→ReplicaSet관리→Pod   ←노출Service
강사 노트 ReplicaSet은 직접 만들 일이 거의 없습니다. Deployment가 버전마다 하나씩 만들고 롤백은 옛 ReplicaSet으로 되돌리는 것 — 이렇게 설명하면 rollout undo가 이해됩니다.

함정 ① — 실제로 오늘 막혔던 지점

Docker Desktop이 관리하는 kind 클러스터에서는 로컬 빌드 이미지를 배포할 수 없습니다. 노드가 호스트 Docker에 컨테이너로 보이지 않아 kind load를 쓸 수 없고, 모든 이미지 pull이 Docker Desktop 내부 미러로 강제 프록시되어 로컬 레지스트리를 띄워도 막힙니다.

→ 그래서 Docker Desktop 내장 k8s를 끄고 kind를 직접 설치했습니다.

강사 노트 이 함정은 검색해도 잘 안 나옵니다. 증상은 ErrImageNeverPull 또는 미러에서 오는 500 Internal Server Error입니다.

왜 셋 다 필요한가

Part 2표준

OpenTelemetry와 OTLP

예전에는 신호마다, 벤더마다 다른 라이브러리를 썼습니다. 벤더를 바꾸면 코드를 다 고쳐야 했습니다.

앱— OTLP →수집기→저장소→UI
  • OpenTelemetry — 계측 API·SDK의 표준 (CNCF)
  • OTLP — 신호를 실어 나르는 벤더 중립 와이어 프로토콜. gRPC(4317) / HTTP(4318)

왜 중요한가: 앱은 OTLP로만 내보내면 됩니다. 수집기를 다른 것으로 바꿔도 애플리케이션 코드는 그대로, 엔드포인트만 바뀝니다. 되돌릴 수 있는 결정이 됩니다.

강사 노트 "벤더 종속을 어떻게 피하나"는 실무에서 매우 자주 나오는 질문입니다.

Part 3이미지

멀티스테이지 Dockerfile

# ---- build ----
FROM gradle:8.14-jdk21 AS build
WORKDIR /src
# 의존성 레이어를 먼저 굳힌다 — 소스만 바뀌면 캐시 유지
COPY settings.gradle.kts build.gradle.kts ./
RUN gradle --no-daemon :app:dependencies > /dev/null 2>&1 || true
COPY . .
RUN gradle --no-daemon :app:bootJar -x test

# ---- runtime ----
FROM eclipse-temurin:21-jre
COPY --from=build /src/app/build/libs/*.jar /app/app.jar
USER 1001:1001
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0"
ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS -jar /app/app.jar"]

왜 두 단계인가

빌드 도구(JDK·Gradle)는 실행에 필요 없습니다. 최종 이미지에서 빼면 크기와 공격면이 줄어듭니다.

왜 MaxRAMPercentage인가

없으면 JVM이 호스트 전체 메모리 기준으로 힙을 잡아 컨테이너 한도를 넘겨 OOMKilled됩니다.

강사 노트 USER 1001:1001이 숫자인 이유는 다음다음 슬라이드에서 다룹니다.
Part 3핵심

빌드했는데 파드가 안 뜹니다

함정 ③ — 로컬 k8s에서 가장 흔한 실수

kind 노드는 호스트 Docker와 별도의 이미지 스토어를 씁니다. docker build만 하면 노드에서는 그 이미지가 보이지 않습니다.

kubectl get pods -n trippilot
trippilot-backend-xxx   0/1   ErrImageNeverPull

해결 — 두 단계입니다

docker build -t trippilot-backend:dev backend
kind load docker-image trippilot-backend:dev --name trippilot   # ← 빠뜨리기 쉬움

노드 안에 들어갔는지 직접 확인할 수 있습니다.

docker exec trippilot-control-plane crictl images | grep trippilot

그래서 build.sh가 두 명령을 항상 함께 실행합니다. 사람이 매번 기억해야 하는 규칙은 언젠가 지켜지지 않습니다.

강사 노트 일부러 kind load를 빼고 배포해 ErrImageNeverPull을 직접 보여주면 확실히 각인됩니다.

Part 4상관 ID

요청 하나를 끝까지 따라가기

class CorrelationIdFilter : OncePerRequestFilter() {
  override fun doFilterInternal(req, res, chain) {
    val id = resolve(req.getHeader("X-Correlation-Id"))
    MDC.put("correlation_id", id)      // 이후 모든 로그에 자동 포함
    res.setHeader("X-Correlation-Id", id)  // 클라이언트에 돌려줌
    try { chain.doFilter(req, res) }
    finally { MDC.remove("correlation_id") }  // 스레드 재사용 대비
  }
}

클라이언트 값은 검증합니다

형식([A-Za-z0-9_-]{8,64})을 벗어나면 새로 발급합니다. 로그 인젝션 방지.

trace_id와 역할이 다릅니다

trace_id는 서버 내부 호출 경로, correlation_id는 클라이언트~비동기 잡까지 잇는 종단 축.

강사 노트 finally의 MDC.remove를 빠뜨리면 스레드 풀에서 이전 요청 ID가 새 나갑니다. 실제로 흔한 버그입니다.

토큰·비밀번호·이메일·생년월일·좌표. 한번 수집되면 저장소에 그대로 남습니다.

개별 로그문에 맡기지 마세요. MaskingAppender를 모든 출력 앞단에 두어 구조적으로 강제합니다.

함정 ⑥ — 실제로 뚫렸던 것

OTel 에이전트가 기본값으로 root 로거에 자체 appender를 자동 부착합니다. 그대로 두면 마스킹을 우회한 원문이 그대로 적재됩니다.

OTEL_INSTRUMENTATION_LOGBACK_APPENDER_ENABLED=false로 끄고 설치를 앱이 소유해야 합니다.

함정 ⑥-b — 경로가 둘이면 규칙도 갈린다

로그가 stdout JSON과 OTLP 두 경로로 나갑니다. 마스킹 규칙이 각각 따로 있으면 한쪽만 고쳤을 때 다른 쪽으로 원문이 샙니다.

실제로 LogMasker에는 Bearer 없는 JWT 규칙이 있었는데 logback-spring.xml에는 없었습니다. MDC에 토큰이 실리자 OTLP로는 ****, stdout으로는 원문이 나갔습니다.

두 테스트가 이를 놓친 이유 — 둘 다 설정을 손으로 복사해 검증했기 때문입니다. 지금은 MaskingParityTest가 logback-spring.xml을 직접 읽어 두 경로를 비교합니다.

강사 노트 "보안 통제는 켰다고 끝이 아니라 우회 경로가 없는지 확인해야 한다"는 교훈. 실제로 SigNoz에서 원문이 보였던 이야기를 하면 임팩트가 큽니다. ⑥-b는 "테스트가 있었는데도 못 잡은 이유"까지 이야기하면 더 좋습니다 — 정본이 아니라 복사본을 검증하면 드리프트는 잡히지 않습니다.

계측은 조용히 깨집니다. 라이브러리를 올렸더니 로그가 안 나가는데 아무도 모르는 상황이 실제로 생깁니다.

// appender 트리를 재귀 탐색해 "마스킹을 안 거친 출력 지점"을 찾는다
@Test
fun `모든 로그 출력 지점이 마스킹을 거친다`() {
  val bypassing = logSinks().filterNot { (_, masked) -> masked }
  assertThat(bypassing).isEmpty()
}

root 바로 아래에는 OTel MDC 래퍼가 붙고 우리 마스킹 appender는 그 안쪽에 중첩됩니다. 1단계만 보면 오판합니다 — 트리를 끝까지 봐야 합니다.

root → [OTel MDC 래퍼] → [MASKED] → [STDOUT_JSON, OTLP]

현재 백엔드 테스트 21건 전부 통과. 외부 의존이 없어 SigNoz 없이도 CI에서 돕니다.

강사 노트 이 테스트는 실제로 함정 ⑥을 잡아낸 것에서 나왔습니다. "버그를 테스트로 고정한다"의 좋은 예.

여섯 개 중 넷은 에러 메시지가 원인을 정확히 말해주지 않습니다. 어디를 봐야 하는지 아는 것이 실력입니다 — 그래서 관측성이 필요합니다.

강사 노트 이 표를 인쇄해 나눠주면 실습 중 참고 자료가 됩니다.
정리핵심 원칙

가져갈 것

  • 선언형으로 생각하기 — "어떻게"가 아니라 "무엇을 원하는지"를 씁니다.
  • 확인이 아니라 차단 — 사람이 매번 지켜야 하는 규칙은 스크립트로 강제합니다.
  • 침묵 실패를 만들지 않기 — 실패는 반드시 흔적을 남겨야 합니다.
  • 벤더 중립 유지 — OTLP로 내보내면 수집기는 바꿀 수 있는 결정이 됩니다.
  • 보안 통제는 구조로 — 개별 호출자의 성실함에 기대지 않습니다.
  • 겪은 버그는 테스트로 — 같은 실수를 두 번 하지 않는 유일한 방법입니다.
