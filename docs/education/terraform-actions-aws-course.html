TripPilot 수업의 범위와 준비

수업의 대상은 여행 서비스 TripPilot이다. 백엔드는 API를 제공하고 AI 서비스와 통신한다. 로컬에서는 kind 클러스터 안에 애플리케이션과 데이터베이스를 함께 띄운다. AWS에서는 EKS에 애플리케이션을, RDS에 PostgreSQL을 배치한다. 여기서는 어떤 명령을 실행하는지에 더해 어떤 도구가 무엇을 소유하며 어떤 결과를 다음 단계에 넘기는지 살펴본다.

이 브랜치의 배포 경로

  1. 01 / LOCAL코드·테스트kind에서 서비스 동작 확인
  2. 02 / ONCE초기 기반 준비OIDC 신뢰 · CloudFormation · state
  3. 03 / PLAN & APPLY인프라 구성Terraform → AWS API
  4. 04 / DEV이미지·앱 배포Docker build → ECR → Helm
  5. 05 / PRD운영 배포·검증운영 브랜치와 환경으로 수동 실행

DEV와 PRD는 각각 별도의 state와 AWS 리소스를 사용한다. 현재 코드는 환경마다 이미지를 다시 빌드한다. 동일 이미지 digest를 승격하는 방식은 3강의 확장 설계에서 다룬다.

수업 시간과 진행 방식

기본 수업은 각 50분, 총 150분이다. 두 번의 10분 휴식까지 포함하면 170분이다. 각 강의의 시간표는 설명과 코드 읽기, 짝 토론, 실습 결과 확인을 포함한다. 30분 수업에서는 핵심 경로와 대표 예제에 집중하고 60분 수업에서는 확장 실습까지 진행한다.

운영안강의별 시간강사의 준비

본문 읽기와 설계 문제에는 AWS 계정이 필요 없다. Terraform의 backend를 비활성화한 초기화와 mock provider 테스트는 AWS 리소스를 만들지 않지만 Provider 다운로드에는 네트워크가 필요하다. 실제 plan은 AWS 조회 권한이 필요하며 state 잠금을 사용할 수 있다. apply와 bootstrap은 실제 리소스를 변경하므로 강사가 지정한 실습 환경에서 진행한다.

강사는 3강 전에 예제 DEV 환경과 배포 로그를 준비하는 편이 좋다. EKS·RDS·NAT 생성과 이미지 빌드는 수업 시간보다 오래 걸릴 수 있고 생성한 리소스에는 비용이 발생한다. 50분 수업의 완료 기준은 배포의 선행 조건과 검증 결과를 설명하고 준비된 환경에서 절차를 따라갈 수 있는지다. 모든 학생이 새 AWS 계정을 처음부터 운영 상태로 만드는 것까지 요구하지는 않는다.

네트워크 구역과 접근 경계

VPC는 서비스 전용 네트워크, 서브넷은 그 안을 나눈 작은 구역입니다.

구역배치하는 것인터넷과의 관계
PublicNAT, 앱 배포 후 NLBInternet Gateway로 나가는 경로
Private computeEKS 노드와 앱 Pod외부 통신은 NAT를 통해 나감
Isolated dataRDS PostgreSQL, Redis인터넷/NAT 기본 경로 없음

NAT는 내부 앱이 밖으로 요청을 보낼 때 쓰는 출구입니다.

강사 노트AZ(가용 영역)는 한 리전 안의 분리된 운영 구역입니다. 각 AZ마다 세 종류의 서브넷을 만듭니다. Public이라는 이름만으로 모든 리소스가 외부에 공개되지는 않습니다. 실제 접근은 주소, 경로, 보안 그룹 설정에 달려 있습니다. RDS 5432와 Redis 6379는 EKS 클러스터 보안 그룹에서만 들어오도록 허용하며 TLS를 사용합니다. EKS 노드는 private이지만 관리 API에는 public endpoint도 있습니다.

원하는 상태와 변경 계획

다음 상황을 생각해 보자. 개발 환경에서 AWS 콘솔로 VPC, 서브넷, 데이터베이스를 만들었다. 일주일 뒤 운영 환경을 만들려는데 어느 옵션을 켰는지 기억나지 않는다. 콘솔 캡처가 있어도 생성 순서, 숨겨진 기본값, 나중에 바꾼 설정을 모두 복원하기는 어렵다. Terraform은 이런 인프라 설정을 버전 관리 가능한 코드로 표현한다. 이 방식을 Infrastructure as Code, IaC라고 부른다.

TripPilot의 resource "aws_vpc" "this"는 이 명령을 한 번 실행하라는 지시가 아니라 이 CIDR과 DNS 설정을 가진 VPC가 이 구성에 존재해야 한다는 선언이다. Terraform은 코드, 저장된 상태 정보, provider가 조회한 실제 리소스를 비교해 필요한 변경을 계산한다. 코드가 같아도 콘솔에서 누군가 설정을 바꿨다면 차이가 나타날 수 있다. 이런 불일치를 drift라고 한다.

여기서 역할을 구분하면 이해가 빨라진다. Terraform CLI는 구성 해석과 변경 계획을 담당한다. Provider는 AWS나 Cloudflare API와 통신하며 각 리소스의 스키마와 동작을 제공한다. Backend는 Terraform의 state를 어디에 보관하고 어떻게 잠글지 정한다. AWS Provider를 쓴다고 state가 자동으로 S3에 저장되지는 않는다.

코드로 기록한 인프라는 PR에서 검토할 수 있고 같은 구조를 다른 환경에 적용하기 쉽다. 그러나 Git 커밋을 되돌렸다고 데이터베이스 안의 데이터도 돌아오지는 않는다. 선언을 되돌리면 Terraform은 그 선언에 맞추는 새 변경을 계획할 뿐이다. 리소스 교체, 데이터 복구, DB 스키마 변경은 각각 다른 문제로 다뤄야 한다.

HCL 블록과 표현식

현재 코드 발췌 · network.tf

resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true
  tags                 = { Name = local.name }
}

resource는 블록 종류, "aws_vpc"는 provider가 제공하는 리소스 종류, "this"는 이 구성 안에서 붙인 이름이다. this 자체가 AWS 콘솔의 VPC 이름이 되는 것은 아니다. 콘솔에서 보는 이름 태그는 tags.Name이 정한다. 구성 내부에서 이 리소스를 가리키는 주소는 aws_vpc.this이고 AWS가 부여한 ID는 aws_vpc.this.id로 읽는다.

cidr_block = var.vpc_cidr는 이름에 값을 할당하는 인자(argument)다. HCL 설명에서 이를 attribute라고 부르기도 한다. 오른쪽에는 문자열이나 숫자뿐 아니라 다른 값에 대한 참조, 함수 호출, 조건식이 들어간다. 중괄호는 블록과 객체 양쪽에 나타나므로 앞 문맥을 봐야 한다. tags = { ... }는 객체 값이고 EKS의 vpc_config { ... }는 중첩 블록이다. provider가 정한 스키마에 따라 둘을 바꿔 쓸 수 없다. HashiCorp의 HCL 구성 문법

자료형예읽는 방법
string"ap-northeast-2"문자열. 문자열 보간은 "trippilot-${var.environment}"
number2, 100가용 영역 수, 스토리지 크기 등의 숫자
booltrue, false따옴표 없는 논리 값
list(string)["backend", "ai"]순서가 있으며 같은 값이 여러 번 들어갈 수 있음
set(string)toset(["backend", "ai"])순서에 의미를 두지 않는 중복 없는 집합
map(string){ dev = "small", prd = "medium" }키는 문자열, 값은 같은 자료형으로 구성된 사전
object({...}){ enabled = true, replicas = 2 }이름별로 서로 다른 자료형을 정할 수 있는 구조
nulllocal.production ? "final" : null값의 부재. 해당 인자를 지정하지 않는 의미로 자주 사용

리터럴의 [...]와 {...}는 엄밀히는 tuple과 object 값을 만든다. 변수에 list(string)이나 map(string) 제약을 주면 호환되는 값으로 변환된다. 처음에는 대괄호를 순서 있는 값 묶음으로, 키와 값이 있는 중괄호를 이름 있는 값 묶음으로 읽고 공개 모듈의 입력을 설계할 때 자료형을 엄격히 지정하면 된다. Terraform 자료형 제약

문법 학습 예제 · 현재 브랜치에 추가된 코드는 아님

variable "service" {
  type = object({
    name     = string
    replicas = number
    labels   = map(string)
  })
  default = {
    name     = "backend"
    replicas = 1
    labels   = { team = "trippilot" }
  }
}

이 입력은 var.service.name과 var.service.replicas처럼 읽는다. replicas = "two"처럼 숫자로 변환할 수 없는 값은 타입 검사에서 실패한다. 유효한 숫자라도 음수는 허용하고 싶지 않으므로 다음 절의 validation을 함께 사용한다. 타입은 값의 모양을, validation은 업무상 허용 조건을 검사한다고 구분하면 된다.

블록 종류는 resource, label은 aws_vpc와 this, 객체 값은 { Name = local.name }, 변수 참조는 var.vpc_cidr다. local.name은 입력 변수가 아니라 locals에서 계산한 값에 대한 참조다.

강사 노트이 문법의 이름은 HCL입니다. 문자열에는 따옴표, true·false와 숫자에는 따옴표를 쓰지 않습니다. resource 뒤의 aws_vpc는 종류, this는 코드에서 참조할 이름입니다. this 자체가 AWS 이름이 되는 것은 아닙니다. aws_vpc.this.id로 AWS가 만든 VPC ID를 읽습니다.

variable "environment" {

  validation {
    condition     = contains(["dev", "prd"], var.environment)
    error_message = "environment must be dev or prd."

locals {
  name       = "trippilot-${var.environment}"
  production = var.environment == "prd"
  azs        = slice(data.aws_availability_zones.available.names, 0, var.availability_zone_count)
  nat_count  = var.single_nat_gateway ? 1 : var.availability_zone_count
}

Variable은 실행하는 쪽이 정하는 입력이다. 이 예제에는 기본값이 없으므로 environment를 제공해야 한다. dev.tfvars의 environment = "dev"는 선언이 아니라 값 지정이다. 환경 파일은 자동으로 모두 읽히는 것이 아니다. 현재 workflow가 -var-file="../environments/$DEPLOY_ENVIRONMENT.tfvars"로 선택한다. 개발과 운영 파일을 동시에 전달하면 뒤에서 지정한 값이 앞의 값을 덮을 수 있으므로 한 환경 파일을 명확히 고른다.

입력 전달에는 기본값, TF_VAR_이름 환경변수, 자동 로드되는 terraform.tfvars·*.auto.tfvars, 명시적인 -var·-var-file 등의 방법이 있다. 이 브랜치는 규모 값은 환경 파일에, AWS 계정과 배포 역할 ARN은 workflow의 TF_VAR_aws_account_id·TF_VAR_deployment_role_arn에 둔다. 입력을 어디서 제공하는지 정해 두면 내 컴퓨터에서는 다른 값으로 실행되는 문제를 줄일 수 있다. Terraform 입력 변수 문서

Locals는 입력에서 계산한 중간 값이다. var.environment가 prd면 local.name은 trippilot-prd, local.production은 true다. 조건 ? 참일 때 값 : 거짓일 때 값은 조건 표현식이다. RDS의 backup_retention_period = local.production ? 14 : 1처럼 정책 차이를 한곳에 표현할 수 있다.

Data source는 이미 존재하는 정보를 조회한다. data "aws_availability_zones"는 사용 가능한 AZ 목록을 가져오고 data "aws_iam_role" "cluster"는 bootstrap이 만든 EKS 역할을 찾는다. 이름을 읽는 코드만 있다고 그 역할이 생성되지는 않는다. 조회 대상이 없거나 조회 권한이 없으면 계획 단계에서 실패할 수 있다.

required_providers는 어떤 플러그인을 어느 범위의 버전으로 설치할지 선언한다. provider "aws"는 설치한 플러그인에 리전·계정 제한·공통 태그 같은 실행 설정을 제공한다. required_version은 Terraform CLI 버전 조건이다. CLI 버전과 AWS provider 버전은 서로 다른 번호 체계이며 함께 기록해야 재현할 수 있다.

이 브랜치의 정확한 기준: workflow는 Terraform CLI 1.13.5를 설치한다. AWS provider 선언 ~> 6.38은 >= 6.38.0, < 7.0.0을 허용하며 현재 .terraform.lock.hcl에 선택된 버전은 6.64.0이다. AWS provider 6.38 고정으로 해석하면 틀린다. ~> 6.38.0은 반대로 6.39 미만으로 범위가 좁아진다. 버전 제약의 의미

allowed_account_ids는 잘못된 AWS 계정 자격증명으로 실행하는 실수를 막는 검증이다. 계정 ID는 12자리 문자열로 받는다. 이 설정이 권한을 부여하지는 않는다. 무엇을 만들 수 있는지는 IAM 정책이 정하고 실제 실행 계정이 허용된 계정인지 provider가 추가 확인한다. default_tags는 지원되는 리소스에 공통 태그를 붙여 프로젝트와 환경을 식별하게 한다. 이 브랜치의 bootstrap 정책도 환경별 이름과 태그를 권한 범위에 활용한다.

이 설정에 access_key나 secret_key가 없는 이유는 인증 정보를 다른 경로에서 제공하기 때문이다. GitHub Actions는 OIDC로 AWS 역할을 Assume하고 짧은 수명의 자격증명을 실행 환경에 설정한다. Terraform의 AWS provider와 S3 backend가 그 인증 환경을 사용한다. 로컬에서 실제 AWS 조회가 필요하다면 조직의 SSO/profile 같은 승인된 인증 경로를 사용한다. 본 수업의 기본 실습은 mock provider를 사용하므로 AWS 자격증명이 필요 없다. AWS Provider 6.64.0 인증·설정 문서

실행 순서는 보통 init에서 provider 다운로드와 backend 초기화, validate에서 스키마 확인, plan에서 AWS 조회와 차이 계산, apply에서 AWS 변경이다. provider 업데이트는 init -upgrade로 할 수 있지만 수업의 복제 환경에서는 사용하지 않는다. 프로젝트는 lock file을 검토한 버전으로 유지하며 workflow가 -lockfile=readonly로 의도하지 않은 변경을 막는다.

강사 노트versions.tf와 .terraform.lock.hcl을 함께 열어 허용 범위와 실제 선택 버전을 비교합니다. 인증 실패와 구성 오류를 구분하고 계정 제한이 왜 필요한지 설명하게 합니다.

State와 두 종류의 잠금

코드에는 aws_vpc.this라는 이름이 있고 AWS에는 vpc-...라는 ID가 있다. State는 둘의 대응과 Terraform이 관리에 필요한 정보를 보관한다. state가 사라져도 AWS의 VPC가 자동 삭제되지는 않는다. 반대로 Terraform이 기존 리소스와의 연결을 잃으면 새 리소스를 만들려는 계획이 나올 수 있다. 그래서 state를 앱의 빌드 캐시처럼 지워도 되는 파일로 취급해서는 안 된다.

공통으로 RDS는 public endpoint를 허용하지 않고 스토리지를 암호화하며 PostgreSQL TLS를 요구한다. Redis도 저장 데이터와 전송 구간을 암호화한다. 데이터 서브넷의 route table에는 Internet Gateway나 NAT로 향하는 기본 경로가 없다. EKS는 Auto Mode를 사용하고 cluster의 compute·storage·load balancing 설정을 함께 켠다. private node와 private Kubernetes API는 다른 설정이다. 현재 Kubernetes API는 private endpoint와 public endpoint를 모두 활성화하고 기본 public CIDR은 0.0.0.0/0이다. GitHub 호스팅 러너가 관리 API에 접근해야 하기 때문이다. IAM 인증과 EKS Access Entry가 접근을 통제하며 고정 egress IP의 러너를 도입한다면 CIDR을 함께 좁힐 수 있다.

현재 코드에 ECR은 backend·ai·embedding 세 저장소가 항상 생성된다. 임베딩 애플리케이션을 배포할지는 workflow의 별도 옵션이다. 인프라가 준비되었다고 해당 기능의 모든 애플리케이션 코드가 활성화되는 것은 아니다. 예를 들어 Redis 인프라는 정의되어 있지만 저장소 가이드 기준 backend의 Redis adapter는 아직 구현되지 않았다.

환경을 다른 이름·VPC·state·역할로 분리하는 것과 서로 다른 AWS 계정으로 격리하는 것은 수준이 다르다. 현재 구성은 둘 다 선택할 수 있지만 같은 계정에서는 계정·리전 수준 조회 API와 서비스 역할 등 일부 범위가 공유된다. 운영을 강하게 격리하려면 환경별 AWS 계정과 그에 맞는 bootstrap을 사용한다. 위 수치는 이 브랜치의 설계 값이며 보편적인 모든 서비스의 정답은 아니다.

강사 노트3 AZ라고 PostgreSQL을 3개 만든다는 뜻은 아닙니다. 이 코드는 RDS DB instance의 Multi-AZ를 켭니다. Redis는 primary 1개와 replica 2개입니다. EKS 노드 수는 Auto Mode가 워크로드에 맞게 관리하므로 고정 숫자로 가르치지 않습니다. DEV의 공유 NAT는 비용을 줄이는 대신 한 NAT에 의존합니다. 같은 AWS 계정에서 환경을 분리해도 완전한 권한 격리가 되지는 않습니다.

확장 예제 · Cloudflare DNS

추가 학습 예제 · 현재 브랜치 미구현. 아래 코드는 Cloudflare v5 문법을 익히기 위한 별도 DNS 구성 예제다. 현재 AWS stack이나 workflow에는 포함되어 있지 않다. 수업에서는 코드를 읽고 설계하며 Cloudflare API 호출·DNS 변경은 수행하지 않는다.

EKS 애플리케이션을 배포하면 Kubernetes Service를 통해 NLB가 생성되고 AWS가 DNS 이름을 부여한다. 그러나 모바일 앱에는 긴 NLB 주소보다 api-dev.example.com 같은 안정적인 서비스 주소를 설정하고 싶다. Cloudflare가 해당 도메인의 권한 DNS를 관리한다면, 그 서브도메인을 NLB DNS 이름에 연결하는 CNAME 레코드를 만들 수 있다. CNAME은 IP를 복사하는 레코드가 아니라 다른 DNS 이름을 가리키는 레코드다.

추가 학습 예제 · 독립된 dns 디렉터리의 구성 가정 · Cloudflare v5

terraform {
  required_version = ">= 1.11.0, < 2.0.0"
  required_providers {
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 5.0"
    }
  }
}

# 실제 실행 시 CLOUDFLARE_API_TOKEN 환경변수에서 인증한다.
# 토큰 문자열을 이 파일에 넣지 않는다.
provider "cloudflare" {}

variable "zone_id" {
  description = "이미 Cloudflare에 등록한 zone의 ID"
  type        = string
}

variable "api_hostname" {
  description = "예: api-dev.example.com"
  type        = string
}

variable "nlb_dns_name" {
  description = "앱 배포 결과의 NLB DNS 이름. URL scheme이나 경로 제외"
  type        = string
}

resource "cloudflare_dns_record" "api" {
  zone_id = var.zone_id
  name    = var.api_hostname
  type    = "CNAME"
  content = var.nlb_dns_name
  ttl     = 300
  proxied = false
  comment = "TripPilot API entrypoint"
}

source = "cloudflare/cloudflare"는 provider의 출처이며 ~> 5.0은 5.x 범위를 허용한다. 설치 후 선택된 정확한 버전과 해시는 DNS 구성의 lock file로 기록한다. v5 DNS 리소스는 cloudflare_dns_record와 content 인자를 사용한다. 과거 예제의 cloudflare_record·value 문법을 섞지 않는다. Cloudflare의 DNS 레코드 스키마

provider "cloudflare" {}가 비어 있어도 실제 API 실행에는 인증이 필요하다. provider가 읽는 CLOUDFLARE_API_TOKEN 환경변수에 토큰을 전달한다. 토큰은 대상 zone의 DNS 편집에 필요한 범위로 제한하고 GitHub Environment secret으로 보관한다. zone ID는 계정 ID와 다르며 zone을 별도로 조회하도록 설계하면 그 조회 권한도 필요하다. AWS OIDC 인증을 했다고 Cloudflare 인증이 생기지는 않는다. Cloudflare Provider 인증 설정

왜 수업 예제에서는 proxied = false인가?

proxied = false는 Cloudflare가 DNS 해석만 담당하도록 하려는 선택이다. 요청은 기존 브랜치 설계대로 NLB의 HTTPS 443 → nginx gateway → backend로 간다. 이 경우 사용자가 보는 서버 인증서는 NLB에 설정한 ACM 인증서다. Cloudflare의 HTTP 프록시를 켜면 Cloudflare가 트래픽 경로에 추가되어 TLS 모드, 캐시, WAF, 요청 제한과 긴 요청 timeout을 다시 설계해야 한다. TripPilot에는 긴 일정 생성 요청도 있으므로 이를 무심코 추가하면 안 된다. NLB에는 Cloudflare 프록시를 절대 사용할 수 없다는 뜻은 아니다. 현재 구성의 통신 경로를 유지하기 위한 학습 예제의 선택이다. Cloudflare Proxy status와 DNS-only 차이

레코드예시 이름대상생성 시점

ACM DNS 검증 레코드는 ACM이 제시한 정확한 이름과 값으로 만들고 DNS-only로 유지한다. 서비스의 CNAME을 만들었다고 인증서가 자동 검증되는 것은 아니다. 인증서 검증에는 아직 NLB가 없어도 된다. 반대로 NLB에 붙일 인증서는 먼저 발급되어 있어야 하므로 현재 workflow는 앱 배포 전에 ACM 상태가 ISSUED인지 확인한다. 검증 레코드는 자동 갱신을 위해 유지한다. ACM DNS 검증과 자동 갱신

현재 Terraform output에 nlb_dns_name이 없는 이유도 이 순서로 설명할 수 있다. NLB는 Terraform이 aws_lb로 만드는 리소스가 아니라, 뒤에서 Helm이 설치한 Kubernetes Service를 EKS Auto Mode가 처리해 만든다. 따라서 앞선 Terraform plan에서 곧바로 aws_lb.api.dns_name을 참조할 수 없다. 현재 구현은 첫 앱 배포의 Summary에서 NLB DNS를 확인하고 도메인 소유자가 DNS를 연결하도록 안내한다.

루트 도메인과 기존 레코드를 다룰 때

example.com 같은 zone apex는 NS·SOA 등과 공존해야 하므로 일반적인 CNAME 제약이 있다. 수업은 api.example.com 같은 서브도메인을 사용한다. 루트를 연결해야 한다면 Cloudflare CNAME flattening의 동작을 확인한다. 저장소 가이드의 Route 53 Alias 설명은 Route 53이 DNS를 관리할 때의 선택지이며 Cloudflare 리소스에 그대로 옮기는 속성이 아니다. Cloudflare CNAME flattening

이미 콘솔에서 만든 레코드를 Terraform에 선언만 하면 Terraform이 기존 레코드의 소유권을 자동으로 알아내는 것은 아니다. 중복 생성이나 충돌을 피하려면 기존 zone ID와 record ID를 확인하여 import한 뒤, 계획에 예상하지 않은 변경이 없는지 검토한다. 같은 레코드를 두 state나 수동 자동화가 동시에 관리하지 않도록 소유자를 하나로 정한다.

실제 plan과 apply는 어떻게 다른가?

Plan 읽기 예제 · 실제 실행 결과가 아님

+ aws_vpc.this
~ aws_db_instance.postgres
-/+ aws_subnet.private[0]

Plan: 2 to add,
      1 to change,
      1 to destroy.

위 예제의 생성 2건은 VPC 신규 생성과 서브넷 교체에 따른 생성을 포함한다. 교체는 삭제 후 생성(-/+) 또는 생성 후 삭제(+/-)로 표시될 수 있다. 변경 기호뿐 아니라 리소스 이름과 변경 속성을 함께 읽는다.

실제 원격 plan은 이미 준비된 backend와 AWS 자격증명을 사용해 state와 AWS API를 읽는다. 인프라 변경은 적용하지 않지만 잠금 객체 생성·삭제와 같은 backend 작업은 일어날 수 있다. 그래서 원격 plan은 자격증명도 필요 없는 오프라인 검사와 구분해야 한다. 저장된 plan에는 민감 정보가 포함될 수 있으며 외부 공유용 결과물로 취급하지 않는다. terraform plan 공식 동작

강사 설명용 · aws-deploy.yml 내부의 실행 방식 · 학생 실행 대상 아님

# 앞 단계에서 환경별 backend와 AWS 인증을 준비한 상태
terraform plan -lock-timeout=5m \
  -var-file="../environments/$DEPLOY_ENVIRONMENT.tfvars" \
  -out="$RUNNER_TEMP/trippilot.tfplan"

# 수동 workflow의 mode=apply일 때만 실행
terraform apply -lock-timeout=5m "$RUNNER_TEMP/trippilot.tfplan"

계획의 +는 생성, ~는 제자리 수정, -는 삭제, -/+는 교체를 뜻한다. 특히 DB·서브넷 같은 리소스의 삭제와 교체가 의도된 것인지 먼저 확인한다. 저장된 plan을 apply하는 방식은 그 실행에서 만든 구체적인 계획을 적용한다. 단, 별도 mode=plan 실행의 결과 파일을 다음 실행이 승계하는 구조는 아니다. 현재 workflow에서 mode=apply를 선택하면 그 실행 안에서 새 plan을 만든 뒤 적용한다.

최초 init 실패는 provider 다운로드나 lock 호환 문제인지, validate 실패는 문법·스키마 문제인지, 원격 plan 실패는 자격증명·backend·조회 권한 문제인지 단계를 구분해 읽는다. lock 오류를 피하려고 무조건 -lock=false를 추가하거나 state를 지우는 대응은 하지 않는다. 오류 메시지가 가리키는 계층부터 해결한다.

강사 노트권한, 계정 제한, 서비스 할당량, 실제 리전 지원 여부 등은 AWS와 연결해야 확인할 수 있습니다. apply는 자원을 만들고 비용을 발생시킬 수 있습니다. 수업의 로컬 단계에서는 실제 AWS를 변경하지 않고, 실제 변경은 환경 준비 후 Actions에서 수행합니다.

YAML과 Job·Step

Workflow 파일은 .github/workflows/ 아래의 .yml 또는 .yaml 파일이다. YAML은 들여쓰기로 구조를 구분한다. 실습에서는 한 단계마다 공백 두 칸을 쓰고 탭은 쓰지 않는다. key: value는 이름과 값, -는 목록의 항목, |는 줄바꿈을 유지한 여러 줄 문자열이다. run: | 아래의 내용은 YAML이 아니라 선택한 shell에서 실행할 스크립트가 된다.

아래 파일은 AWS 자격 증명을 요청하지 않고 저장소의 부트스트랩 정책 테스트만 수행하는 완전한 연습 예제다. 우선 별도 연습 폴더의 course-checks.example.yml로 저장하고 읽는다. 원격 실행을 실습할 경우에는 저장소 내용이 있는 개인 연습용 사본에서만 .github/workflows/course-checks.yml로 등록한다. 본 프로젝트의 AWS workflow는 변경할 필요가 없다.

작성 예제 · 검증용 workflow 전체 · AWS 접근 없음
name: Course / offline checks

on:
  workflow_dispatch:
    inputs:
      make_report:
        description: 결과 요약 생성
        type: boolean
        default: true

permissions:
  contents: read

env:
  COURSE_NAME: TripPilot automation

jobs:
  validate:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    outputs:
      revision: ${{ steps.check.outputs.revision }}
    steps:
      - name: Read repository
        uses: actions/checkout@v4
        with:
          persist-credentials: false
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.13'
      - name: Test bootstrap policy files
        id: check
        env:
          VALIDATED_REVISION: ${{ github.sha }}
        run: |
          python -m unittest discover -s infra/bootstrap/tests -v
          printf 'revision=%s\n' "$VALIDATED_REVISION" >> "$GITHUB_OUTPUT"
          printf 'CHECK_LABEL=bootstrap-contracts\n' >> "$GITHUB_ENV"
      - name: Show same-job environment
        run: printf '%s / %s\n' "$COURSE_NAME" "$CHECK_LABEL"

  report:
    needs: validate
    if: inputs.make_report
    runs-on: ubuntu-latest
    permissions: {}
    env:
      CHECKED_REVISION: ${{ needs.validate.outputs.revision }}
    steps:
      - name: Write human-readable result
        run: |
          printf '### Offline checks passed\n' >> "$GITHUB_STEP_SUMMARY"
          printf 'Commit: `%s`\n' "$CHECKED_REVISION" >> "$GITHUB_STEP_SUMMARY"

첫 블록 on.workflow_dispatch는 수동 실행을 허용하고 make_report는 체크박스 입력을 만든다. validate는 코드와 Python을 준비한 후 테스트를 실행한다. run의 테스트가 실패하면 이후 성공 경로의 출력은 작성되지 않는다. report는 needs: validate 때문에 검증 성공 뒤에만 실행되며 체크박스가 꺼져 있으면 건너뛴다.

uses: actions/setup-python@v5의 @v5는 action 버전 참조다. Python 버전은 action의 입력인 with.python-version에서 정한다. 두 버전은 서로 다른 대상을 가리킨다. 동일한 step에 uses와 run을 함께 넣는 대신, 준비 action과 실행 명령을 별도 step으로 나눈다.

report에는 checkout이 없다. 파일을 읽지 않고 전달받은 문자열만 요약에 쓰기 때문이다. 반대로 소스를 읽는 새 job을 추가하면 그 job에서도 checkout이 필요하다. GitHub 호스팅 job 사이에 작업 폴더나 설치한 도구가 자동 공유된다고 가정하지 않는다. 문자열은 output으로 전달하고 필요한 파일은 명시적으로 artifact에 저장해 전달하는 식으로 구분한다. 이 브랜치의 state·plan·비밀값은 일반 artifact로 올리지 않는다. Job 구성 공식 설명

실제 workflow의 working-directory: backend는 해당 run 명령을 backend 폴더에서 실행한다. cd backend를 한 step에서 실행했다고 다음 step까지 현재 폴더가 유지되는 것은 아니다. 여러 step에 같은 기본 폴더가 필요하면 AI CI처럼 defaults.run.working-directory를 설정한다. 이 기본값은 run에 적용되며 action의 with.context 같은 입력을 대신하지 않는다. Shell·작업 폴더 기본값

강사 노트위 예제는 실제 workflow에서 중간 도구 설치 단계를 생략한 발췌입니다. 그대로 새 workflow로 복사하는 완성 예제가 아닙니다. setup-terraform step이 먼저 Terraform CLI를 설치해야 run의 명령을 사용할 수 있습니다.

Actions 값의 범위

${{ ... }}는 GitHub Actions 표현식이고 Bash의 $NAME은 runner에서 읽는 환경변수다. 둘은 평가하는 주체가 다르다. Workflow에서 env: DEPLOY_MODE: ${{ inputs.mode }}로 입력을 넘기면 Python은 os.environ['DEPLOY_MODE']로, Bash는 "$DEPLOY_MODE"로 읽는다. 외부 입력을 shell 코드에 직접 이어 붙이지 않고 값으로 전달하면 코드와 데이터를 구분하기 쉽다.

실제 발췌 · 같은 실행 안의 plan → apply
- name: Terraform plan
  working-directory: infra/terraform/stack
  run: terraform plan -lock-timeout=5m -var-file="../environments/$DEPLOY_ENVIRONMENT.tfvars" -out="$RUNNER_TEMP/trippilot.tfplan"

- name: Apply the saved run plan
  if: inputs.mode == 'apply'
  working-directory: infra/terraform/stack
  run: terraform apply -lock-timeout=5m "$RUNNER_TEMP/trippilot.tfplan"

-var-file은 DEV/PRD 구성값을 고르고 -out은 적용할 계획을 파일로 저장한다. 다음 step은 그 파일을 지정하므로 같은 실행 안에서 계획한 내용을 적용한다. -lock-timeout=5m은 state 잠금을 얻기 위해 기다릴 최대 시간이다. Terraform 전체 작업의 제한 시간이 아니다.

별도 plan 실행과 apply 실행은 연결되어 있지 않다. 월요일에 mode=plan을 실행한 뒤 화요일에 mode=apply를 실행하면 화요일 job이 새 plan을 만든다. 월요일 plan 파일은 재사용하지 않는다. 현재 workflow는 plan을 artifact로 올리지 않고 종료 시 임시 파일을 지운다.
수동 입력사전 검증 결과실행되는 주요 경로
plan + 앱 체크 truedeploy_application=false검증 → OIDC → init → plan → 요약·정리
apply + 앱 체크 falsedeploy_application=false검증 → OIDC → init → plan → apply → 요약·정리
apply + 앱 체크 truedeploy_application=true인증서 검사와 이미지·Secret·DB·Helm·smoke를 포함한 전체 경로

workflow_config.py는 deploy = mode == 'apply' and requested_deploy로 앱 배포 여부를 정한다. plan 모드에서 기본 체크박스가 켜져 있어도 앱이 배포되지 않는다. 다만 실제 plan은 AWS 인증과 조회, state 잠금 접근을 수행한다. 강의의 AWS 접근 없는 실습은 이 수동 plan 실행과도 구분한다.

강사 노트mode 기본값은 plan, deploy_application 기본값은 true, embedding_enabled 기본값은 false입니다. workflow_config.py가 조합을 검사하여 실제 앱 배포 여부를 결정합니다. 임베딩을 활성화하면 메모리 비용이 늘어납니다. AWS 변경은 수동 입력으로만 시작합니다.

DEV의 그룹은 aws-dev, PRD는 aws-prd다. 같은 환경의 bootstrap과 일반 배포가 겹치지 않게 같은 이름을 쓴다. 서로 다른 환경은 다른 그룹이므로 병렬 진행할 수 있다. cancel-in-progress: false는 새 요청 때문에 이미 진행 중인 실행을 자동 취소하지 않게 한다.

현재 파일에는 queue 옵션이 없으므로 기본 pending 동작이 적용된다. A가 실행 중이고 B가 대기하는 동안 C가 같은 그룹에 들어오면 B가 C로 교체될 수 있다. 모든 클릭을 순서대로 보존하는 무손실 대기열로 이해하면 안 된다. 반복 클릭 대신 기존 실행과 대기 상태를 확인한다. 최신 GitHub에는 queue: max 옵션도 있으나 이 브랜치는 사용하지 않는다. Concurrency와 pending queue 공식 동작

GitHub concurrency와 Terraform state lock은 보호하는 범위가 다르다. 전자는 같은 그룹의 workflow 중복 실행을 제어하고 후자는 같은 state의 동시 변경 충돌을 줄인다. 로컬에서 실행한 Terraform은 GitHub의 그룹에 들어오지 않으므로 원격 state 잠금도 필요하다.

문제 1. validate job에서 export RESULT=ok를 실행했다. 다른 deploy job에서 $RESULT를 읽을 수 있는가? 전달 방법을 쓰라.

해설 보기

자동으로 전달되지 않는다. 같은 job에서도 별도 shell step 사이에는 단순 export가 유지되지 않는다. 같은 job의 다음 step이면 GITHUB_ENV에 쓰고 다른 job이면 GITHUB_OUTPUT으로 step output을 만들고 job의 outputs에 매핑한 뒤 needs.validate.outputs.RESULT로 읽는다.

해설 보기

현재 구조에서는 그렇게 단정할 수 없다. 승인은 deploy job 시작 전이고 plan은 이후에 생성된다. 사전 plan 실행을 검토했더라도 apply 실행은 새 plan을 만든다는 점까지 기록해야 한다.

문제 5. 새 DEV 배포를 세 번 요청했다. cancel-in-progress: false이므로 세 번 모두 차례로 배포된다고 설명해도 되는가?

Apple Silicon에서 성공한 arm64 실행도 AWS amd64 실행을 대신 검증하지 않는다.

이 간격을 줄이려면 CI에서 실제 AWS용 Dockerfile로 만든 후보 이미지를 테스트하고 필요하면 그 이미지를 별도의 로컬 검증 클러스터에 받아 실행한다. 로컬의 PostgreSQL 16-alpine과 RDS의 16은 같은 major 계열이지만 minor 버전·확장·TLS·권한 정책이 같다는 뜻이 아니다. 클러스터 내부 연결에 성공한 뒤에도 DEV에서 RDS 연결, Flyway migration과 실제 API 시나리오를 확인해야 한다.

승인이 검사하는 지점

현재 deploy job 전체가 Environment를 참조하므로 reviewer 승인은 그 job이 시작하기 전이다. 그 job 안에서 Terraform plan과 apply가 연속 실행된다. 이 승인은 방금 만들어진 plan 파일을 읽고 누른 승인이 아니다. 운영에서는 별도 plan 실행의 결과와 대상 SHA를 먼저 검토하고 apply 실행을 승인하되, apply 실행은 새 plan을 만든다는 점까지 확인해야 한다. 정확히 검토한 plan을 승인 후 적용하려면 job 분리, 동일 SHA 고정, 제한된 plan 저장·전달과 만료 정책을 추가 설계해야 한다.

OIDC subject가 repo:ASM-TripPilot/trippilot:environment:prd 형태이면 environment는 제한하지만 branch나 workflow 파일명까지 증명하지는 않는다. Environment branch 보호와 workflow 코드 리뷰를 함께 적용한다. bootstrap Role은 배포 Role의 권한을 만들 수 있으므로 초기 준비가 끝난 뒤 접근을 제한한다. DEV·PRD를 같은 계정에 두어도 이름·state·VPC 분리만으로 완전한 계정 수준 격리가 생기지 않는다.

실습 B · DEV 인프라와 앱

수업 실습에서는 강사가 준비한 실행 로그를 읽는 것으로 대체할 수 있다. 실제 실행자는 배포할 develop의 commit SHA, 해당 코드의 앱 CI 결과, GitHub Environment 변수, AWS 계정과 리전을 먼저 기록한다. AWS deploy workflow의 검증 job은 인프라·배포 도구·Helm 검사와 backend 종료 설정의 일부 테스트를 수행한다. backend·AI·frontend 전체 테스트 성공을 자동으로 종합 확인하는 release gate는 현재 별도로 구현되어 있지 않다.

현재 구현의 PRD 배포

현재 절차에서는 검토한 변경을 main에 반영하고 그 commit의 필수 테스트를 확인한 뒤, main branch에서 environment=prd로 plan과 apply를 실행한다. 현재 backend·AI CI의 자동 push/PR 대상은 develop 중심이므로 main에 병합했다고 두 CI가 자동 실행됐다고 가정하지 않는다. 각 CI의 workflow_dispatch에서 main을 선택해 테스트를 실행하고 대상 SHA를 확인하거나, 운영 branch를 포함하는 별도 CI gate를 추가해야 한다. 최초 PRD는 bootstrap·ACM·Secrets Manager·DNS 준비를 PRD 환경에서도 수행한다. DEV의 state 버킷·NLB·DB를 PRD 변수에 재사용하지 않는다.

  1. DEV에서 검증한 기능과 변경을 main에 반영하고 실제로 배포할 main SHA를 기록한다. merge commit이나 squash를 사용하면 DEV에서 본 SHA와 달라질 수 있으므로 코드 차이와 CI 대상도 확인한다.
  2. PRD plan의 계정·리전·state·삭제/교체 계획을 검토한다. DB migration에 기존 앱과의 호환성 문제가 있는지 검토한다.
  3. PRD Environment의 리뷰어가 배포를 승인한다. 현재 승인 시점은 앞에서 설명한 deploy job 시작 전이다.
  4. PRD apply와 앱 배포를 실행하고 Summary의 SHA·이미지 tag·URL을 기록한다. DEV와 동일한 기능 시나리오를 PRD에 적합한 테스트 데이터로 확인한다.
  5. 오류율·응답 시간·DB 상태를 관찰한다. 이 브랜치에 운영 관측성 수집 시스템 전체가 포함되어 있지는 않으므로 조직의 로그·모니터링 절차를 연결한다.
현재 구현은 동일 이미지의 DEV → PRD 승격이 아니다

각 apply + deploy_application=true 실행은 backend와 AI 이미지를 새로 빌드한다. tag는 sha-<commit SHA>-<run ID>-<attempt>다. 같은 소스 SHA를 다시 빌드해도 Dockerfile의 가변 베이스 tag, 외부 다운로드, 의존성 해석, 빌드 메타데이터가 달라질 수 있다. ECR tag의 immutable 설정은 그 tag를 덮어쓰지 못하게 하지만 다른 두 tag의 이미지 내용이 같다는 뜻은 아니다. 현재 workflow에는 검증된 기존 digest를 입력해 빌드를 생략하는 기능이 없다.

이 차이를 표현할 때 DEV에서 검증한 코드 변경을 PRD에서 다시 빌드했다는 말과 DEV에서 검증한 이미지 digest를 PRD에 그대로 배포했다는 말을 구분한다. tag는 사람이 추적할 이름이고 digest는 이미지 내용의 식별자다. Kubernetes에서 digest를 직접 지정하면 repository@sha256:... 형태를 사용한다. Kubernetes의 digest 고정, ECR tag immutable 설정.

강사 노트상세 강의의 실제 파일과 예제를 함께 열어 값의 입력과 결과를 추적합니다. 확인 문제는 정답을 먼저 보여 주기 전에 각자의 근거를 설명하게 하고, 구현과 확장 학습의 경계를 확인합니다.

확장 설계 · 동일 Digest 승격

교육용 확장 · 이 브랜치에 미구현 사용자가 개발·테스트한 이미지 자체를 DEV와 PRD에 배포하려면 이미지 생성과 이미지 선택을 분리한다. 후보 이미지를 한 번 빌드하고 digest를 기록한 다음, 그 digest로 DEV를 테스트하고 승인된 결과를 PRD에 전달한다. 환경별 DB 주소·Secret·replica 수는 바꿔도 앱 이미지 digest는 바꾸지 않는다.

release 기록에는 최소한 repository, source SHA, build run ID와 attempt, backend/AI/선택형 embedding digest, Helm chart 버전 또는 commit, DEV 검증 실행 번호를 넣는다. 최신 성공 실행처럼 움직이는 대상을 찾지 말고 한 실행을 명시적으로 선택한다. PRD 승인자는 해당 소스가 운영 branch에 반영된 검토 대상인지, DEV 결과가 바로 그 digest와 chart를 검증했는지 확인한다. 기록 자체에는 비밀값이나 Terraform plan/state를 넣지 않는다.

변경 예시 ① 빌드 step에 id를 부여하여 digest를 수집 · 기존 workflow 수정안

- name: Build and publish backend
  id: backend_image
  if: steps.config.outputs.deploy_application == 'true'
  uses: docker/build-push-action@v6
  with:
    context: ./backend
    platforms: linux/amd64

- name: Build and publish AI

- name: Record candidate image identities

    [[ "$AI_DIGEST" =~ ^sha256:[a-f0-9]{64}$ ]]

이것은 완성된 release workflow가 아니라 digest를 얻는 부분의 수정안이다. repository·chart·검증 결과를 추가하고 실제 DEV에도 이 digest를 배포한 뒤 성공한 기록만 승격 대상으로 게시해야 한다. Buildx action은 digest output을 제공한다. 이미지 manifest 또는 image index의 digest와 실제 노드가 고른 platform manifest digest는 층위가 다를 수 있으므로 비교 대상을 명확히 기록한다. Buildx action outputs.

현재 chart에 --set images.backend.digest=...만 추가하면 동작하지 않는다. 현재 helper는 항상 repository:tag를 만들고 values schema는 알 수 없는 digest 필드를 거부한다. runtime.py도 --image-tag만 받는다. 세 곳을 함께 바꿔야 한다.

변경 예시 ② tag와 digest를 지원하는 Helm helper · digest 우선 정책

{{- define "trippilot.image" -}}
{{- $image := index .root.Values.images .component -}}
{{- $repo := required "image repository is required" $image.repository -}}
{{- if $image.digest -}}
  {{- if not (regexMatch "^sha256:[a-f0-9]{64}$" $image.digest) -}}
    {{- fail "image digest must be sha256 followed by 64 lowercase hex characters" -}}
  {{- end -}}
  {{- printf "%s@%s" $repo $image.digest | quote -}}
{{- else -}}
  {{- printf "%s:%s" $repo (required "image tag is required" $image.tag) | quote -}}
{{- end -}}
{{- end -}}

함께 바꿀 schema에는 각 이미지의 선택적 digest 문자열과 ^sha256:[a-f0-9]{64}$ 패턴을 추가한다. 활성 이미지의 repository는 필수로 두고 nonempty tag 또는 유효 digest 중 하나는 반드시 존재하게 anyOf로 검증한다. embedding의 이미지 식별자 필수 검증은 embedding.enabled=true일 때만 적용한다. 비활성 embedding은 현재 기본 values나 Helm lint에서 빈 값을 허용해야 한다. gateway가 기존 tag 형식으로도 동작하도록 호환성을 유지하고 활성 앱 이미지에는 승격 시 digest를 필수로 하는 별도 검증을 둔다. 값이 둘 다 있으면 위 helper는 digest를 우선한다.

runtime에는 검증된 release 파일을 받아 backend·AI·embedding별 digest를 렌더링하는 옵션을 추가한다. 단일 공통 tag만 받는 현재 인터페이스로는 구성요소별 digest를 표현할 수 없다. 입력 repository는 Terraform output의 대상 환경 ECR과 일치시키고 임의 공개 registry URL을 허용하지 않는다. 이때 PRD values의 replica·Secret·DB 주소는 계속 PRD 값을 사용한다.

교육용 복사 예시 · 별도 구현·권한·인증이 필요한 단계

# 양쪽 ECR 인증은 별도로 구성하고 토큰을 로그에 출력하지 않는다.
# skopeo 설치와 최소 권한 Role 준비가 필요하다.
skopeo copy --all --preserve-digests \
  "docker://$SOURCE_REPOSITORY@$BACKEND_DIGEST" \
  "docker://$TARGET_REPOSITORY:$RELEASE_TAG"

# 현재 AWS CLI 인증이 목적지 계정인지 먼저 검증한 상태여야 한다.
copied_digest=$(aws ecr describe-images \
  --region "$TARGET_REGION" \
  --repository-name "$TARGET_REPOSITORY_NAME" \
  --image-ids "imageTag=$RELEASE_TAG" \
  --query 'imageDetails[0].imageDigest' --output text)

test "$copied_digest" = "$BACKEND_DIGEST"

--all은 image index가 가리키는 이미지까지 복사하고 --preserve-digests는 digest 보존이 불가능할 때 실패하도록 요청한다. 임의로 다시 build하거나 manifest 형식을 바꿔놓고 같은 이미지라고 기록하지 않는다. backend·AI·활성 embedding 모두 확인한다. Skopeo copy 공식 옵션.

동일 앱 digest는 실행 환경 전체의 동일성까지 보장하지 않는다. PRD에는 다른 DB 데이터·Secret·외부 API·네트워크 정책이 있고 gateway·DB 초기화 Job 같은 보조 이미지도 있다. 엄격한 재현성을 원하면 Dockerfile의 베이스 digest, 잠금 파일, 빌드 도구, chart·보조 이미지와 migration 버전까지 release 기록에 연결한다. DB 변경은 이전 앱과 새 앱이 잠시 공존하는 rolling update를 고려해 호환되는 컬럼 추가 → 앱 전환 → 나중에 오래된 컬럼 제거처럼 단계적으로 설계한다.

Helm atomic이 되돌리는 범위

기존 release의 Helm upgrade 실패에는 이전 revision으로 되돌리는 동작이 적용되지만 최초 설치에는 돌아갈 이전 revision이 없다. 더구나 현재 내부 smoke는 Helm 성공 다음의 별도 step이다. smoke step에서만 실패했다면 앞서 성공한 Helm 변경이 자동으로 rollback되지는 않는다. Terraform 변경, Secrets Manager/Kubernetes Secret 동기화, 이미 실행된 DB migration도 Helm rollback 범위 밖이다.

현재 저장소의 일반 앱 복구 절차는 배포 branch에 revert commit을 만들고 CI 검증 후 수동 배포를 다시 실행하는 것이다. 이 역시 이미지를 새로 빌드하는 복구이며 예전 digest를 그대로 재사용하는 기능은 아니다. 운영자가 즉시 이전 Helm revision으로 복구해야 한다면 조직의 장애 대응 권한과 runbook 아래에서 아래 작업을 수행하고 Git의 배포 정의도 후속 수정해 다음 배포가 다시 잘못된 상태를 만들지 않게 한다.

교육용 장애 대응 예시 · 실제 실행은 지정 운영자만

# history에서 정상 상태였던 revision을 확인한 뒤 지정한다.
helm --kube-context "$EKS_CONTEXT" -n trippilot history trippilot
helm --kube-context "$EKS_CONTEXT" -n trippilot rollback \
  trippilot "$GOOD_REVISION" --wait --timeout 20m

Helm revision은 chart·values를 되돌리지만 외부에서 이미 바뀐 DB 스키마·암호·서비스 데이터는 되돌리지 못한다. 이전 앱이 현재 DB와 호환되는지 확인하고 외부·내부 검증을 반복한다. DB 복구는 백업·시점 복원과 데이터 손실 허용 범위를 판단하는 별도 운영 절차다. PRD RDS에는 삭제 보호가 있으며 이 브랜치에는 전체 destroy workflow가 제공되지 않는다. 로컬 just down은 kind 데이터까지 삭제하지만 AWS 정리 명령은 아니다. Helm rollback 동작.

강사 노트로그를 공유할 때 비밀값을 포함하지 않습니다. EKS Pod 조회는 올바른 계정·리전·클러스터 컨텍스트인지 먼저 확인합니다. 상태 잠금이 남아 있다고 곧바로 강제 해제하지 말고 같은 환경에서 실행 중인 배포가 있는지 확인합니다.

확인 · 한 페이지 배포 기록

문제 1. develop의 backend CI가 GHCR push까지 성공했다. AWS DEV 수동 배포는 그 이미지를 그대로 사용하는가?

해설 보기

아니다. 현재 AWS workflow는 checkout한 코드와 backend Dockerfile로 ECR 이미지를 다시 빌드한다. 기존 앱 CI 통과와 AWS 배포 이미지의 digest 동일성은 별개의 사실이다.

문제 2. just update를 실행했는데 backend 코드 수정이 보이지 않는다. 먼저 확인할 것은?

해설 보기

just backend-build로 새 JAR를 생성·stage했는지 확인한다. update는 이미지 생성·Pod 교체를 하지만 Gradle bootJar를 만드는 의존성이 없다. 이어 실제 kind context와 Pod image를 확인한다.

문제 3. PRD reviewer가 승인했으므로 이번 apply에 사용된 plan 파일을 이미 검토했다고 말할 수 있는가?

해설 보기

현재는 말할 수 없다. Environment 승인은 deploy job 시작 전에 이루어지고 해당 job 안에서 plan이 만들어진다. 별도 plan 실행의 검토와 이번 run의 plan 동일성은 자동 보장되지 않는다.

문제 4. DEV·PRD 이미지 tag에 같은 commit SHA가 포함되어 있다. 동일 이미지 검증의 충분한 증거인가?

해설 보기

아니다. 같은 소스를 재빌드해도 base·dependency·build metadata 차이로 digest가 달라질 수 있다. build once 후 원본과 대상 ECR digest, DEV 테스트 기록을 연결해야 한다.

문제 5. Helm step은 성공했지만 뒤의 smoke step이 실패했다. 자동 롤백이 끝났다고 보고해도 되는가?

해설 보기

안 된다. atomic은 Helm 명령 자체의 실패에 적용된다. 현재 smoke는 별도 step이므로 실제 Helm revision과 Pod 상태를 확인하고 복구 여부를 결정한다. DB migration과 인프라도 별도 상태다.

문제 6. 외부 /healthz는 200인데 /actuator/health는 404다. gateway 고장인가?

해설 보기

현재 gateway 정책상 정상이다. 외부에는 API와 healthz만 열고 internal·Actuator 경로는 막는다. backend readiness는 클러스터 내부 Service로 확인한다. 업무 API 정상 여부는 별도 시나리오로 검사한다.

제출물 — 비밀값 없이 한 페이지 배포 기록을 작성한다.

  1. 로컬 테스트 대상 SHA, 실행 명령과 결과, 로컬 image·AWS image 경로의 차이.
  2. DEV/PRD의 branch·계정·state·DB·도메인 매핑. 수업 외부 공유본의 계정 정보는 필요한 범위만 남긴다.
  3. 샘플 AWS 실행의 첫 검증 step, image tag, Helm 상태, 내부 smoke와 외부 TLS 결과.
  4. 동일 digest 승격을 위해 바꿀 workflow·runtime·Helm schema/helper·IAM 목록.
  5. smoke 실패 + DB migration 완료 상황의 조사 순서와 복구할 수 없는 범위.

채점 기준: 현재 구현과 제안 설계의 구분 25점, 명령·실행 순서 정확성 25점, 이미지 출처·동일성 설명 25점, 검증·복구 경계 설명 25점. 실제 AWS 리소스 생성 여부는 점수에 포함하지 않는다.

다시 찾아볼 저장소 문서: AWS EKS 배포 가이드, bootstrap 가이드, 로컬 개발 안내. 공식 자료는 각 개념 가까이에 연결했으며 도구 버전은 이 브랜치의 Terraform 1.13.5·Helm 3.19.0 구성을 기준으로 설명했다.

강사 노트추가 과제: 구성도에서 Terraform이 만들지 않는 항목 3개 찾기, DEV와 PRD 차이 3개 설명하기, 수동 배포 로그에서 각 단계의 시작점을 찾기. 실제 AWS를 생성하지 않아도 코드와 자료만으로 수행할 수 있습니다.

Terraform 리소스 주소와 실제 원격 객체를 대응시키는 상태 데이터.
Backend
Terraform state를 보관하는 방식. 이 브랜치는 환경별 S3 버킷을 사용한다.
Plan
현재 상태와 설정을 비교한 변경 계획. 실제 서비스 생성·수정은 apply 단계에서 수행한다.
Workflow
이벤트에 따라 실행할 Job들을 정의한 GitHub Actions YAML 파일.
Runner
Job의 Step을 실행하는 컴퓨팅 환경.
OIDC
외부 실행 주체의 신원을 검증하는 표준. GitHub의 신원 토큰을 AWS의 임시 자격증명으로 교환하는 데 사용한다.
Tag / digest
Tag는 이미지에 붙인 이름이고 digest는 콘텐츠를 식별하는 해시다. immutable tag는 덮어쓰기를 막지만 다른 빌드의 동일성을 증명하지는 않는다.
ECR / EKS
ECR은 컨테이너 이미지 레지스트리, EKS는 관리형 Kubernetes 서비스다.
Helm
템플릿과 values로 Kubernetes 매니페스트를 구성하고 release를 관리하는 도구.
Promotion
검증한 릴리스 아티팩트를 다음 환경으로 전달하는 과정. 같은 소스의 재빌드와는 구분한다.
