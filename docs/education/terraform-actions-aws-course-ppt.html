01 / 먼저 배포할 AWS 전체 모습

TripPilot이 올라갈 AWS 구성도

Terraform: 네트워크·EKS·DB·관리 서비스앱 배포: NLB·Pod별도 준비: bootstrap·ACM·DNS
큰 경계인 VPC는 우리 서비스의 네트워크 공간입니다. EKS 노드는 private compute에, DB와 캐시는 isolated data에 있습니다. EKS 제어 영역과 ECR·Secrets Manager·CloudWatch는 AWS 관리 서비스로 구분합니다. S3 state와 IAM 역할은 bootstrap이 만듭니다. 그림의 선은 성격에 따라 연결·관리·요청 흐름을 나타냅니다. 정확한 Terraform 참조 관계는 뒤쪽의 ‘도구와 원본 그래프’에서 별도로 봅니다.

  4. 04PostgreSQLbackend가 앱 데이터를

Redis는 인프라에 준비되어 있지만 현재 backend 캐시 어댑터는 아직 없습니다. AI의 pgvector 검색과 임베딩 서비스는 배포 옵션을 켰을 때 연결됩니다.

외부에서 들어오는 입구는 NLB입니다. AI와 DB는 내부에서 연결합니다.

코드: services.yaml, gateway-config.yaml · AWS 배포 가이드

여기서 gateway는 이 프로젝트의 nginx 애플리케이션 이름입니다. AWS API Gateway 서비스를 뜻하지 않습니다. Expo 모바일 앱은 EKS에 올리지 않습니다. EKS 배포 대상은 gateway, backend, AI, 선택형 embedding입니다. 외부 /internal·Actuator 경로는 gateway가 공개하지 않습니다.

01 / 네트워크 읽기

서브넷을 세 구역으로 나눈 이유

VPC는 서비스 전용 네트워크, 서브넷은 그 안을 나눈 작은 구역입니다.

구역배치하는 것인터넷과의 관계
PublicNAT, 앱 배포 후 NLBInternet Gateway로 나가는 경로
Private computeEKS 노드와 앱 Pod외부 통신은 NAT를 통해 나감
Isolated dataRDS PostgreSQL, Redis인터넷/NAT 기본 경로 없음

NAT는 내부 앱이 밖으로 요청을 보낼 때 쓰는 출구입니다.

코드: network.tf, data.tf

AZ(가용 영역)는 한 리전 안의 분리된 운영 구역입니다. 각 AZ마다 세 종류의 서브넷을 만듭니다. Public이라는 이름만으로 모든 리소스가 외부에 공개되지는 않습니다. 실제 접근은 주소, 경로, 보안 그룹 설정에 달려 있습니다. RDS 5432와 Redis 6379는 EKS 클러스터 보안 그룹에서만 들어오도록 허용하며 TLS를 사용합니다. EKS 노드는 private이지만 관리 API에는 public endpoint도 있습니다.

02 / TERRAFORM

원하는 AWS 모습을 코드로 적기

콘솔에서 클릭했던 설정을 파일에 적어 두면
동료와 검토하고, 다른 환경에도 다시 적용할 수 있습니다.

  1. 01코드어떤 자원이 필요한가?
  2. 02State어떤 AWS 자원을
    관리하고 있는가?
  3. 03Plan현재와 비교하면
    무엇이 달라지는가?

“VPC를 하나 클릭해서 만들어라”보다 “이 VPC가 있어야 한다”에 가깝습니다.

이 방식을 IaC(Infrastructure as Code), 인프라를 코드로 관리하기라고 합니다. Terraform은 코드와 state, provider를 통해 읽은 실제 정보를 비교합니다. 콘솔에서 누군가 설정을 바꾸면 코드와 실제가 달라질 수 있는데, 이를 drift라고 합니다. 같은 코드를 다시 적용할 때도 plan을 확인합니다.

02 / STEP 1 · 파일 찾기

처음에는 이 파일들만 따라갑니다

infra/terraform/
stack/
  versions.tf       # 도구 설정
  variables.tf      # 입력값
  network.tf        # 네트워크
  eks.tf            # 앱 실행 공간
  data.tf           # DB와 캐시
  registry-secrets.tf
  outputs.tf        # 다음 단계에 전달
environments/
  dev.tfvars
  prd.tfvars
  1. 환경값부터 읽기dev.tfvars에서 크기와 개수를 확인합니다.
  2. 그림과 파일 연결하기VPC는 network.tf, EKS는 eks.tf에 있습니다.
  3. 출력 찾기outputs.tf에서 배포에 쓸 이름·주소를 봅니다.

같은 폴더의 .tf 파일은 함께 읽습니다. 파일 이름순으로 실행하지 않습니다.

stack 폴더가 이번 실행의 root module입니다. Terraform의 module은 함께 평가하는 코드 묶음입니다. 이 프로젝트는 외부 VPC 모듈을 호출하지 않고 리소스를 직접 정의합니다. data.tf라는 이름은 여기서 DB·캐시를 묶기 위한 분류이지, data 블록만 담는다는 뜻이 아닙니다.

02 / STEP 2 · 코드 한 블록 읽기

이 여섯 줄이 VPC 하나를 정의합니다

network.tf · 실제 코드
resource "aws_vpc" "this" {
  cidr_block = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support = true
  tags = { Name = local.name }
}
  • resource관리할 자원을 선언합니다.
  • aws_vpc / this자원 종류 / 코드 안에서 부르는 이름
  • var.vpc_cidr환경에서 받은 네트워크 주소 범위
  • tags.NameAWS에 표시할 이름 태그

“이 주소 범위와 이름을 가진 VPC가 필요하다”라고 읽으면 됩니다.

코드: network.tf · 실제 내용의 공백만 정리

이 문법의 이름은 HCL입니다. 문자열에는 따옴표, true·false와 숫자에는 따옴표를 쓰지 않습니다. resource 뒤의 aws_vpc는 종류, this는 코드에서 참조할 이름입니다. this 자체가 AWS 이름이 되는 것은 아닙니다. aws_vpc.this.id로 AWS가 만든 VPC ID를 읽습니다.

02 / STEP 3 · 값의 흐름

dev라는 값이 이름으로 바뀌는 과정

실제 코드 발췌 · 중간 설정 생략
# dev.tfvars: 입력할 값
environment = "dev"

# network.tf: 계산한 이름
locals {
  name = "trippilot-${var.environment}"
}

# eks.tf: 이름을 사용
name = local.name
  1. Variable · 입력 자리variables.tf가 environment를 받도록 선언합니다.
  2. tfvars · 실제 입력값DEV 실행에서는 dev.tfvars를 선택합니다.
  3. Local · 계산한 값local.name은 trippilot-dev가 됩니다.
  4. Output · 전달할 결과EKS 이름을 Actions의 다음 단계가 받습니다.
prd.tfvars를 선택하면 같은 코드로 trippilot-prd를 만듭니다. workflow가 -var-file 옵션으로 환경 파일 하나를 지정합니다. AWS 계정 ID와 배포 역할 ARN은 GitHub Environment 변수에서 TF_VAR_ 환경변수로 전달합니다. outputs.tf는 클러스터 이름, ECR 주소, DB 주소 등을 다음 작업에 전달합니다.

02 / STEP 4 · 연결과 순서

“이 VPC 안에 서브넷을 만든다”

network.tf · 연결을 보여주는 발췌
resource "aws_subnet" "private" {
  count = var.availability_zone_count

  vpc_id = aws_vpc.this.id
  availability_zone = local.azs[count.index]
  # CIDR과 태그 등 생략
}
  • 참조가 연결을 만듭니다서브넷은 VPC의 ID가 필요합니다.
  • 연결이 순서를 만듭니다Terraform은 VPC를 준비한 뒤 서브넷을 만듭니다.
  • graph로 확인합니다코드의 참조 관계를 DOT 그래프로 출력할 수 있습니다.

코드 속 ID 참조가 AWS 구성도의 연결선이 되는 단서입니다.

실제 terraform graph 결과 열기 · 의존성 화살표는 요청 트래픽의 방향과 다릅니다.

직접 참조에서 드러나지 않는 선행 조건은 depends_on으로 적습니다. 이 프로젝트의 EKS는 NAT 경로와 로그 그룹이 준비되기를 기다립니다. graph 원본은 의존하는 자원에서 필요한 자원 쪽으로 선을 그립니다. 전체 AWS 그림의 사용자 요청 방향과 혼동하지 마세요.

02 / STEP 6 · 연결 담당과 기록 담당

Provider와 State의 역할

Provider · AWS와 대화

provider "aws" {
  region = var.aws_region
  # 계정 검사·태그 생략
}

AWS API를 통해 자원을 조회하고 변경합니다.

State · 자원 연결 기록

# terraform 블록 내부
backend "s3" {
  encrypt = true
  use_lockfile = true
}

aws_vpc.this가 실제 어떤 VPC인지 기억합니다.

DEV와 PRD는 서로 다른 S3 버킷을 사용합니다. 각 버킷 안의 파일 이름은 terraform.tfstate로 같습니다.

코드: versions.tf · S3 backend 공식 문서

Backend는 state를 어디에 저장할지 정합니다. AWS provider를 쓴다는 이유만으로 state가 S3에 저장되지는 않습니다. S3 버킷 이름과 리전은 workflow의 init 명령이 전달합니다. 잠금 파일은 동시 수정을 막고, 버전 관리는 이전 state 복구를 돕습니다. State에는 민감한 정보가 들어갈 수 있으므로 공개하지 않습니다. sensitive 표시만으로 저장 자체를 막을 수는 없습니다.

02 / STEP 7 · 명령 읽기

준비하고, 검사하고, 비교한 뒤 적용

명령쉬운 설명이때 확인할 것
init실행 준비Provider 설치와 backend 연결
validate코드 검사문법과 구성에 모순이 없는지
plan변경 미리보기만들 것, 바꿀 것, 지울 것
apply실제 변경대상 환경과 계획이 맞는지

이 프로젝트의 AWS plan은 AWS 조회와 원격 state 잠금을 사용합니다. 자격증명 없는 로컬 검사와는 다릅니다.

validate 성공은 AWS 배포 성공을 보장하지 않습니다.

권한, 계정 제한, 서비스 할당량, 실제 리전 지원 여부 등은 AWS와 연결해야 확인할 수 있습니다. apply는 자원을 만들고 비용을 발생시킬 수 있습니다. 수업의 로컬 단계에서는 실제 AWS를 변경하지 않고, 실제 변경은 환경 준비 후 Actions에서 수행합니다.

02 / STEP 8 · PLAN 읽기

더하기보다, 삭제와 교체를 먼저 확인

설명용 예시 · 실제 실행 결과가 아님
+ aws_vpc.this
~ aws_db_instance.postgres
-/+ aws_subnet.private[0]

Plan: 2 to add,
      1 to change,
      1 to destroy.
  • + 생성새 자원을 만듭니다.
  • ~ 수정기존 자원의 설정을 바꿉니다.
  • - 삭제 / -/+ 교체기존 자원이 사라지거나 새로 만들어집니다.

줄 한 개를 바꿔도 운영 영향은 클 수 있습니다. 이름과 변경 속성까지 읽습니다.

2 to add에는 VPC 신규 생성 1개와 서브넷 교체에 따른 생성 1개가 들어갑니다. replacement는 삭제 후 생성(-/+)이나 생성 후 삭제(+/-)로 보일 수 있습니다. 특히 DB, 서브넷, 클러스터의 변경을 확인합니다. 예시의 숫자와 자원은 문법을 설명하기 위한 것이며 이 프로젝트의 실제 plan 결과가 아닙니다.

02 / 실습 A · AWS 변경 없이 검사

  1. 기대 결과형식 검사, 구성 검사, DEV·PRD 설계 조건 테스트가 통과합니다.
  2. 왜 AWS 계정 없이 되나요?테스트가 mock provider를 사용하고 S3 backend 연결을 끕니다.

코드: environments.tftest.hcl · 첫 provider 다운로드에는 인터넷이 필요합니다.

mock은 실제 AWS 응답 대신 테스트용 응답을 제공하는 장치입니다. 이 실습은 실제 네트워크 연결이나 AWS 권한 검증까지 해주지는 않습니다. 저장소가 고정한 provider lock을 유지하며, 테스트를 위해 apply나 destroy를 실행할 필요는 없습니다. Terraform CLI 버전은 현재 workflow의 설정을 기준으로 적었습니다.

03 / GITHUB ACTIONS

배포 순서를 실행 가능한 작업표로

사람이 매번 명령을 기억하지 않아도
같은 검사와 배포 순서를 실행하도록 YAML에 적습니다.

  1. EVENT언제 시작?이 프로젝트는
    Run workflow 클릭
  2. WORKFLOW어떤 작업표?aws-deploy.yml
    전체 실행 정의
  3. JOB어떤 작업 묶음?validate와 deploy
    각각 runner에서 실행
  4. STEP무엇을 실행?checkout, 검사,
    plan, apply 등
Runner는 작업을 실행하는 컴퓨터입니다. workflow 하나에 여러 job이 있고, job 안의 step은 순서대로 실행합니다. 서로 다른 job은 기본적으로 별도 실행 환경이므로 작업 폴더가 자동 공유되지 않습니다. uses는 준비된 action을 쓰고, run은 셸 명령을 실행합니다.

03 / STEP 1 · 두 JOB 읽기

검사가 통과해야 deploy가 시작됩니다

aws-deploy.yml · 구조를 줄인 발췌
on:
  workflow_dispatch:
    # 실행 입력 생략
jobs:
  validate:
    runs-on: ubuntu-latest
    # 검사 steps 생략
  deploy:
    needs: validate
    environment: ${{ inputs.environment }}
    # 배포 steps 생략
  • validateTerraform·배포 도구·Helm 구성을 검사합니다.
  • needs: validate검사 job이 성공할 때까지 기다립니다.
  • environmentdev 또는 prd의 변수와 보호 규칙을 사용합니다.

코드: aws-deploy.yml

validate는 Python 테스트와 coverage, bootstrap/chart 검사, Helm lint, Terraform fmt·validate·mock test를 수행합니다. apply와 앱 배포를 함께 선택하면 backend 종료 설정 테스트도 추가됩니다. Environment에 required reviewers를 설정했다면 deploy job 시작 전에 승인을 받습니다. 이는 그 실행에서 아직 만들지 않은 plan을 승인하는 단계는 아닙니다.

03 / STEP 2 · STEP 읽기

uses는 도구 사용, run은 명령 실행

aws-deploy.yml · validate job 발췌
steps:
  - uses: actions/checkout@v4

  # 중간 setup step 생략
  - name: Validate Terraform offline
    working-directory: infra/terraform/stack
    run: |
      terraform fmt -check -recursive ..
      terraform init -backend=false -lockfile=readonly
      terraform validate
      terraform test
  1. checkout선택한 커밋의 저장소 파일을 가져옵니다.
  2. working-directory명령을 실행할 폴더를 지정합니다.
  3. run: |여러 줄의 셸 명령을 순서대로 실행합니다.
위 예제는 실제 workflow에서 중간 도구 설치 단계를 생략한 발췌입니다. 그대로 새 workflow로 복사하는 완성 예제가 아닙니다. setup-terraform step이 먼저 Terraform CLI를 설치해야 run의 명령을 사용할 수 있습니다.

03 / STEP 3 · 실행 입력

Run workflow에서 네 가지를 고릅니다

입력값의미
environmentdev / prd어느 환경에 실행할지
modeplan / apply미리보기만 할지, 실제 변경할지
deploy_applicationtrue / falseapply 후 앱도 빌드·배포할지
embedding_enabledtrue / false선택형 임베딩 서비스도 배포할지

첫 확인: dev + plan
인프라 생성: dev + apply + deploy_application=false

plan을 고르면 앱 배포 옵션을 켜도 앱은 배포하지 않습니다.

mode 기본값은 plan, deploy_application 기본값은 true, embedding_enabled 기본값은 false입니다. workflow_config.py가 조합을 검사하여 실제 앱 배포 여부를 결정합니다. 임베딩을 활성화하면 메모리 비용이 늘어납니다. AWS 변경은 수동 입력으로만 시작합니다.

03 / STEP 4 · 자동 검사와 수동 배포

CI 성공 후 AWS 배포는 직접 시작합니다

기존 backend / AI CI

  • push·PR 등으로 코드 검사
  • develop push에서는 GHCR 발행
  • 개발 중 문제를 발견하는 경로

AWS 배포 workflow

  • Run workflow로 수동 시작
  • 선택한 소스를 다시 빌드해 ECR 발행
  • AWS 인프라와 앱을 변경하는 경로

현재 AWS workflow에는 push·PR·schedule·다른 CI 완료를 통한 자동 배포 트리거가 없습니다.

코드: backend-ci.yml, ai-ci.yml, aws-deploy.yml

기존 CI는 develop push, develop/main 대상 PR, 수동 실행을 지원합니다. GHCR 이미지가 ECR로 자동 복사되는 구조가 아닙니다. AWS workflow에는 자체 validate job이 있지만 기존 CI 성공을 필수로 연결하는 needs 관계는 없습니다. PRD도 DEV에서 만든 이미지를 그대로 승격하는 기능 없이 선택한 소스를 다시 빌드합니다.

03 / STEP 5 · AWS 인증

OIDC로 잠시 사용할 권한을 받습니다

  1. GitHub가 실행의 신원을 증명어느 저장소의 어느 Environment에서 실행하는지 담은 토큰을 발급합니다.
  2. AWS가 신뢰 조건을 확인허용된 저장소와 환경인지 IAM 역할의 정책으로 검사합니다.
  3. 짧은 시간 유효한 AWS 자격증명 발급이 권한으로 Terraform·ECR·EKS 작업을 실행합니다.

이 workflow는 GitHub에 장기 AWS 액세스 키를 저장하지 않습니다.

코드: bootstrap-trust.example.json · GitHub OIDC 공식 문서

deploy job의 id-token: write는 OIDC 토큰 요청 권한입니다. 그것만으로 AWS 작업 권한이 생기지는 않습니다. AWS_ROLE_ARN으로 지정한 IAM 역할의 신뢰 정책과 권한 정책을 통과해야 합니다. Environment 기반 subject에는 브랜치가 포함되지 않으므로 GitHub Environment의 배포 브랜치 제한도 설정합니다.

04 / STEP 1 · 처음 한 번 준비

Terraform보다 먼저 필요한 것

State를 저장할 S3와 AWS 작업 권한이 있어야 Terraform을 시작할 수 있습니다.

  1. AWS 관리자GitHub OIDC provider와 환경별 bootstrap 역할을 준비합니다.
  2. AWS bootstrap (manual) 실행CloudFormation이 S3 state, 배포 역할, EKS cluster/node 역할을 만듭니다.
  3. 출력값 등록DeploymentRoleArn을 같은 GitHub Environment의 AWS_ROLE_ARN에 넣습니다.

실행 안내: AWS 초기 설정 가이드 · 코드: aws-bootstrap.yml

아무 AWS 권한이 없는 workflow가 자신의 최초 권한을 만들 수는 없습니다. 그래서 관리자 설정과 bootstrap이 먼저입니다. 환경별 최초 설정 후에는 일반 배포 workflow를 사용합니다. bootstrap을 다시 실행하면 CloudFormation stack을 갱신합니다. bootstrap 역할은 권한 위임을 다루므로 일반 배포 역할과 구분해서 관리합니다.

04 / STEP 2 · GITHUB 설정

dev와 prd의 설정을 따로 보관합니다

Environment Variable무엇을 넣나요?
AWS_ACCOUNT_ID대상 AWS 계정의 12자리 ID
AWS_REGION리전. 생략하면 ap-northeast-2
AWS_BOOTSTRAP_ROLE_ARN최초 bootstrap에 사용할 기존 역할
AWS_ROLE_ARNbootstrap 출력의 일반 배포 역할
ACM_CERTIFICATE_ARN앱 배포 전에 검증 완료한 인증서
API_HOSTNAME예: api-dev.example.com

기본 배포 브랜치는 DEV develop, PRD main입니다. Environment의 배포 브랜치 제한도 같은 값으로 설정합니다.

저장소 Settings → Environments에서 dev와 prd를 만듭니다. 브랜치가 다르면 선택 변수 DEPLOY_BRANCH와 Environment 규칙을 함께 바꿉니다. 기존 OIDC provider ARN을 지정하는 AWS_GITHUB_OIDC_PROVIDER_ARN은 선택입니다. PRD required reviewers도 설정할 수 있습니다. Run workflow 버튼은 workflow 파일이 저장소 기본 브랜치에 있어야 나타납니다.

04 / STEP 3 · DEV 미리보기

첫 실행은 dev + plan

  1. Actions에서 AWS / Terraform and EKS deploy 선택배포할 develop 브랜치를 선택합니다.
  2. environment=dev, mode=plan으로 실행validate 통과 후 AWS 인증과 S3 state 연결을 진행합니다.
  3. Terraform plan 로그 확인리전·환경 이름, 추가·수정·삭제 자원을 읽습니다.

계획 파일의 범위: 이후 apply를 새로 실행하면 그 실행 안에서 새 plan을 만듭니다. 이전 plan 실행의 파일을 이어받지 않습니다.

처음에는 기존 data source인 cluster/node IAM 역할도 조회하므로 bootstrap이 완료되어 있어야 합니다. plan은 AWS 자원을 생성하지 않지만 조회와 state 잠금을 사용합니다. required reviewers가 있어도 새 plan 생성 이후에 한 번 더 멈추는 승인 단계는 현재 구현되어 있지 않습니다.

04 / STEP 4 · AWS 공간 생성

apply로 인프라부터 준비합니다

두 번째 실행: dev / apply / deploy_application=false

이번 실행이 하는 일

  1. 새 plan 생성
  2. 같은 실행에서 저장한 plan 적용
  3. VPC·EKS·RDS·ECR 등 준비

완료 후 확인할 것

  • 환경 이름이 trippilot-dev인지
  • Secrets Manager 저장소가 생겼는지
  • 앱용 ACM 인증서가 ISSUED인지

자원이 만들어지면 EKS·NAT·RDS 등의 비용이 발생합니다. 인프라만 생성한 상태에서는 앱과 NLB가 아직 없을 수 있습니다.

이 순서는 초보자가 문제 위치를 나누어 확인하기 위한 실습 경로입니다. 인증서와 도메인이 준비되어 있다면 첫 apply에서 앱도 함께 배포할 수 있습니다. 별도 전체 destroy workflow는 제공하지 않습니다. PRD는 삭제 보호를 사용하므로 실습 중 임의로 끄지 않습니다.

04 / STEP 5 · 앱 포장

코드를 이미지로 만들어 ECR에 보관

다음 실행에서 apply + deploy_application=true를 선택합니다.

  1. 01Terraform outputs생성된 ECR 저장소 주소와
    EKS 이름을 읽습니다.
  2. 02Docker buildbackend와 AI 코드를
    컨테이너 이미지로 만듭니다.
  3. 03ECR push환경별 저장소에
    버전 태그와 함께 저장합니다.
  4. 04Helm에 전달어떤 이미지 주소와 태그를
    실행할지 지정합니다.

이미지 태그: sha-<commit>-<run_id>-<attempt>
ECR은 같은 태그의 덮어쓰기를 막습니다.

이미지는 linux/amd64로 빌드합니다. 임베딩 이미지는 embedding_enabled=true일 때만 빌드합니다. 이미지 태그에 실행 번호까지 넣어서 workflow 재실행이 기존 버전을 덮어쓰지 않게 합니다. ECR 주소와 이미지 태그는 Helm values에 들어가지만 비밀값은 따로 처리합니다.

04 / STEP 6 · 비밀값과 DB 준비

앱 실행 전에 로그인 정보와 DB를 준비

  1. Secrets Manager 값 확인Terraform은 저장소를 만들고, 배포 도구가 값을 읽습니다.
  2. Kubernetes Secret으로 전달빈 저장소의 DB 암호·서비스 토큰·JWT 키는 배포 도구가 생성합니다.
  3. DB 초기화 Job 실행앱 계정·스키마·AI DB 등을 준비하고 임시 관리자 자격증명을 정리합니다.

외부 LLM·기상·지도 API 키는 직접 준비해야 합니다.

코드: runtime.py, runtime_secrets.py

앱용 저장소는 backend, ai, database, shared 네 개입니다. RDS 관리자 암호는 RDS가 Secrets Manager에서 관리합니다. 앱 Pod에는 관리자 암호를 넘기지 않습니다. Flyway용 app_migrate와 실행용 app_user를 구분합니다. 기존 비밀값은 재사용하며 비밀값 변경 후에는 다시 배포해야 Pod에 반영됩니다. 외부 API 연동과 AI KB 데이터 적재는 별도 준비가 필요합니다.

Pod는 컨테이너를 실행하는 단위입니다. Service는 바뀔 수 있는 Pod 앞에 안정적인 연결 지점을 제공합니다. Helm은 여러 Kubernetes 설정 파일과 환경값을 묶어 설치하는 도구입니다. gateway Service의 annotation에서 internet-facing과 ACM 인증서를 설정합니다. NLB는 여기서 생성되므로 Terraform resource 목록에 직접 나타나지 않습니다.

04 / STEP 8 · 밖에서 접속 확인

마지막 연결은 DNS와 HTTPS

  1. Actions Summary의 NLB DNS 확인생성된 로드 밸런서 주소가 출력됩니다.
  2. API 도메인의 DNS 연결API_HOSTNAME의 CNAME을 NLB 주소로 설정합니다. Route 53 루트 도메인은 Alias를 사용합니다.
  3. 실제 도메인으로 HTTPS 확인DNS 해석과 인증서가 맞는지, API 요청이 성공하는지 봅니다.
도메인 연결 후 · 본인 환경 주소로 바꿔 실행
curl --fail --show-error https://api-dev.example.com/healthz

이 확인은 gateway 응답을 검사합니다. backend·AI 연결은 workflow의 내부 smoke 결과와 실제 API 요청도 함께 확인합니다.

ACM 인증서는 앱 배포 전에 같은 리전·계정에서 발급하고 DNS 검증을 마쳐야 합니다. 앱 배포 후에는 API 도메인을 새 NLB 주소에 연결합니다. 인증서 검증용 DNS 레코드와 API 접속용 DNS 레코드는 역할이 다릅니다. workflow의 내부 smoke 통과만으로 외부 DNS가 올바르다고 판단할 수 없습니다.

04 / 개발부터 운영까지

로컬, DEV, PRD에서 확인하는 것이 다릅니다

단계주요 확인이 프로젝트의 실행 방식
로컬 kind내 컴퓨터에서 서비스 연결just doctor, just up, just health
AWS DEV실제 AWS 권한·네트워크·TLSdevelop에서 dev 수동 plan/apply
AWS PRD운영 규모·보호 설정·배포 결과검토한 main에서 prd 수동 plan/apply

현재 PRD 배포는 선택한 커밋을 다시 빌드합니다. DEV 이미지를 그대로 승격하는 구현은 없습니다.

로컬 안내: deploy/README.md · 로컬 deploy/k8s/와 AWS deploy/eks/는 별도 구성입니다.

로컬은 Docker, kind, kubectl, Helm, Bazel, JDK 등의 도구가 필요하며 just doctor로 확인합니다. just up은 로컬 자원을 만들므로 준비된 개발 환경에서 실행합니다. kind가 통과해도 IAM·RDS·NLB까지 검증한 것은 아닙니다. PRD에서는 Environment 보호 설정과 선택 브랜치를 확인하고, 배포 후 이미지 태그와 실제 API 상태를 기록합니다.

04 / 실패한 STEP에서 시작

빨간색이 된 첫 작업부터 확인합니다

실패 위치먼저 볼 것
validateTerraform 문법, 테스트 결과, Helm 환경값

실패한 위치를 알면 “AWS가 안 된다”를 구체적인 문제로 바꿀 수 있습니다.

로그를 공유할 때 비밀값을 포함하지 않습니다. EKS Pod 조회는 올바른 계정·리전·클러스터 컨텍스트인지 먼저 확인합니다. 상태 잠금이 남아 있다고 곧바로 강제 해제하지 말고 같은 환경에서 실행 중인 배포가 있는지 확인합니다.

04 / 복구 범위

앱 복구와 인프라 복구는 별개입니다

  • Helm 배포 단계가 실패하면--atomic이 기존 release 복구를 시도합니다. 최초 설치 실패에는 설치 내용을 정리합니다.
  • 그 뒤의 smoke가 실패하면배포 전체를 자동으로 되돌리는 동작은 없습니다.
  • Terraform·DB·Secret이 바뀌었다면각 변경의 영향을 따로 확인하고 복구해야 합니다.
  • 앱 코드만 되돌릴 때배포 브랜치에 revert commit을 반영하고 수동 배포합니다.

Git을 되돌려도 DB 데이터가 과거로 돌아가지는 않습니다.

Helm은 --atomic --wait --timeout 20m으로 실행됩니다. Helm 성공 이후 smoke 실패에는 이 atomic 옵션이 적용되지 않습니다. Terraform 변경이나 DB migration도 Helm의 범위 밖입니다. 데이터 삭제를 포함하는 migration은 백업과 별도 복구 계획이 필요합니다.

05 / 코드에서 그림 다시 만들기

선택한 도구: Terraform graph + Graphviz

코드의 의존성 원본

terraform graph가 참조 관계를 DOT로 출력하고, dot이 SVG 그림으로 바꿉니다.

실제 생성한 원본 그래프 열기

발표용 전체 구성도

HCL·tfvars를 읽어 AZ·서브넷·서비스를 묶었습니다. Helm과 bootstrap 경계도 표시했습니다.

DEV 구성도 · PRD 구성도

원본 graph는 자원 의존성을 보여줍니다. 첫 장의 그림은 그 코드에 근거한 학습용 배치도이며, 실제 배포 상태를 조회한 그림은 아닙니다.

도구 비교·설치·재생성 방법 · Terraform graph 공식 문서 · Graphviz 공식 사이트

Rover와 InfraMap 등도 검토했으며, 이 자료에서는 배포 전 코드만으로 로컬에서 재생성할 수 있는 Terraform 공식 graph와 Graphviz를 선택했습니다. graph는 네트워크 패킷 흐름이나 실제 AZ 배치를 자동 확정하는 도구가 아닙니다. 발표용 생성기는 이 저장소 구조에 맞춘 해석을 적용하므로 변경한 코드는 생성 방법 문서와 함께 검토합니다.

05 / 오늘 배운 내용을 내 말로

이 네 가지를 설명하면 됩니다

  1. 사용자 요청이 DB까지 어떻게 가나요?전체 AWS 그림에서 요청 경로를 짚어 봅니다.
  2. Terraform과 Actions는 무엇을 나눠 하나요?설계와 실행 순서를 구분해 봅니다.
  3. plan과 apply는 어떻게 다른가요?새 apply 실행이 어떤 plan을 사용하는지도 설명합니다.
  4. DEV 성공 후 PRD는 어떻게 배포하나요?브랜치·Environment·환경값·수동 실행을 연결합니다.
핵심 답 보기

요청은 NLB, nginx, backend를 거쳐 AI·DB로 이어집니다. Terraform은 AWS 구성을 정의하고 Actions는 작업 순서를 실행합니다. plan은 변경 미리보기, apply는 같은 실행에서 저장한 계획을 적용합니다. PRD는 준비된 main과 prd 설정을 선택해 수동으로 다시 빌드·배포합니다.

추가 과제: 구성도에서 Terraform이 만들지 않는 항목 3개 찾기, DEV와 PRD 차이 3개 설명하기, 수동 배포 로그에서 각 단계의 시작점을 찾기. 실제 AWS를 생성하지 않아도 코드와 자료만으로 수행할 수 있습니다.
