# 개발 8단계 워크플로우

> 모든 개발은 아래 8단계를 따른다. **단, 규모별로 보정**한다 — 한 줄 수정에 8단계를 다 밟는 것은 그 자체가 안티패턴(`anti-patterns.md`)이다.

## 8단계와 산출물 매핑

대부분의 단계는 **이미 우리가 만드는 산출물**로 존재한다. 새 오버헤드가 아니라 "빠진 칸 채우기"다.

| # | 단계 | 산출물(우리 기준) | 위치 |
|---|---|---|---|
| 1 | 기능 정의 · 브레인스토밍 | 계획·논의(선택지 제시) | 이슈 코멘트 / 대화 |
| 2 | 기능 정의서 | 설계문서 | `backend/docs/design/*-설계.md` · `aidlc/.../construction/` |
| 3 | 테스트 시나리오 | 테스트 계획(케이스·불변식·PBT 대상) | 설계문서 내 "테스트" 절 또는 PR |
| 4 | 기능 구현 | 코드 | 각 패키지 |
| 5 | 구현 리포트 | PR "변경 사항" 절 | PR |
| 6 | 테스트 수행 | 단위·ArchUnit·통합(IT) 실행 | CI / 로컬 |
| 7 | 테스트 리포트 | PR "테스트" 절(무엇을 어떻게 검증) | PR |
| 8 | 사용 매뉴얼 | API 계약 · 사용법 | `openapi.yaml` · 엔드포인트/README |

## 규모별 보정

| 변경 규모 | 밟는 단계 |
|---|---|
| **스토리 · 신규 모듈**(예: 숙소 탐색) | 1~8 전체 |
| **버그픽스 · chore · 스키마 조정** | 4·5·6·7 (구현·구현리포트·테스트수행·테스트리포트). 1·2·3·8은 `N/A` |
| **문서만** | 5·7 수준(무엇을·왜) |

원칙: **단계는 목적을 위한 것**이지 의식(儀式)이 아니다. 해당 없는 단계는 PR에서 `N/A`로 명시한다(빠뜨린 게 아니라 판단했음을 남긴다).

## 강제 장치

- **PR 템플릿**(`.github/PULL_REQUEST_TEMPLATE.md`)의 "개발 8단계" 체크리스트가 빠진 칸(특히 우리가 약한 3 테스트시나리오 · 8 사용매뉴얼)을 보이게 한다.
- 실패·실수가 나오면 `anti-patterns.md`에 한 줄 누적(별도 관행).

## 우리가 약한 두 칸 (의식적으로 챙길 것)

- **3 테스트 시나리오**: 구현 전에 "무엇을 어떤 케이스로 검증할지"를 짧게라도 적는다(PBT 대상·엣지 케이스·불변식).
- **8 사용 매뉴얼**: 백엔드는 대개 `openapi.yaml`·엔드포인트 계약. API가 생기면 계약을 갱신한다.
