# 숙소 콘텐츠 수집 설계 — 사진·주소를 어디서 가져오나

- **작성**: 2026-09-21 (송승윤 결정: **전국 진행**)
- **상태**: 착수 — 칸 0(측정)부터. 계약·사람 선행 없이 시작한다.
- **정본 관계**: 숙소 요구·규칙의 정본은 inception C3(`components.md`)와 BR-U1-14~18
  (`aidlc/aidlc-docs/construction/u1-accommodation-trip/functional-design/business-rules.md`).
  이 문서는 그 아래의 **데이터 출처·수집 설계**를 맡는다. 제휴(딥링크·가격)는 형제 문서
  `제휴링크-연동-설계.md` 가 소유한다 — 둘의 경계는 §6.
- **남은작업 추적**: `work-graph.toml` 의 `STAY-CONTENT-MEASURE`·`STAY-CONTENT-TOURAPI`·
  `STAY-DETAIL-API`·`STAY-ADDRESS-SEED`.

## 0. 한 줄 요약

숙소 정본 12,782곳은 **LOCALDATA 인허가 대장**에서 왔고, 인허가 대장에는 **사진이 없다.**
사진·주소의 현실적 출처는 **TourAPI 숙박(contentTypeId=32)** 이고 — 우리는 이미 그 클라이언트를
갖고 있다. 가격은 여기서 안 나온다(제휴 몫, §6).

## 1. 지금 무엇이 비어 있나 (2026-09-21 실측)

| 필드 | 현재 | 원인 |
|---|---|---|
| 이름·좌표·지역·업태 | **있다**(12,782곳) | `R__seed_stay.sql`, LOCALDATA |
| `address` | **없다** | 생성기가 읽고 **버린다** — `gen_stay_seed.py:114` 가 도로명주소를 region_code 뽑는 데만 쓴다 |
| `imageUrl` | **컬럼도 없다** | LOCALDATA 에 사진이 없다 |
| `amenities` | 전부 빈 배열 | LOCALDATA 에 그 칸이 없다 — 응답이 `amenitiesKnown=false` 로 "없음이 아니라 모름"을 알린다 |
| 가격 | LOCALDATA 건 **0건** | `stay_price_snapshot` 은 `source='STUB'` 5건뿐(제주). 정본은 전부 `LOCALDATA` — **교집합이 0** |

그래서 `STAY_CONTENT_MODE=db` 로 켜는 순간 12,782곳이 **사진 없음·가격 없음**으로 나간다.
켜는 것 자체는 맞지만, 그것만으로 화면이 Figma 와 같아지지는 않는다(TRIP-825 가 기대한 것).

## 2. 왜 TourAPI 숙박인가 — 이미 다 갖고 있다

한국관광공사 TourAPI 의 `contentTypeId=32`(숙박)가 사진·주소·좌표를 준다. 우리 상황에서 이게
정답인 이유는 새 벤더가 아니라 **이미 도는 것의 매개변수**이기 때문이다.

| 필요한 것 | 현재 상태 |
|---|---|
| TourAPI 클라이언트 | 있다 — `ai/src/trippilot/poi_curation/sourcing/tourapi.py` |
| 사진·주소 추출 | **이미 한다** — `firstimage`(:323) · `addr1`(:313) · `mapx/mapy`(:314-315) |
| API 키 | 있다 — GitHub secrets `TOUR_API_KEY`·`KEY2`·`KEY3` (**키링 3개**, 쿼터 분산) |
| 전국 배치 | 있다 — `ai-poi-collect.yml` 이 광역 **17개를 공평 순회**(미설정이 곧 전국) |
| 타입 선택 | 있다 — `TOURAPI_CONTENT_TYPES` 기본 `"12,14,39"` |
| LOCALDATA 대조 | 있다 — `ai/scripts/match_business_status.py` 의 `addr_key()`(주소 4요소 정규화 + 상호 일치). POI 에서 **83.3% 매칭** 실적 |

**지금 32 를 그냥 켤 수는 없다.** POI 파이프라인의 매핑표가 숙박을 명시적으로 버린다 —
`mapping.py:28` *"그 외(15 축제공연행사·25 여행코스·**32 숙박** 등) → None(매핑 불가 — 드롭+카운트)"*.
POI 에 숙박 카테고리가 없으니 그 판단은 옳다. 숙소는 **다른 정본 테이블**(`stay`)이라
같은 입구로 넣으면 안 된다 — §4 가 그래서 별도 경로다.

## 3. 칸 0 — 먼저 잰다 (전국, 계약·사람 선행 0)

**착수 여부를 숫자로 정한다.** 커버리지가 낮으면 이 트랙 자체를 접는 것이 맞고, 그 판단을
코드를 다 짠 뒤에 하면 비싸다.

- 범위: **전국 17개 광역 전부**(2026-09-21 결정). 한 지역 표본은 지역 편차를 못 걸러낸다 —
  제주는 관광 숙박 비중이 전국 평균보다 높을 것이 거의 확실해 **낙관 쪽으로 치우친 표본**이다.
- 잴 값 넷:
  1. TourAPI 숙박 총건수(전국)
  2. 그중 `firstimage` 가 있는 비율
  3. 우리 12,782곳과의 **매칭률**(`addr_key` + 상호)
  4. 매칭된 것 중 사진이 있는 비율 = **실제로 채워지는 칸의 수**
- 산출: 이 문서 §7 에 표로 추기(건수는 산문에 박지 않는다 — `ai/data/README.md` PR #388 규칙).
- 비용: 키링 3개 × 일일 상한 안에서 목록 조회만. 상세(`detailCommon`)는 칸 1 로 미룬다.

**판정선**(착수 전에 정해 둔다 — 결과를 보고 정하면 자기합리화가 된다):
- 매칭 × 사진 보유가 **30% 이상** → 칸 1 진행
- **10~30%** → 진행하되 "사진 있는 숙소 우선 정렬"을 같은 PR 에 넣는다(빈 카드가 섞이면
  사진 없는 쪽이 고장으로 보인다)
- **10% 미만** → 이 트랙을 접고 제휴 콘텐츠 API(§6)를 기다린다

## 4. 칸 1 — 수집·병합 (칸 0 이 받쳐주면)

**POI 제안 입구를 재사용하지 않는다.** `POST /internal/pois/proposals` 는 POI 수집 게이트(INV-1)를
태우는 자리이고, 숙소는 그 게이트의 대상이 아니다(closed-set 은 일정 후보 풀의 규약이지 숙박이
아니다). 같은 입구에 넣으면 게이트 로직이 두 갈래로 갈린다 — TRIP-681 에서 같은 이유로
`proposals` 확장을 접었다.

**API 도 새로 열지 않는다.** 호출자가 아직 하나(배치)뿐이라 수신 엔드포인트를 먼저 만들면
죽은 계약이 된다(TRIP-681 의 결론과 같다). 대신 **생성물로 잇는다**:

```
ai/scripts/collect_stays.py   (tourapi.py 재사용, contentTypeId=32, 전국 17개)
        ↓  ai/data/stay_content.json   (content_id · name · addr1 · firstimage · 좌표)
backend/scripts/gen_stay_seed.py  --content ai/data/stay_content.json
        ↓  R__seed_stay.sql  (address·image_url 채워진 정본)
```

- 마이그레이션: `stay` 에 `address text` · `image_url text` 추가(둘 다 nullable — **없는 것과
  모르는 것을 구분**한다, amenities 선례).
- 병합 키: `addr_key`(주소 4요소) + 상호 일치. **주소가 같아도 상호가 다르면 붙이지 않는다** —
  같은 건물의 다른 숙소에 남의 사진을 붙이는 쪽이 훨씬 되돌리기 어렵다(폐업 대조와 같은 규율).
- 재실행: `R__` 라 체크섬이 바뀌면 다시 돈다 — TourAPI 사진이 갱신되면 다음 수집분이 이긴다.
- **`address` 는 TourAPI 없이도 채울 수 있다.** LOCALDATA CSV 에 도로명주소가 있고 생성기가
  이미 읽는다. 다만 **CSV 가 리포에 없다**(브라우저로만 받는다 — `curl` 403, 생성기 docstring).
  그래서 주소는 CSV 가 오면 **전수**, 사진은 TourAPI 로 **부분** — 두 축을 섞지 않는다.

## 5. 칸 2 — 숙소 상세 계약 (계약 무관, 언제든)

`GET /stays/{stayId}` 가 없다. FE 의 TRIP-323(e03 숙소 상세)이 *"계약 3종 미존재"* 로 보류 중이고
그중 하나가 이것이다 — 나머지 둘(라이브 가격·아웃바운드)은 제휴 몫이라 이것만 먼저 풀린다.

**설계 결정 하나**: `stay` 의 PK 가 `(external_source, external_id)` 복합키라 경로에 그대로 못 넣는다.
- 택: `"LOCALDATA:3000000-201-1965-00264"` 형태의 **합성 문자열**.
- 기각: 대리 UUID 신설 — 시드를 재생성할 때마다 값이 흔들리고, FE 가 이미 두 필드를 따로 들고
  있어 조립만 하면 된다.

## 6. 경계 — 이 문서가 다루지 않는 것

| 항목 | 소유 | 이유 |
|---|---|---|
| 가격(부터가격·정확가) | `제휴링크-연동-설계.md` | C3 설계가 `LivePricePort` = 정확 가격(캐싱 금지)로 두었고, 그 출처가 OTA 다. TourAPI 는 가격을 주지 않는다 |
| OTA 딥링크·클릭·포스트백 | 같음 | C5 |
| 편의시설(`amenities`) | 미정 | LOCALDATA·TourAPI 목록 응답 둘 다 안 준다. TourAPI `detailIntro2` 에 일부 있으나 숙박 필드명이 타입별로 달라 별건 |

**가격이 없어도 서비스는 성립한다** — BR-U1-14 가 *"스냅숏이 없으면 '가격 미확인'을 표기한다.
가격 부재는 카드 제외 사유가 아니다"* 로, BR-U1-15 가 *"실시간 가격순은 미제공"* 으로 이미 못
박아 두었다. 설계가 처음부터 실시간 가격의 비용을 피해 갔다는 뜻이라, 사진·주소를 먼저 채우는
이 순서가 설계와 어긋나지 않는다.
