# 제휴 링크(C5) 연동 설계 — 조사·계획 박제

- **작성**: 2026-09-11 (송승윤 검토, 실측·조사 기반)
- **상태**: **보류** — 구현 착수하지 않는다(2026-09-11 결정). 실질 선행이 사업 계약이고, 어필리에이트
  심사가 "운영 중인 매체"를 전제해 본계약은 출시 시점에 열리기 때문이다. 이 문서는 그때 그대로
  집어들 수 있도록 조사 결과와 칸 단위 계획을 정본으로 남긴다.
- **정본 관계**: 요구·규칙의 정본은 inception C5(`components.md`)와 BR-U1-29~32
  (`aidlc/aidlc-docs/construction/u1-accommodation-trip/functional-design/business-rules.md`)다.
  이 문서는 그 아래의 **연동·구현 설계**를 맡는다. 남은작업 추적은 `work-graph.toml` —
  이 문서 박제 시점 기준 `AFFILIATE-LINK` 노드는 아직 없다(착수 시 칸 0 에서 신설).

## 0. 한 줄 요약

업계 표준은 **서버가 만드는 아웃바운드 리다이렉트 + 클릭 ID(sub_id) 관통 + 서버간 포스트백** 3종
세트이고, inception C5 설계가 이미 그 모양이다. 빠진 것은 코드가 아니라 **계약**(어느 프로그램에
매체로 승인받느냐)이며, 계약 없이도 세울 수 있는 골격(칸 0·1)과 계약 후에만 되는 것(칸 2·3)을
갈라 두었다.

## 2. 업계 구현 표준 (조사, 2026-09-11)

### 3종 세트

1. **서버 아웃바운드 엔드포인트** — 클라이언트가 OTA URL 을 직접 조립하지 않고 자기 서버의
   `GET /stays/{id}/outbound?...` 를 연다. 서버가 클릭 로그를 남기고 302 로 최종 딥링크에 보낸다.
   이유가 우리 BR 과 일대일이다: 날짜·인원 파라미터 정확성(C5 "딥링크 파라미터 정확 구성")을
   서버가 보증하고, 클릭 추적이 공짜로 생기고, OTA 교체가 앱 배포 없이 서버 변경만으로 된다.
2. **클릭 ID 관통** — 우리 클릭 UUID 를 OTA 의 sub-ID 자리(Booking `label`, Travelpayouts
   `sub_id`, Impact `clickref`)에 실어 보낸다. 리다이렉트 과정에서 sub-ID 가 벗겨지면 전환을
   클릭에 못 붙인다 — "파라미터 병합 시 sub-ID 보존"이 구현 체크리스트 1번.
3. **포스트백(S2S) 수신** — 전환 시점에 상대가 우리 웹훅으로 이벤트를 쏜다. 네트워크 이벤트 ID
   기준 **멱등**(재전송 흔함), 예약 확정→투숙 완료→취소 다단 이벤트를 같은 클릭 ID 로 갱신.
   숙박은 "예약 ≠ 매출"(취소·노쇼)이라 다단 대사가 필수다.

### 계약 경로 유형

- **OTA 직계약**: Booking(숙박 완료 기준 ~4%, **세션 기반** — 클릭한 그 브라우저 세션 내 예약만
  인정)·Agoda(셀프서브, CID 즉시 발급)·Expedia(Impact 경유). 통합 1개로 수십만 숙소.
- **제휴 네트워크 경유**: CJ·Awin·Impact, 국내는 **링크프라이스**. 여러 OTA 를 한 계정·한 정산으로.
- **여행 특화 애그리게이터**: Travelpayouts — 예약확정/투숙완료/취소 포스트백을 같은 클릭에
  대사해 주는 여행 전제 설계. 30일 쿠키.
- **메타서치 모델**(스카이스캐너·카약·네이버 호텔): 실시간 가격 피드 응답에 OTA 별 딥링크가 실려
  온다 — 링크를 만드는 게 아니라 오퍼가 가져온다. 우리 `LivePricePort`(캐싱 금지·표시 시점 호출)
  설계가 이 모양이다.

### 모바일 앱 특유 관행

- 이상형은 OTA 앱 유니버설 링크 → 웹 폴백 사다리지만, 앱→앱 어트리뷰션이 자주 유실돼 실무에선
  **인앱 브라우저(iOS SFSafariViewController / Android Custom Tab)로 웹 딥링크**를 여는 쪽이
  흔하다 — 쿠키 기반 세션 어트리뷰션이 보존된다(Booking 류 세션 기반 정책에서 특히 중요).
- 이동 직전 고지 시트(우리 BR-U1-30 문구·국내 표시광고법 "(광고)" 표기)는 통상 패턴 — FE 구현 완료.

## 4. 선행 조건 시행 절차 (사업 몫 — 단계별)

> 주의: 어필리에이트 심사는 "운영 중인 매체"를 전제한다. 미출시 상태에서 지금 되는 것은
> 1단계(기술 검증)와 3단계의 "문의"까지고, **본계약(2단계 매체 승인)은 출시 시점이 사실상 전제**다.

- **0단계 — 내부 준비물**: 정산 주체 결정(개인=실명인증+계좌 / **사업자=사업자등록증 승인+세금계산서
  필수**) · 매체 소개 자료(앱 소개·스크린샷·지표) · 담당자 1명 지정. 백엔드는 아래 6칸 체크리스트를
  질문지로 제공한다.
- **1단계 — Agoda 셀프서브 기술 검증** (지금 가능, 반나절): partners.agoda.com 가입 → CID 즉시
  발급 → 딥링크 규격으로 손 조립 1건 → 모바일·인앱 브라우저에서 **착지 후 파라미터 보존** 확인
  → 결과를 이 문서에 추기. 목적은 수익이 아니라 칸 3 어댑터 설계의 실물 입력이다.
- **2단계 — 링크프라이스 본명 트랙**: 가입(무료·즉시) → **매체 등록**(미출시 앱은 보류될 수 있음 —
  막히면 웹 랜딩으로 우선 등록 후 출시 뒤 앱 매체 추가) → 야놀자·여기어때·아고다 머천트 승인 신청
  (자동=즉시, 수동=1주+) → 머천트별 수수료율·쿠키 기간·앱 트래픽/인앱 브라우저 정책·금지 행위
  확인 → 실적 API 스펙 수령.
- **3단계 — 여기어때 직계약 병행 문의**: 등록 전에 "앱 내 숙소 상세 → 아웃바운드" 매체가 승인
  대상인지 문의로 확인 → 되면 파트너 정보 등록(정산 계좌·신분증·채널, 종합 심사) → 안 되면 이
  트랙은 접고 2단계로 흡수. 정산은 확정 후 익월 말일 지급 구조.
- **4단계 — 스펙 확정 게이트** (백엔드 칸 2·3 착수 조건): 어느 트랙이든 아래 6칸이 채워지면 열린다.

  | # | 확인 항목 | 용도 |
  |---|---|---|
  | 1 | 트래킹 ID(CID/매체코드) | 어댑터 설정값 |
  | 2 | **sub_id 파라미터 이름·길이 제한** | clickId 관통 자리 |
  | 3 | 딥링크 규격(숙소·날짜·인원) | `OtaDeeplinkPort` 구현 |
  | 4 | **숙소 ID 체계 + 매핑 방법**(피드 제공 여부) | 최대 비용 항목 — 피드 없으면 수작업 매핑 |
  | 5 | 전환 통지 방식(실시간 포스트백 vs 배치 API)·서명·재전송 정책 | 웹훅 vs 폴링 설계 갈림 |
  | 6 | 앱 트래픽 정책(인앱 브라우저 인정 여부) | FE 이동 사다리 결정 |

- **5단계 — 법·고지**: 이동 전 제휴 고지(BR-U1-30)·"다시 보지 않기"(BR-U6-33)는 구현 완료.
  "(광고)" 표기 최종 문구는 머천트 가이드 확정 시. 개인정보 처리방침에 클릭 데이터(clickId·숙소·
  시각) 수집 항목 추가는 칸 1 착수와 함께.

## 5. 개발 계획 — 칸 0~3

계약 무관(칸 0·1)과 계약 후(칸 2·3)를 가른다. fake 기본·CI 외부호출 0·모드 스위치 선례
(`RegionGeocodeModeAnnouncer`·`AI_SCHEDULE_MODE`)를 그대로 쓴다.

### 칸 0 — 공백 박제 + 그래프 (30분, 계약 무관)

- `work-graph.toml`: `AFFILIATE-LINK` 노드 신설(status todo, 선행 = 사업 계약(외부), touches =
  `backend/modules/affiliate-link`(신설 예정)·openapi, 이 문서를 note 에서 참조).
- 같은 커밋에서 제휴 고지 저장 노드의 낡은 touches(`modules/affiliate-link` → 실제 구현처
  profile) 정정.
- (이 문서 자체는 2026-09-11 선박제됨.)

### 칸 1 — 아웃바운드 서버 승격 (반나절, 계약 무관·회귀 0)

- **모듈 신설** `modules/affiliate-link` (api/application/domain/infra, R1 준수):
  - `domain`: `OtaDeeplinkPort` — `buildOutbound(stayRef, dates?, party?, clickId): OutboundLink(url, vendor)`
  - `infra`: `WebSearchFallbackAdapter` — FE `stayOutbound.ts` 의 웹검색 URL 생성을 서버로 이식
    (BR-U1-31 우회 경로의 서버 승격). 모드 스위치 기본 `fallback` + 모드 어나운서.
  - `api`: `AffiliateLinkFacade` (inception C5 이름 그대로).
- **엔드포인트**: `GET /stays/{stayId}/outbound?checkin&checkout&adults` → `affiliate_click` 행
  삽입(clickId UUID·accountId·stayId·vendor·요청 파라미터·시각) → 302. 인증 요구 여부는 착수 때
  결정(현 숙소 상세가 로그인 뒤 화면이라 요구가 자연스러움). 실패 시에도 폴백 URL 로 302 — 침묵 금지.
- **마이그레이션**: `affiliate_click` — 번호는 착수 시점에 열린 PR 확인 후 채번(선채번 금지).
  BR-U1-32 준수: 클릭·전환은 내부 지표 전용, 사용자 대면 응답에 미노출.
- **openapi**: outbound 오퍼레이션(302 + Location) 추가.
- **FE 몫(명시만)**: orval 재생성 후 `stayOutbound.ts` 를 서버 `/outbound` 호출로 교체. 그 전까지
  기존 폴백이 그대로 살아 있어 순서 강제 없음.
- **검증**: 모듈 테스트(클릭 행·302·폴백 URL) + 역검증(클릭 로깅 제거 변이 → 해당 테스트만 실패)
  + ArchUnit 신규 모듈 + 전체 빌드 캐시 오프.
- 이득: 계약 전부터 클릭 데이터 축적(협상 근거), OTA 교체가 서버 배포만으로 가능.

### 칸 2 — 포스트백 수신 골격 (계약 후 — 칸 3 과 묶는다)

- `POST /webhooks/affiliate/{vendor}` — 벤더 이벤트 ID 유니크 제약으로 멱등(`affiliate_conversion`),
  서명 검증 fail-closed. **벤더 스펙(§4-4단계 5번) 확정 전 구현은 재작업 위험이 커서 미리 만들지
  않는다.** 링크프라이스가 배치 조회형이면 웹훅 대신 폴링 어댑터로 바뀐다.

### 칸 3 — 실 벤더 어댑터 (계약 확정 후)

- `{Vendor}DeeplinkAdapter`: 트래킹 ID + **숙소 매핑 테이블**(우리 stay ↔ 벤더 숙소 ID — 숨은 최대
  작업, 이름/좌표 매칭은 부정확) + clickId 를 sub_id 자리에 관통.
- `LIVE_AFFILIATE=1` 왕복 IT(선례: LIVE_KAKAO·LIVE_AI) — 실링크 착지에서 파라미터 보존 확인.
  평소 꺼짐(CI 외부호출 0 정책).
- FE 와 인앱 브라우저 결정(어트리뷰션 보존엔 Custom Tab/SFSafariVC 가 표준).

## 6. 리스크

- **숙소 ID 매핑** — 칸 3 최대 비용. 머천트 피드 제공 여부가 관건(§4 체크리스트 4번).
- **앱 매체 승인 불확실** — 여기어때 공고는 SNS 운영자 대상. 문의 결과에 따라 트랙이 접힌다.
- **세션 기반 정책 × 인앱 브라우저** — Booking 류는 클릭 세션 내 예약만 인정. 외부 브라우저로
  열면 세션이 끊길 수 있어 FE 이동 방식과 묶어서 결정해야 한다.
- **포스트백 멱등은 실물 없이 검증 불가** — 재전송·순서 역전은 LIVE 게이트에서만 드러난다.
